# 城瘾 Questify · 三端角色体系专家报告（用户 / 商家 / 俱乐部）

> 目的：把「用户·商家·俱乐部」三端的**定位差异、权限矩阵、功能清单、前后端差距、改造方案、落地顺序**统一成一份可执行的产品 + 技术蓝图。
> 本报告所有「现状 / 缺口」均以当前小程序代码实测为准，非推测。

---

## 0. 一句话结论

> 城瘾本质是一个 **城市级任务操作系统（City RPG OS）**，由三种**生产力**驱动：
> **用户 = 行为生产（Play）｜商家 = 节点生产（Node Supply）｜俱乐部 = 内容生产（Rule & Theme Design）**。
>
> 目前代码已跑通「**玩家打卡 + 发帖 + 商家发券 + 三端身份/额度框架**」这条最浅的线。
> 要成为 OS，还差四块地基：**① 分端权限网关 ② 任务编辑器升级为"城市剧本引擎"（节点类型 + 分支/触发 + 博弈）③ 建群与勋章系统 ④ 三端数据看板 + 优惠券到店核销闭环**。

---

## 1. 系统总定义（统一世界观）

城瘾 = **City RPG OS**。三端是三种生产力，缺一不可：

| 端 | 生产力 | 本质层 | 类比 |
|---|---|---|---|
| 用户 USER | 行为生产 Play | 城市参与层 Player Layer | App 的"用户/玩家" |
| 商家 MERCHANT | 节点生产 Node Supply | 现实节点层 Physical Node Layer | 地图上的"POI / 基础设施" |
| 俱乐部 CLUB | 内容生产 Rule & Theme Design | 城市创作者层 Creator Layer | 游戏的"关卡设计师 / 导演" |
| 城瘾平台 | 撮合 + 引擎 + 结算 | 中台 OS Kernel | 操作系统内核 |

**核心约束（写进权限模型）**：
- 俱乐部**设计规则**，但**不能绑定 / 不能直接控制商家节点**——商家节点的开放权属于"商家自身 + 系统"，俱乐部只能在系统开放的节点池里**引用**。
- 用户是**轻量行为生成者**，不是创作者——可建极简主题，但不触碰高级玩法、券、城市数据。
- 商家是**城市基础设施**，不是内容创作者——出节点、出券、承接活动，但不设计城市玩法结构。

## 2. 三端定位与本质差异（速览）

| 维度 | 用户 USER | 商家 MERCHANT | 俱乐部 CLUB |
|---|---|---|---|
| 一句话定位 | 城市任务的执行者（行为发生器） | 真实空间的任务承接点 + 转化节点 | 城市玩法设计者（规则制定者 + 内容导演） |
| 主题发布额度 | **1** | **3** | **5** |
| 节点能力 | 最多 **2** 个、简单逻辑 | **开放自身为节点**、配置营业/参与规则 | **编排多点路径**（引用开放节点池） |
| 任务逻辑 | 顺序/自由、单点/双点（Lite） | 系统模板（有限） | 完整编辑器：分支/条件/时间触发 |
| 优惠券 | ❌ 不可用 | ✅ 发布（最多 **3**）+ 到店核销 | ✅ 可发布（绑定任务体系） |
| 博弈玩法（竞速/对抗/协作） | ❌ | ❌ | ✅ 配置 |
| 勋章 | **只能获得** | — | **唯一设计权**（设计 + 定义获取规则 + 绑定任务） |
| 建群 | 加入"任务自动群" | 门店运营群 | 城市俱乐部群 + 多群管理 |
| 数据 | ❌ 看不到城市数据 | 到店转化 / 流量来源 / 路径（基础） | 完成率 / 路径行为 / 节点热力 / 流失（进阶） |
| 货币 | 积分（唯一） | 收益（提现） | 收益（提现） |

| `canBranch` 分支/条件逻辑 | ❌ | ❌ | ✅ | |
| `canGameMechanic` 博弈机制 | ❌ | ❌ | ✅ | 竞速/对抗/协作 |
| `canOpenAsNode` 开放为城市节点 | ❌ | ✅ | ❌ | 商家专属 |

## 4. 分端详解（定位 / 功能 / 现状 / 前后端缺口）

### 4.1 用户层 USER —— 城市参与层 / Behavior Layer

**定位**：城市任务的执行者（行为发生器）。

**应有功能**
1. **任务参与（Lite Creator + Player Hybrid）**：可建 1 主题、≤2 节点、顺序/自由 + 单/双点。
2. **城市探索（核心体验）**：任务流推荐、附近/热点任务、节点路径导航、地理触发打卡。
3. **成长（唯一进阶）**：积分（唯一货币）+ 等级（城市身份）+ 成就勋章（仅解锁）。
4. **轻社交**：加入任务自动群、评论 / 打卡分享。

**现状（代码实测）**
- ✅ 打卡：`pages/play`（`/api/play/nodes`、`/api/play/checkin`、扫码、通关）。
- ✅ 探索/路线：`pages/topic`（橙线轨迹 `routePolyline`、城市定向/自由探索 tab）。
- ✅ 积分：`/api/user/points/statistics`、`/api/points/result_list`。
- ✅ 发帖/分享：`square` 正在 Strava 化。
- ⚠️ 等级/成就：`role/center` 与 `subpackageP3/growth`(56 行) 为**写死/空壳**。

**缺口**
- 🔴 **成长体系是假数据**：Lv、Top X%、徽章全硬编码 → 需真实化（见 §5.3 勋章 + §5.4 数据）。
- 🔴 **用户建主题被"创作者额度"卡死或无 Lite 入口**：需 `maxThemes=1 / maxNodes=2` 的轻量发布路径（复用 `publish/fabu` 但按 `permission` 收敛 UI）。
- 🟠 **任务自动群不存在**：报名后无自动建群（IM 仅 1v1，见 §5.2）。
- 🟠 **任务流推荐/附近任务**：`searchmap` 有地图，但"附近/热点任务流"推荐缺。

---

### 4.2 商家层 MERCHANT —— 现实节点层 / Physical Node Layer

**定位**：城市真实空间的任务承接点 + 转化节点（"城市基础设施"，不是创作者）。

**应有功能**
1. **节点系统（核心）**：后台报名开放为节点 → 被俱乐部/系统纳入路线 → 承接触发 → 配置营业时间/参与方式。
2. **主题发布（中高级）**：≤3 主题、有限模板、绑定自身节点。
3. **优惠券（商业闭环核心）**：≤3 券、任务触发发券、到店核销。
4. **活动参与**：加入俱乐部设计的城市活动、成为链路节点、多活动并行承接。
5. **商业数据**：到店转化、流量来源、用户路径（基础）。
6. **社群**：门店运营群、管理到店用户。

**现状（代码实测）**
- ✅ 入驻：`merchant/apply`（5 步 + 营业执照）、`/api/club ... ` 同构的审核状态机。
- ✅ 商家中心：`merchant/index`（"优惠券发布"入口）。
- ✅ 发券：`/api/coupon/mypublishlist`、`coupon/couponInfo`。
- ✅ 品牌报名活动：`topic/merchantjoin`、`topic/merchantapply1~3`、`merchantinfo`。
- ✅ 收益/提现：`/api/user/income/breakdown`、`tixian`。

**缺口**
- 🔴 **"开放为节点"不存在**：当前商家是"报名参加某主题(merchantjoin)"，**不是把门店登记成可被多条路线复用的城市节点**。需独立的**节点注册/节点池**模型（§5.1）。
- 🔴 **到店核销闭环缺失**：有券、无 `核销台`、无 `/api/coupon/redeem`、无"任务完成→触发发券"绑定。
- 🔴 **商业数据看板缺失**：到店转化/流量来源/路径统计无任何页面与接口。
- 🟠 **门店群缺失**：IM 无群。
- 🟠 **节点规则配置弱**：营业时间在 `publish/fabu` 里是"发主题时填"，没有沉淀为节点的常驻属性。

---

### 4.3 俱乐部层 CLUB —— 城市创作者层 / Creator Layer

**定位**：城市玩法设计者（规则制定者 + 内容导演）。

**应有功能**
1. **城市主题设计（核心引擎）**：≤5 主题、发券、完整任务编辑器（多点路径 + 顺序/分支 + 时间/条件触发）。
2. **城市玩法（高级）**：博弈机制（竞速/对抗/协作）、模板调用复制、多主题并行。
3. **勋章（唯一设计权）**：设计勋章 + 定义获取规则 + 绑定任务体系。
4. **社群（组织能力）**：建城市俱乐部群、多群管理、活动组织调度。
5. **数据分析（进阶）**：完成率、路径行为、节点热力（基础）、流失分析。

**约束**：❌ 不能绑定商家、❌ 不能直接控制商家节点（只能引用系统开放的节点池）。

**现状（代码实测）**
- ✅ 入驻：`club/apply`（3 步，`/api/club/apply`、`/api/club/my-apply` 状态机）。
- ✅ 身份中心：`role/center` 展示"主题发布额度 + 资产来源（主题/邀请/品牌收益）"。
- ✅ 任务编辑器（部分）：`publish/fabu` 有**章节 + 节点 + 选点 + 营业时间 + 模板**。
- ⚠️ `subpackageP3/creator`(109 行) 创作者中心为雏形。

**缺口**
- 🔴 **编辑器只到"线性多节点"**：grep 全库**无 分支 / 顺序-自由切换 / 条件触发 / 博弈** 逻辑。要做模式二三（剧情/解谜/博弈）必须升级（§5.1）。
- 🔴 **勋章设计权完全缺失**：无勋章实体、无设计 UI、无获取规则引擎。
- 🔴 **数据分析缺失**：完成率/路径/热力/流失零实现。
- 🟠 **建群与多群管理缺失**：IM 无群。
- 🟠 **节点引用机制缺失**：俱乐部编排路线时，应从"系统开放节点池"选点，而非自由填地址（约束落地点）。

## 5. 引擎层 / 中台（贯穿三端，最关键）

### 5.1 任务编辑器 → 城市剧本引擎（City Game Engine）

**现状**：`publish/fabu` = 章节→节点（描述 + 地点 + 营业时间），节点完成机制只有 `checkin / needScan`。

**目标数据模型**
```jsonc
// topic（主题/剧本）
{
  "id": 1, "ownerType": "club|merchant|user", "ownerId": 9,
  "flow": "sequence|free",            // 顺序 / 自由
  "chapters": [{
    "branch": [{ "ifNode": 3, "ifResult": "pass", "goto": 5 }],  // 分支（仅 canBranch）
    "nodes": [{
      "id": 10,
      "type": "checkin|scan|quiz|puzzle|collect|occupy|minigame", // 节点类型枚举
      "rule": { /* 各 type 的配置：题目/答案/收集物/占领冷却/小游戏ID */ },
      "trigger": { "time": "...", "geofence": {...}, "precondition": [9] }, // 条件触发
      "reward": { "points": 50, "medalId": 7, "couponId": 3 },             // 完成奖励
      "nodeRefId": 88   // 引用商家"开放节点"（俱乐部只能引用，不能新建商家节点）
    }]
  }],
  "gameMechanic": "none|race|versus|coop"  // 博弈（仅 canGameMechanic）
}
```

**关键改造**
- 后端：`topic` 增 `flow / branch / gameMechanic`；`node` 增 `type / rule / trigger / reward / nodeRefId`。
- `play` 完成判定从"打卡/扫码"扩展为按 `node.type` 分派（答题校验、收集计数、占领冷却…）。
- 前端：`publish/fabu` 节点弹层加 **type 选择器**，并按 `permission.nodeTypes / canBranch / canGameMechanic` **按角色收敛**（用户只见 checkin、俱乐部见全集）。

### 5.2 建群 IM（三端共性硬缺口）

**现状**：`subpackageB/im` 仅 1v1（`/api/im/block`）。

**目标**：新增群实体与接口
- `POST /api/im/group/create`（owner=club/merchant；用户无权）
- 用户报名活动 → 系统**自动建/拉入"任务群"**（`groupType=activity`）。
- `groupType: activity | merchant_store | club_city`；群成员/公告/调度（俱乐部多群管理）。

### 5.3 勋章系统（俱乐部设计、用户获得）

**现状**：无后端，`role/center` 写死。

**目标**
- `POST /api/medal/design`（仅 `canDesignMedal`）：名称/图标/获取规则 `rule`（绑定 topicId/nodeId/完成条件）。
- `GET /api/medal/wall?memberId=`：用户勋章墙（替换写死 `BENEFITS`）。
- 任务完成时按 `node.reward.medalId` 发放。

### 5.4 数据看板（商家 store 维度 / 俱乐部 theme+city 维度）

**现状**：零。手册第三章反复要求"完成率/参与/社交数据驱动迭代"，供给侧目前盲飞。

**目标接口**
- 商家：`GET /api/stats/merchant` → 到店转化、流量来源（哪个活动/主题）、用户路径。
- 俱乐部：`GET /api/stats/club` → 主题完成率、节点漏斗、节点热力、流失节点。
- 数据范围由 `permission.dataScope` 网关控制（用户 `self` 看不到城市数据）。

### 5.5 优惠券闭环（发券 → 任务触发 → 到店核销 → 结算）

**现状**：能发券（商家），但**任务不触发券、到店不能核销**。

**目标**
- 任务侧：`node.reward.couponId` 完成发券。
- 核销侧：商家 `核销台` 页 + `POST /api/coupon/redeem {code}`（仅 `canRedeemCoupon`）。
- 结算侧：核销数据进 §5.6 分账。

### 5.6 三端结算 / 分账（OS Kernel）

**现状**：`wallet/tixian` 有提现壳，分账规则不透明。
**目标**：定义分账引擎——用户(积分↔权益) / 俱乐部(内容分成) / 商家(核销实收-平台抽佣) / 平台(撮合抽成)，对账 + 流水可查。

## 7. 改造方案（How）

**原则一：单一权限事实源。** 所有角色差异收敛到 `/api/role/info.permission`。前端实现一个 `roleGuard(capability)` 工具，UI 一律按能力位渲染/禁用，**禁止散落 `if (role==='club')` 判断**。

**原则二：节点类型化。** 把"完成机制"从硬编码（打卡/扫码）抽象为 `node.type + node.rule` 枚举，`play` 用策略分派。新增玩法 = 加一个 type，不动主流程。这是"城市游戏引擎"的技术内核。

**原则三：节点与内容解耦。** 商家**生产节点**（`node` 实体，归商家+系统）；俱乐部**生产规则**（`topic` 引用 `nodeRefId`）。从模型上保证"俱乐部不能控制商家节点"——只能引用开放池，落点合法性由后端校验。

**原则四：双数据范围。** `permission.dataScope` 网关：用户 `self`、商家 `store`、俱乐部 `theme+city`，后端按 scope 过滤，杜绝越权看城市数据。

**数据模型落点（最小集）**
```
permission(role)          // §3 全集，单一事实源
node(merchant)            // 商家开放节点池：geo/营业/参与规则
topic(owner) -> chapters -> nodes(type/rule/trigger/reward/nodeRefId)
medal(club) -> rule -> 发放(user)
```

## 8. 落地顺序（里程碑）

> 按"解锁三边飞轮"排序，而非按页面美观。
