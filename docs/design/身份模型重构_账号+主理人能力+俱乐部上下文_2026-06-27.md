# 身份模型重构:一个账号 + 主理人能力 + 俱乐部上下文

> 2026-06-27 拍板。废止"role=club 即切成另一个身份"的隐式口径。
> 不推倒重来——`club_leader` / 多俱乐部 / `cms_topic.club_id` 已建好;主要错在前端和部分接口仍把 `club` 当"登录后要跳走的身份"。

## 核心结论

**保留一个登录账号。**

- 后端不再把 `role=club` 理解为"这个人不再是玩家",而是"这个人具备主理人能力"。
- 前端不再因 `role=club` 自动踢到俱乐部管理台;用户默认仍在玩家/发现体验,只有点"管理俱乐部 / 发团 / 报名管理"时才进入 club context。

一句话:**`member` 永远是这个人,`club_leader` 是他的能力,`clubId` 是当前管理对象。**

## 三层模型

| 层 | 表 | 语义 |
|---|---|---|
| 个人账号层 | `ums_member` | 登录/头像/昵称/手机/积分/钱包/订单/报名,**永远保留玩家能力** |
| 主理人能力层 | `club_leader`(member_id 唯一,一人一档) | 能力/经验/L1-L5/资质/标签——"有没有资格办团" |
| 组织实体层 | `club`(member_id,一人最多 2) | clubType/city/logo/cover/desc/activityPrefs/keywords/style;团/成员/动态/群聊/合作挂 clubId |
| 关系层 | `club_member`(role=1 为管理员) | 成员/管理员关系 |

## 已核实的代码缝(根因)

能力判定绑在**单值 `ums_member.role`** 上、且互相覆盖,这是唯一真缝:

1. `RoleServiceImpl.resolveRole`(:21)= 直接读单值 `member.role`。
2. 权限/配额 `userPermissionService.getByRole(resolveRole(member))` = 一个 role 一套权限,**装不下"同时是主理人+商家"**。
3. `ApiClubController.ensureRole`(:164)成为主理人 → `role` 覆盖成 `club`。
4. `MmsMerchantController`(:109)商家审核通过 → `role` 覆盖成 `merchant`。→ **二者互相冲掉**。
5. 发团门禁 `ApiTopicController`(:132)查 `role=='club'`,**不是"有没有 club_leader 档"**。
6. 反例:先成主理人(role=club)、后开商家(role=merchant)→ 名下有 club_leader+俱乐部却**发不了团**。

✅ 已经对的:报名 `createRegistration` **不查 role** → 玩家能力本来就始终在;`club_leader.member_id` 唯一;数据层一个 member 可同时挂 leader/club/merchant,无跨表互斥约束。

## 后端怎么改

### 1. `/api/role/info` 扩成"能力快照"(短期不动表)
```json
{
  "role": "club",
  "effectiveRole": "club",
  "isClubLeader": true,
  "isMerchant": false,
  "ownedClubs": [],
  "joinedClubs": [],
  "permission": {},
  "usage": {}
}
```
重点:`role=club` 只代表能力,不代表默认视角。长期更干净是 `member_capability` 多能力表,现在不做。

### 2. `ApiClubController`
- `/become-leader` 成功仍可保留 `role=club`,但语义=**解锁主理人能力**。
- `/my-apply` 降级为旧兼容,不再走主流程。
- `/update-mine` 前端必须传 `id`,后端继续强校验 `club.memberId == currentMemberId`。
- 新增 owner/admin 工具:
```java
private boolean canManageClub(Long clubId, Long memberId) {
    Club club = clubService.selectClubById(clubId);
    if (club == null) return false;
    if (memberId.equals(club.getMemberId())) return true;
    ClubMember cm = clubMemberService.selectByClubAndMember(clubId, memberId);
    return cm != null && cm.getRole() != null && cm.getRole() == 1;
}
```

### 3. 城市定向团发布(`ApiTopicController`)
- 门禁由 `ROLE_CLUB` 改为 **判断有 `club_leader` 档**。
- 城市定向团**必须传 `clubId`**,校验该 clubId 属于当前用户。
- 不再用"当前 role 是不是 club"作唯一判断(一个人仍是玩家,但有主理人能力,也能以某俱乐部发团)。

### 4. 报名管理接口(新增)
- `POST /api/club/enrollments`,入参 `clubId`,权限 owner 或 `club_member.role=1`。
- 返回该 club 下所有团/票种/报名者名册/成团状态。
- 清退退款仍只允许 owner(管理员放权待后续明确)。

### 5. `/api/topic/info-to-user`(公开详情)
- 不再返回报名者明细(`cmsRegistrationList`)。
- 只返回报名人数/库存/成团阈值。名册只走 club 管理接口(#4)。

## 前端怎么改

1. `identity-policy.js`:删/弱化全局 `isClubView()` 自动跳转;新增 `isClubLeader(snap)=snap.role==='club'||snap.isClubLeader`。club 是能力不是默认视角。
2. `pages/index/index`:不再自动跳 `/pages/club/index`;主理人也能看玩家首页;首页加"我的俱乐部/管理台"入口但不强跳。(商家强跳暂不动)
3. `roleGuard.js`:缓存扩展 `isClubLeader / ownedClubs / joinedClubs / activeClubId? / permission`。
4. 新增 `utils/context/current-context.js`:`{ mode:'player'|'club', clubId, locked }`。管理台发团=`mode=club,clubId=A,locked=true`;普通入口发团=`clubId=null,locked=false`;回浏览=`mode=player`。
5. `pages/club/index`:`onCreateTeam`/`onEdit` 带 clubId;编辑→`club/edit?clubId=`;发团→`publish/topicadd?clubId=&lockClub=1`。
6. `pages/club/detail`:owner"发起城市定向团"带 `clubId=this.data.clubId&lockClub=1`。
7. `pages/publish/topicadd`:接收 `clubId/lockClub`,跳 `fabu` 时续传。
8. `pages/publish/fabu`:`onLoad` 读 `clubId/lockClub`;`lockClub=1` 锁定俱乐部选择器,显示"归属俱乐部:XX"不可切;提交必带 clubId。(已有 formData.clubId/myClubs 基础)
9. `pages/club/edit`:弃 `my-apply`,改 `update-mine` 带 id;字段统一 `clubType/city/keywords/style/activityPrefs/logo/cover/description`;`leaderName/phone` 移到主理人档案。
10. `pages/club/enroll`:弃 `info-to-user`,改 `/api/club/enrollments`;管理员可看、普通成员不可看;清退仅 owner。
11. `pages/shezhi` `pickClub`:按快照分流——非主理人→apply;主理人无团→create;有团→index;已 2 个→index。
12. `pages/role/center`:按 `isClubLeader`+`ownedClubs.length` 显示(成为主理人/创建俱乐部/管理台);玩家积分资料照常展示。

## 数据库

短期不需大改(`club_leader`/`club`/`club_member`/`cms_topic.club_id`/`club_post` 已有)。
长期可选:`member_capability`(替代单值 role)、`club_operator_permission`(细化管理员:看报名/发动态/退款/编辑)。现在先用 `club_member.role=1` 做管理员。

## 改造顺序

1. 停 `role=club` 自动跳管理台,主理人仍能正常玩家浏览。(前端)
2. 扩 `/api/role/info` 返回 `isClubLeader/ownedClubs/joinedClubs`。(后端)
3. 打通 `clubId` 上下文:管理台/详情 → topicadd → fabu → backend。
4. 改 `club/edit` 指定俱乐部编辑。
5. 新增报名管理专用接口,替换 `info-to-user` 名册读取。
6. 改设置页和身份中心入口。
7. 整理文案:统一叫"管理俱乐部 / 以某俱乐部发起",不叫"切换俱乐部账号"。
