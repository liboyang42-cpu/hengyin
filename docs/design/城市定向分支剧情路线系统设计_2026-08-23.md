# 城市定向分支剧情路线·系统设计

> 状态：本地实现与自动化验证完成，外部发布 NO-GO · 基线：`github/master@133c62f0d4e78db496efba071574550d5cc88f67` · 更新：2026-08-23

## 1. 目标与范围

在不改变旧 `LINEAR` 城市定向的前提下，增加主题级 `BRANCH_GRAPH`：节点玩法产出稳定 `outcomeCode`，服务端根据冻结路线图和本局状态决定下一个物理地点。

本次做到 M5 首版，包括确定性分支、权威 session、复制重映射、完赛口径、创作/玩家端、多条件池与可重放随机、图形辅助查看、子图复制/导入、校验与模拟。不包括自由拖拽编辑，也不包括生产迁移、合并、部署、微信上传和真机发布。

M4 已接入当前仓内可确认的票种、购买类型、活动角色、节点营业时间与节点间直线距离；事实缺失、无效或服务异常统一判 `UNKNOWN`，不冒充可用。仓内没有可信玩家实时位置，也没有可作为生产真源的道路封闭/路网可达服务，因此 `maxDistanceMeters` 明确表示“当前路线节点到候选节点的地理线段距离”，`requireReachable` 当前通过 provider seam fail-closed 到 explicit fallback，不能宣称实时路网已经上线。

## 2. 深模块与 seam

| Module | Interface（同时是测试 seam） | 隐藏的实现复杂度 |
|---|---|---|
| `TopicRouteEngine` | 冻结配置 + state + `NodeOutcome` → route decision | trigger/condition/priority/weight/effect/fallback/seed |
| `NodeAccessPolicy` | 用户 + 局 + node → playable/原因 | LINEAR `sortId`、BRANCH session、节点额外门禁 |
| `TopicCompletionPolicy` | 局上下文 → completed/进度 | 线性全节点、分支 terminal、未选分支排除 |
| `TopicRouteRuntimeService` | start/state/advance | 快照、owner/scope、幂等、CAS、decision log、事务 |
| `TopicRouteCandidatePolicy` | 仓内事实 + node requirements → available/unavailable/unknown | 票/角色/营业/距离、外部可达性 fail-closed |
| `TopicRoutePublishGate` | 路线图 + 生产引擎 → 可发布/精确错误 | 每条候选的确定性夹具，不依赖随机样本“碰运气” |
| 创作端 route graph module | form state ↔ schema/validation/layout | client key、DB id、边编辑、错误定位、图布局 |
| 玩家端 route state adapter | API payload → 页面可消费状态 | LINEAR 兼容、隐藏/锁定/可玩、重试与冲突恢复 |

## 3. 数据合同

### 3.1 主题路线图

```json
{
  "schemaVersion": 1,
  "startNodeId": 101,
  "terminalNodeIds": [999],
  "variables": {},
  "nodeRequirements": [
    {
      "nodeId": 203,
      "allowedTicketIds": [88],
      "allowedPurchaseKinds": [1],
      "requiredRoleCodes": ["LEADER"],
      "requireOpen": true,
      "maxDistanceMeters": 1500,
      "requireReachable": true
    }
  ],
  "edges": [
    {
      "id": "e_history",
      "fromNodeId": 101,
      "trigger": { "type": "PREFERENCE_RESULT", "outcomeCode": "HISTORY" },
      "conditions": [],
      "effects": [{ "op": "ADD_TAG", "value": "HISTORY" }],
      "toNodeId": 203,
      "priority": 100,
      "weight": 1,
      "once": true,
      "maxVisits": 1,
      "allowLoop": false
    }
  ],
  "fallbacks": [{ "fromNodeId": 101, "toNodeId": 102 }]
}
```

新建主题的节点尚无数据库 ID，因此创建 DTO 允许每个节点携带一次提交内稳定的 `clientNodeKey`。后端在节点落库后的同事务中将 graph 里的 client key 全部重映射为 DB id；任一 key 无法映射则整体失败。

路线 JSON 的 canonical 字段固定为：`trigger.outcomeCode`；condition 使用 `op/var/value`（`NODE_COMPLETED` 另带 `nodeId`）；effect 使用 `op/var/value`。历史草稿的 `code/name/type/variable/operator/tag` 只允许在解析边界归一，持久化和跨端夹具一律输出 canonical 形状。

首次创建时临时节点引用必须显式写成 `startNodeKey/terminalNodeKeys/fromNodeKey/toNodeKey`，`NODE_COMPLETED` 使用 `nodeKey`；禁止把字符串 key 塞进 `*NodeId` 冒充数据库 ID。

### 3.2 路线状态

```json
{
  "routeMode": "BRANCH_GRAPH",
  "sessionId": 7788,
  "status": "ACTIVE",
  "currentNodeId": 203,
  "recommendedNodeId": 203,
  "version": 8,
  "nodeStates": {
    "101": "COMPLETED",
    "203": "PLAYABLE",
    "305": "HIDDEN"
  },
  "decisionLog": []
}
```

`nodeStates` 值域固定为 `HIDDEN | DISCOVERED_LOCKED | PLAYABLE | COMPLETED`。小程序不接收全部隐藏节点的敏感剧情内容，不能用 `sortId` 改写 `BRANCH_GRAPH` 的当前节点。

### 3.3 动作合同

- 只读恢复：`GET /api/play/route-state?topicId=...&activityId=...`
- 各原有完成请求附加：`routeActionId`、`expectedRouteVersion`
- 客户端不提交 `outcomeCode`、`targetNodeId`；服务端从可信完成事实生成 `NodeOutcome`
- 完成响应附带最新 `routeState`；版本冲突使用项目现有 `AjaxResult` 错误合同，客户端再回读状态

## 4. 事务、安全与可恢复性

1. 节点完成事实和路线推进在同一可恢复协调链路中恰好一次。
2. 同库写入同事务；不能同事务的奖励/外部副作用通过 outbox + 幂等消费恢复。
3. `NodeAccessPolicy` 在所有 checkin/answer/puzzle/sensor/arrive/photo 等写入入口之前执行。
4. route session 使用 owner/scope 校验、`routeActionId` 幂等、`version` CAS。
5. effect 仅支持白名单操作；不执行 JavaScript、SpEL、SQL 或任意脚本。
6. 完赛口径集中到 `TopicCompletionPolicy`；`BRANCH_GRAPH` 以 session 到达 terminal 为准，未选分支不计入分母。
7. 节点奖励、掉落与路线推进共用外层事务；奖励异常向外抛出并整体回滚，重试不留下“路线已走、奖励待人工”。
8. `route_graph_json/config_version` 仅保存草稿，`published_route_graph_json/published_config_version` 只在服务端发布门禁成功后复制并递增；新 session 只读发布快照，既有 session 继续自己的冻结快照。迁移文件已生成但尚未执行，生产仍是 NO-GO。
