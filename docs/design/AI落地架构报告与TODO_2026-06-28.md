# 城瘾小程序 AI 落地架构报告与 TODO

日期：2026-06-28  
范围：城瘾小程序、RuoYi 后端、AI 创作助手、AI NPC/陪伴能力、DeepSeek + MiniMax 双模型接入

## 1. 结论

当前架构不是完整生产落地状态，而是“AI 创作助手半落地 + AI NPC/陪伴原型级”。

如果第一阶段只做俱乐部/商家侧的 AI 组题、主题草稿、节点助手、安全预检，仓库已经具备大约 60%-70% 基础，主要差在真实模型配置、灰度开关、上线验证和后台运营能力。

如果目标是玩家侧 AI 陪伴、NPC 聊天、长期记忆、活动内剧情互动、语音陪伴，则当前只具备后端雏形，距离完整落地还缺 MiniMax provider、场景化模型路由、小程序聊天体验、记忆系统、运营后台和合规闭环。

推荐路线：

- DeepSeek：作为低成本默认模型，负责主题生成、节点生成、商家/俱乐部策划、安全预检、结构化 JSON 输出。
- MiniMax：作为陪伴/NPC 强角色模型，负责活动内 NPC、多轮角色聊天、后续语音陪伴。
- Mock：保留为测试、灰度、模型异常兜底。

## 3. 当前主要缺口

| 模块 | 当前状态 | 缺口 |
|---|---|---|
| DeepSeek 接入 | 有 provider 雏形 | application.yml 仍默认 mock/qwen 配置，未完成真实 DeepSeek 回测 |

## 4. 目标架构

### 4.1 推荐调用链

```text
小程序
  -> RuoYi API Controller
  -> AI Gateway
  -> Scene Router
  -> DeepSeek / MiniMax / Mock
  -> 内容安全后检
  -> 日志 + 成本统计 + 审核队列
  -> 小程序展示 / 回填编辑器 / NPC 对话
```

### 4.2 模型分工

| 场景 | 推荐模型 | 原因 |
|---|---|---|
| 主题草稿 | DeepSeek | 成本低，结构化输出够用 |
| 节点玩法 | DeepSeek | JSON 输出、短文本生成、成本敏感 |
| 商家组题 | DeepSeek | 需要事实约束和候选商家反幻觉 |
| 安全预检 | DeepSeek + 规则 | 模型只做补充判断，不能替代规则/微信安全 |
| 俱乐部活动策划 | DeepSeek | 成本低，适合高频创作 |
| NPC 事件话术 | 缓存话术优先 | 低延迟、低成本、可控 |
| NPC 自由追问 | MiniMax | 更适合角色对话和陪伴感 |
| 长期陪伴/语音 | MiniMax | 后续扩展语音和角色生态更顺 |
| 模型故障兜底 | Mock + 预设话术 | 保证体验不断链 |

## 5. DeepSeek + MiniMax 接入设计

### 5.1 配置建议

不要继续只用一个 `CHENGYIN_AI_API_KEY` 承载所有模型。建议拆成：

```yaml
ai:
  model:
    defaultProvider: deepseek
    dailyLimit: 20
    timeoutMs: 8000
  providers:
    deepseek:
      enabled: true
      apiKey: ${CHENGYIN_DEEPSEEK_API_KEY:}
      baseUrl: https://api.deepseek.com
      model: deepseek-v4-flash
    minimax:
      enabled: false
      apiKey: ${CHENGYIN_MINIMAX_API_KEY:}
      baseUrl: https://api.minimax.io/v1
      model: MiniMax-M2.7
    mock:
      enabled: true
```

说明：

- DeepSeek 官方 API 文档显示 base URL 为 `https://api.deepseek.com`。
- MiniMax 官方 OpenAI 兼容文档显示 base URL 为 `https://api.minimax.io/v1`。
- 具体模型名以最终开通控制台为准，接入时要以官方控制台可调用 model id 回测。

参考：

- DeepSeek API Docs：https://api-docs.deepseek.com/
- DeepSeek Pricing：https://api-docs.deepseek.com/quick_start/pricing
- MiniMax OpenAI SDK：https://platform.minimax.io/docs/api-reference/text-openai-api
- MiniMax Pricing：https://platform.minimax.io/docs/guides/pricing-paygo

### 5.2 场景路由建议

新增 `AiSceneRouter`：

```text
merchant_plan           -> deepseek
theme_draft             -> deepseek
node_generate           -> deepseek
safety_precheck         -> deepseek
merchant_task_suggest   -> deepseek
club_design             -> deepseek
npc_event               -> cache only
npc_chat                -> minimax
npc_chat_fallback       -> cached_line/mock
```

### 5.3 数据表建议

当前 `ai_generation_log` 和 `npc_chat_log` 可以保留，但建议补充：

- `ai_model_provider_config`：后台配置 provider、model、enabled、timeout。
- `ai_scene_route`：场景到模型的路由配置。
- `ai_usage_daily`：按日期、用户、角色、场景、模型统计调用量和成本。
- `ai_prompt_template`：prompt 模板版本化。
- `ai_moderation_case`：AI 内容人工复核记录。
- `npc_memory_summary`：用户/活动维度的长期记忆摘要。

第一阶段不一定全部建表，P0 至少补 `ai_usage_daily` 或在 `ai_generation_log` 中补真实 token 入/出字段。

## 7. 优先级排序

### 先做

1. DeepSeek 创作助手真实接入。
2. AI 输出 JSON 稳定性和异常兜底。
3. 小程序 AI 创作页到发布页完整回填。
4. AI 日志、频控、内容安全闭环。

### 后做

1. MiniMax NPC 自由聊天。
2. NPC 前端聊天体验。
3. 长期记忆。
4. 语音陪伴。
5. 高级运营后台。

### 暂不建议做

1. 一上来做“AI 恋人/情绪陪伴”。
2. 玩家首页强推 AI 聊天。
3. 未做审核就开放用户自定义 NPC 人设。
4. 不做预算控制就开放无限聊天。
5. 前端直连任何模型 API。

## 8. 风险清单

### 技术风险

- 模型输出不是合法 JSON，导致解析失败。
- SSE 在微信小程序环境兼容性需要单独验证。
- MiniMax/DeepSeek API 抖动时，用户体验可能不稳定。
- 当前 AI/NPC 文件有未提交状态，需要先梳理归属再继续开发。

### 成本风险

- NPC 自由聊天比创作助手更容易烧 token。
- 长上下文记忆如果不摘要，会快速放大成本。
- 没有月预算熔断会导致不可控账单。

### 安全风险

- AI 可能生成危险线下行为建议。
- NPC 可能被诱导输出不合规内容。
- 用户输入可能包含隐私、联系方式、敏感内容。
- 微信内容安全异常 fail-open 对公开发布内容不够稳。

### 产品风险

- AI 如果喧宾夺主，会削弱城瘾“线下探索/城市任务”的核心。
- 陪伴方向如果做得太泛，会变成普通聊天工具，没有城瘾差异化。
- 角色人设如果没有审核，会带来品牌和合规风险。

## 9. 推荐最终方案

第一阶段只上线“AI 创作助手”，定位为俱乐部和商家的生产力工具：

```text
DeepSeek + AI Gateway + 内容安全 + 日志 + 频控 + 发布页回填
```

第二阶段灰度“AI NPC”，定位为城市探索中的向导和剧情角色：

```text
MiniMax + NPC Profile + 事件缓存话术 + 活动进度记忆 + 小程序聊天浮层
```

第三阶段才做长期陪伴：

```text
用户偏好记忆 + 成本预算 + 后台运营 + 合规公示 + 语音能力
```

这条路线成本低、风险可控，也更符合城瘾的产品定位：AI 不是主产品，AI 是让城市探索、活动策划、NPC 剧情更好玩的增强层。
