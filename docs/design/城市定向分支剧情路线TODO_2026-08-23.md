## 1. 最终要交付的结果

把现在的：

```text
完成当前节点 → 按 sortId 进入下一站
```

升级为：

```text
完成当前节点
  → 取得服务端认可的 outcomeCode / choiceId
  → 根据本局状态过滤合法路线边
  → 由服务端决定并保存下一站
  → 解锁不同城市地点
  → 后续可分开、汇合或进入不同结局
```

### Definition of Done

- [ ] 旧主题默认 `LINEAR`，路线和完成规则与现在一致。
- [ ] 新主题可选 `BRANCH_GRAPH`，玩家在同一节点的不同选择/结果能解锁不同的下一个真实地点。
- [ ] 路线决策由服务端权威计算，小程序不能上报任意 `targetNodeId` 跳关。
- [ ] 刷新、断网重试、换设备后，玩家仍恢复同一当前节点和同一条已选路线。
- [ ] 复制整个主题时，所有路线节点 ID 随 `nodeIdMap` 重映射；复制通用节点模板时不携带某座城市的地点 ID。
- [ ] 发布前可检出悬空目标、不可达节点、无终点路线、非法环、无 fallback 死路。
- [ ] 每项关键门禁都有独立负控，故意破坏时能稳定变红。

## 2. 已锁定的产品与领域决策

以下结论不在实现期反复摇摆：

1. **路线是“整个主题”的配置，不是单个节点模板的配置。**
2. **节点玩法只产出通用结果。** 例如 `HISTORY`、`ART`、`CORRECT`、`ASSISTED`；不在通用模板里写死城市地点 ID。
3. **路线边负责将结果映射到地点。** `fromNodeId + outcomeCode/choiceId + conditions -> toNodeId`。
4. **玩法节点、物理地点节点、路线边、玩家路线局是四个不同概念。**
5. **“隐藏”、“已发现但锁定”、“可玩”、“当前推荐”、“已完成”必须分开。** 不再用一个 `done` 反推全部状态。
6. **V1 先上确定性分支，不先上随机。** 随机只能是“合法条件池内的可重放抽取”，不是 shuffle 剩余地点。
7. **存档保存运行状态，并指向发布时配置快照。** 发布后修改主题不能中途改掉玩家已开局的路线。

- [ ] 客服/作者能从 `decisionLog` 看到甲乙分别为何走 B/C。
