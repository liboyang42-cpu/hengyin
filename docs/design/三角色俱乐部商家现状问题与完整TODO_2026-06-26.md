## 0. 一句话结论

当前系统已经从“只有商家首页、俱乐部只有申请页”的阶段，推进到“商家经营台雏形 + 俱乐部管理台/详情页/动态/成员管理雏形”的阶段。

但还没有完整闭环:

- 俱乐部还缺: 多俱乐部模型、主题发布时选择归属俱乐部、成团人数/报名截止/退款规则写进主题发布、订阅消息、IM 群聊入口、排行榜、商家协作邀请、完整验收链路。
- 商家还缺: 商家公开主页、核销台账/订单处理页、完整经营漏斗、商家与俱乐部协作页、准入闸统一 RBAC、事件流沉淀。
- 现有规划文档已经落后于当前代码: 它把部分已实现内容仍写成缺口，同时又提出“一人多俱乐部”等目标，但没有充分展开 DB/API/前端迁移成本。

## 1. 当前三角色真实状态

### 1.1 共享架构

当前不是三个独立小程序，而是一个小程序共享壳:

- 统一 `app.json` tabBar。
- 统一登录态与 `role/user_type`。
- 统一权限源 `/api/role/info`。
- 首页通过 `pages/index/index.js` 做身份分流:
  - 玩家: 走默认首页。
  - 商家: 跳 `pages/merchant/index/index`。
  - 俱乐部/达人: 跳 `pages/club/index/index`。

底层角色事实源:

- 后端 `RoleServiceImpl.resolveRole()` 优先使用 `ums_member.role`。
- `role` 为空时，`user_type == 2` 兜底为商家。
- 前端通过 `roleGuard.js` 缓存 `/api/role/info` 的 `permission/usage`。

### 1.2 玩家 player

当前定位:

- 城市体验消费者。
- 可轻量创建主题。
- 可加入俱乐部。
- 参与活动、报名、游玩、拿积分/勋章。

已具备:

- 默认首页、广场、模板、我的、游玩页。
- 成长、勋章、积分、订单、券等基础能力已有不同程度实现。
- 玩家可以进入团体/俱乐部发现入口。

主要缺口:

- 玩家加入俱乐部后的“团体动态、活动提醒、群聊、排行榜”仍未完整串起来。
- 玩家视角的活动详情还需要按 Strava/旅游团式体验重构。
- 玩家订阅消息授权与活动提醒链路缺失。

### 1.3 商家 merchant

当前定位:

- 城市节点 / 门店供给方。
- 发券、核销、经营、参与主题招募。
- 可作为俱乐部路线里的消费/体验节点。

已具备:

- `pages/merchant/index/index` 商家首页。
- 商家资料、收入、曝光、待处理订单。
- 近 7 日收入趋势。
- 今日待办: 待核销、扫码待确认、待发货。
- 券统计: 领取、核销、在用券。
- 真实动态接口: 收入到账、核销事件。
- 扫码验券、优惠券发布、财务结算、品牌中心、品牌招募广场。
- 后端接口: `/api/merchant/dashboard`、`/api/merchant/todo-summary`、`/api/merchant/coupon-summary`、`/api/merchant/events`。

主要缺口:

- 商家准入闸还在 `onLoad` 使用旧 `user_type` 判断，和 RBAC policy 不一致。
- 缺玩家视角的商家公开主页。
- 缺订单/核销台账页。
- 缺完整经营漏斗: 曝光 -> 访问 -> 报名/下单 -> 核销 -> 收入。
- 缺商家承接档案和“商家看俱乐部/发邀请”能力。
- 缺与俱乐部/达人合作的结构化邀请流程。

### 1.4 俱乐部 / 达人 club

当前代码里 `role='club'` 实际承担“达人/主理人身份”。`club` 表是俱乐部实体。

已具备:

- `pages/club/apply/index`: 申请。
- `pages/club/edit/index`: 编辑资料。
- `pages/club/index/index`: 俱乐部管理台。
- `pages/club/detail/index`: 俱乐部详情/主页雏形。
- `app.json` 已注册 club apply/detail/index/edit。
- 首页已分流到 `pages/club/index/index`。
- 后端 `/api/club/update-mine` 已存在。
- 后端 `/api/club/my` 已存在。
- 后端 `/api/club/topics` 已存在。
- 后端 `/api/club/post/list/create/like/comment` 已存在。
- 后端 `/api/club/set-member-role` 已存在。
- 后端 `/api/club/members/remove-member/join/quit/detail/list` 已存在。
- `cms_topic.club_id` 已作为俱乐部城市定向团归属字段。
- `club_post`、`club_post_like`、`club_post_comment` 相关迁移和 mapper 已存在。

主要缺口:

- 仍然是“一人一个俱乐部”的代码和 DB 模型，和“达人可建多个俱乐部”目标冲突。
- 管理台 `club/index` 和详情页 `club/detail` 已经存在，但规划文档目标是 `club/home` 三视角合一，路线冲突。
- 俱乐部“活动”目前是 `CmsTopic.clubId` 关联主题，不是完整旅游团模型。
- 成团人数、最低成团、报名截止、退款规则、集合点等尚未明确落进主题发布器/票种配置。
- 订阅消息没有接入。
- IM 群聊没有接入俱乐部/活动。
- 排行榜没有接入 club 主页。
- 动态缺内容安全、举报、删除/下架。
- 成员列表可能不显示 owner 本人，`memberCount` 口径也可能不含主理人。

## 2. 当前代码问题

### 2.1 P0 问题

#### 2.1.1 新迁移依赖强，部署顺序错会直接炸

当前代码已经引用:

- `cms_topic.club_id`
- `club_post`
- `club_post_like`
- `club_post_comment`

如果生产库未先执行对应 migration，新 jar 会出现“列不存在 / 表不存在”的 SQL 错误。

需要执行/确认:

- `migration_club_topic_link.sql`
- `migration_club_topic_backfill.sql`
- `migration_club_post.sql`
- `migration_club_post_like.sql`
- `migration_club_post_comment.sql`
- `migration_club_fields.sql`

验收要求:

- 先只读预检生产库是否已有字段/表。
- 再执行 migration。
- 再部署 jar。
- 再上传/预览小程序。

#### 2.1.2 商家准入闸仍使用旧事实源

`pages/merchant/index/index.js` 的 `onLoad` 仍用:

```js
if (wx.getStorageSync('user_type') != 2) {
  wx.redirectTo({ url: '/pages/index/index' });
  return;
}
```

但 `onShow` 又使用 `policy.isMerchantView({ role, userType })`。

问题:

- `role=merchant` 但本地 `user_type` 未同步为 2 时，会被误踢。
- 入口事实源不一致，容易复现“身份跳转错乱”。

修复方向:

- `onLoad` 也统一用 `policy.isMerchantView(viewSnap)`。
- 或者先等待 `/api/user/info` / session 恢复后再做准入。

#### 2.1.3 “达人可建多个俱乐部”尚未实现

当前数据库:

```sql
UNIQUE KEY uk_club_member (member_id)
```

当前后端大量使用:

- `clubService.selectClubByMemberId(memberId)`
- `/api/club/my` 返回 `owned` 单个对象
- `CmsTopicServiceImpl` 发布城市定向时自动取当前用户唯一俱乐部

如果要支持“一人多个俱乐部”，必须改:

- DB 唯一索引。
- `selectClubByMemberId` 改为列表。
- `/api/club/my` 返回 `owned[]`。
- 发布主题必须传 `clubId`。
- 前端管理台必须有俱乐部切换器。
- 旧数据回填策略。

#### 2.1.4 主题发布缺“成团配置”

你明确提到“成团人数需要写在主题发布里面”，这是对的。现在俱乐部活动复用 `CmsTopic`，所以成团配置不能新散在别处，应该写入主题发布/票种层。

需要补进发布器的字段:

- 最低成团人数 `minPeople`
- 最大人数/名额 `maxPeople`
- 报名截止时间 `signupDeadline`
- 集合点名称 `gatherPoint`
- 集合点经纬度 `gatherLng/gatherLat`
- 成团失败退款规则 `refundRule`
- 出发前退款规则 `cancelRule`
- 是否需要主理人确认 `needAudit`，当前建议预留不启用
- 成团状态 `teamStatus`: 招募中 / 已成团 / 未成团退款 / 已结束 / 已取消

落地位置:

- 如果按“活动=主题城市定向”，优先扩展 `OmsTicket` 或主题票种 DTO。
- 前端应在 `publish/temp`、`publish/simple` 的城市定向票种配置里出现。
- 后端在报名、支付、退款、活动开始前定时任务中使用这些字段。

### 2.2 P1 问题

#### 2.2.1 当前 club/index 与规划 club/home 路线冲突

当前已有:

- `pages/club/index/index`: 管理台。
- `pages/club/detail/index`: 详情/主页。

文档目标:

- `pages/club/home/index`: 三视角合一，后台内嵌。

必须先拍板:

1. 保留当前两页模式:
   - `club/index` = 主理人后台
   - `club/detail` = 对外主页
2. 或迁移到一页模式:
   - `club/home` = 游客/成员/主理人三视角合一

建议:

- 短期保留两页，减少返工。
- 后续如果 UI 需要 Strava 式三视角，再把 `club/detail` 升级成 `club/home`，`club/index` 作为轻管理台保留或重定向。

#### 2.2.2 俱乐部成员 owner 口径不完整

当前 `club_member` 是加入关系，owner 存在 `club.member_id`，不一定在 `club_member` 里。

影响:

- 成员列表可能没有主理人。
- `memberCount` 可能不包含主理人。
- 排行榜/群聊权限判断容易漏 owner。

建议:

- 方案 A: 创建俱乐部时同步插入 owner 到 `club_member`，role=2。
- 方案 B: 查询成员列表时 union owner。
- 短期建议 B，风险低；长期建议 A，模型更清晰。

#### 2.2.3 俱乐部动态缺治理闭环

当前有动态、点赞、评论，但缺:

- 文本/图片内容安全检查。
- 举报。
- 删除自己的动态/评论。
- 主理人下架动态/评论。
- 平台后台审核/封禁。

建议:

- 发动态、评论前接现有 `WxContentSecurityService`。
- 增加 `/api/club/post/delete`。
- 增加 `/api/club/post/comment/delete`。
- 增加举报表或复用内容审核体系。

#### 2.2.4 订阅消息缺失

没有看到 `wx.requestSubscribeMessage`。

旅游团/成团必需的提醒:

- 报名成功。
- 达最低人数成团。
- 未成团自动退款。
- 出发前提醒。
- 集合点变更。
- 报名/退款状态变更。

#### 2.2.5 IM 没接入俱乐部

IM 基建存在，但俱乐部没有:

- 俱乐部群聊入口。
- 活动群聊入口。
- 报名成功后自动入群。
- 退出俱乐部/取消报名后权限变化。

建议:

- 俱乐部维度一个长期群。
- 每个城市定向团可选一个活动群。
- 初期只做俱乐部群入口，活动群后置。

### 2.3 P2 问题

#### 2.3.1 排行榜没有接入

文档提到复用 `QuestifyLeaderboardDark`，但当前 club 页面未看到排行榜接入。

建议:

- `/api/club/leaderboard?clubId=`
- 指标: 完成节点数、报名次数、获得勋章、近 7 天活跃。

#### 2.3.2 商家与俱乐部协作完全未落地

当前没有:

- 商家承接档案。
- 商家看俱乐部。

#### 2.3.3 数据埋点和运营后台缺失

## 4. 俱乐部完整闭环还缺什么

### 4.1 产品闭环

完整俱乐部应该闭环为:

1. 玩家看到“团体”入口。
2. 玩家申请成为达人/主理人。
3. 平台审核通过。
4. 达人创建或维护一个/多个俱乐部。
5. 达人在发布主题时选择归属俱乐部。
6. 达人创建城市定向团，并配置成团人数、截止时间、退款规则。
7. 玩家浏览俱乐部主页。
8. 玩家加入俱乐部。
9. 玩家报名城市定向团。
10. 报名付款占位。
11. 达到最低成团人数后自动成团。
12. 未达成团人数则自动退款。
13. 成团后订阅消息提醒。
14. 活动前进入群聊。
15. 活动中进入 `pages/play` 游玩。
16. 完成后沉淀战报、勋章、排行榜。
17. 达人查看数据和收益。

当前已具备 1、2、3、7、8、部分 9、部分 15、部分 16。

缺口集中在 4、5、6、10、11、12、13、14、17。

### 4.2 前端页面缺口

必需页面/模块:

| 页面/模块 | 当前状态 | 建议 |
|---|---|---|

## 6. 推荐的目标架构

### 6.1 短期先不要强行重构成 club/home

建议当前阶段:

- 保留 `pages/club/index/index` 作为主理人管理台。
- 保留 `pages/club/detail/index` 作为俱乐部对外主页。
- 文档里 `club/home` 可以作为下一阶段统一页目标，但不要现在推翻已有实现。

原因:

- 当前代码已有两页雏形。
- 继续补功能比迁移路由更快。
- 现有页面可以先跑通 MVP，再做体验合并。

### 6.2 俱乐部活动不新建 club_event，但必须扩展主题发布

建议:

- 不新建 `club_event`。
- 继续采用 `CmsTopic.clubId`。
- 把成团配置写进主题发布/票种配置。

推荐字段放在 `OmsTicket` 或主题票种配置:

| 字段 | 说明 |
|---|---|
| `min_people` | 最低成团人数 |
| `max_people` | 最大名额 |
| `signup_deadline` | 报名截止 |
| `gather_point` | 集合点名称 |
| `gather_lng/gather_lat` | 集合点经纬度 |
| `team_status` | 招募中/已成团/未成团退款/已结束/已取消 |
| `refund_rule` | 阶梯退款规则 |
| `need_audit` | 是否需要主理人确认，先预留 |

前端发布器:

- 只有选择“城市定向”票种时显示成团配置。
- 达人身份发布时必须选择所属俱乐部。
- 商家发布城市定向时不归属 club，走商家/合作逻辑。

### 6.3 多俱乐部建议分阶段

> ❗**已被 C1 推翻(2026-06-26,见 §0.0):现在就做多俱乐部,不分阶段、不后置。** 下方「短期继续一人一个」建议作废;§2.1.3 改造清单即本期施工清单。

短期:

- 继续一人一个俱乐部。
- 先跑通 MVP。

中期:

- 取消 `club.member_id` 唯一限制。
- `/api/club/my` 返回 `owned[]`。
- 发布主题选择 `clubId`。
- club 管理台增加切换器。

理由:

- 多俱乐部改动横跨 DB/API/前端/发布器/权限。
- 当前更优先的是让一个俱乐部完整跑通。
