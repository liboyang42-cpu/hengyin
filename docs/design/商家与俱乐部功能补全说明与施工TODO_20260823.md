## 1. 最终方案

不新增“第二套商家后台”或“第二套俱乐部后台”，在现有信息架构内补齐缺口：

- 商家维持 5 个一级入口：**工作台、营销、模板、合作、我的**。
- 俱乐部维持详情页 4 个身份化视图：**帖子、活动、概览、管理**；Owner 与获授权角色看到按权限裁剪的“管理”，普通成员不显示。
- 高频待办进入工作台或管理页，低频配置进入“我的”或设置，单个客户/成员操作进入详情或半屏操作层。
- 复用现有退款状态机、结算、CRM 基础表、`marketing-home`、俱乐部群聊、团码和入会审核，不重建同义模型。
- 资金、权限、通知和导出写入统一遵守“锁定权威主体后重新鉴权、同事务写 durable 状态、提交后从服务端权威回读”；HTTP 200、toast 或本地合成状态都不是完成证明。

补齐后，产品目标是达到：

- 商家 **L2 核心经营闭环完整**：团队分权、售后处理、CRM、基础归因和导出均可真实闭环。
- 俱乐部 **L2 核心组织闭环完整**：可委派角色、候补/重复活动、成员治理、分群通知、会费/续费均有明确状态。
- L3 项目（自动化 CRM、高级 ROI、会员等级自动运营、平台级风控）可以后置，不能拿来阻塞 L2。

### 依赖顺序（当前工作树已形成代码候选）

以下是已实现能力的依赖关系，用于后续拆分评审、迁移和发布；研究文档只说明可复用边界，不覆盖本文档的产品合同。

1. **0A 语义前置**：预约假入口已清理；CRM 生产迁移/写入链路仍须发布前只读核实。
2. **0B1 权限基础前置**：商家主体解析、permission 常量和 scope guard 是团队 UI/邀请与售后的共同依赖；发布拆分不得让业务 API 越过 guard。
3. **0D1 角色基础前置**：俱乐部角色和 scope 是封禁、转让、举报申诉、候补与活动通知的共同依赖。
4. **后续域依赖 P0 合同**：CRM/导出依赖商家权限；候补/通知依赖俱乐部场次角色；会费独立 feature flag。
5. 候补、通知、导出的代码候选已在对应 P0 合同之上完成；发布时仍必须先落权限/治理依赖迁移，再启用后续任务。

## 2. 不重复建设清单

|---|---|---|
| 商家营销聚合 | `/api/merchant/marketing-home`，已聚合漏斗、优惠券和内容数 | 扩字段和时间维度，不新建另一个首页聚合接口 |

| 退款状态机 | `refund_application`、`RefundService`、微信原路退款、人工兜底、maker≠checker | 商家仅提交同意/举证/拒绝建议；真金打款仍走平台已有安全链路 |

| 导出能力 | RuoYi `ExcelUtil` 已在大量后台控制器使用 | 后端导出复用现有工具；小程序只发起受控导出任务/下载，不引入新 Excel 库 |
| 商家底层身份 | 现有 JWT + role/userType + owner 校验 | 团队权限是商家域授权，不复制系统后台 `sys_role` 到小程序用户侧 |
| 俱乐部角色 | `club_member.role` 当前为成员/管理员，`set-member-role` 已做 Owner 归属校验和管理员上限 | 演进为角色+作用域，不另建一份“群管理员”关系 |
| 俱乐部沟通 | `/api/club/chat` 原生群聊、帖子/评论/点赞、站内消息 | 通知编排复用现有会话和订阅消息；不再造独立聊天系统 |
| 俱乐部现场 | 报名名册、团码、扫码核销、到场/未到事实 | 增候补、负责人和出勤纠正，不重建票或签到表 |
| 俱乐部经营配置 | `scene-club-edit` 已有入会审批、成员优先报名、保留名额 | 会费/等级作为子配置进入，不把长表单继续堆在同一首屏 |
| 审计事件 | `biz_event_log`、`SysOperLog`、退款/核销流水均已存在 | `biz_event_log` 只做分析；后台操作用 `SysOperLog`；小程序高风险动作统一写 `business_audit_event`，领域终态仍留在各自业务表 |

## 3. GitHub 代码复用决策

完整源码与许可证核查见 [GitHub 复用研究](../research/merchant-club-github-reuse-20260823.md)。采用原则是“仓内优先、小依赖其次、跨语言只移植模型、copyleft 不复制”。

| 仓库 | 可用内容 | 城瘾采用方式 | 决策 |
|---|---|---|---|
| [apache/casbin-jcasbin](https://github.com/apache/casbin-jcasbin) | domain RBAC：subject + domain + object + action | 只有固定 service guard 已难维护时才另行评估；保留现有 JWT/登录/用户表 | **本轮未采用**，Apache-2.0，Java 8 |
| [ical4j/ical4j](https://github.com/ical4j/ical4j) | RRULE、重复活动展开、ICS | 当前未获批、未引入；未来若立项只能评估 Java 8 兼容 3.x adapter | **本轮不采用**，BSD-3-Clause |
| [flarum/framework](https://github.com/flarum/framework) | 举报、封禁原因/期限、停权、审计字段 | 只参考状态与表边界，本轮为城瘾仓内自行实现 | **未引包/未复制**，MIT |
| [krayin/laravel-crm](https://github.com/krayin/laravel-crm) | Tag、Activity、SavedFilter | 只对照领域分层，本轮使用现有 CRM 表与城瘾服务内实现 | **未引包/未复制**，MIT |
| [killbill/killbill](https://github.com/killbill/killbill) | 计划、订阅、权益、账单、支付解耦 | 只参考会费状态机；不引完整平台/模块 | **仅参考**，Apache-2.0，当前 Java 11 且过重 |

直接复用城瘾仓内实现：

- Excel：`chengyinhub-common/.../ExcelUtil.java` + 已有 Apache POI 4.1.2。
- 通知：`NotifyEvent`、`NotifyMessage`、`WxSubscribeChannel`、`BeforeStartNotifyTask` + Quartz。
- 二维码：现有 ZXing 3.5.2、小程序扫码与后端核销台账。
- CRM：`MerchantCustomerProfile`、`MerchantCustomerTag`、`MerchantCrmServiceImpl`。
- 权限/审计：`PermissionService`、owner/scope guard、`@Log`、`SysOperLog`，再补业务治理审计。

许可证红线：

- Pretix、Hi.Events 是 AGPL 路线，Alf.io 是 GPL-3.0；只观察公开功能分层，**不复制源码、SQL、测试或翻译后端算法**。
- 本轮没有获批 iCal4j，代码也没有引入。未来若冻结任意 RRULE/ICS 合同，必须另行验证 Java 8 兼容 3.x；不能直接跟最新 4.x。
- jCasbin 不是必选依赖。若角色规则仍能用清晰的 Java service guard 表达，就不为“看起来先进”增加抽象。
- 候补队列自建小型事务状态机：`WAITING → OFFERED → CONVERTED`，旁路 `CANCELLED/EXPIRED`；现成 GPL/AGPL 实现不进入代码。

第三方真正进入 POM 前必须新增 `docs/licenses/merchant-club-third-party-adoption.md`，逐项冻结 Maven coordinate、精确版本、上游 tag/commit、Java 8 构建证据、传递依赖许可证、LICENSE/NOTICE 归档位置和升级复核条件。研究时的漂移分支链接不能直接充当上线依赖证据。

### 5.1 商家工作台：健康，禁止继续加第五个快捷操作

首屏的扫码、客户、财务、更多已经形成稳定的 4 项主任务。售后应以红点/数字待办进入财务，团队设置应去“我的”，避免挤压扫码和客户。

### 5.2 商家“更多”：结构健康，但“预约”语义错误

施工前“预约”错误跳向核销记录。本轮采用短期删除方案；只有完成预约资源、时段、容量、预约单和到店态后，才可恢复“预约管理”。经营团队已进入商家“我的”，没有堆入该菜单。

### 5.3 客户：适合加详情层，不适合再加一级入口

施工前的分段与最近行为已经清楚。本轮已让整行可点，用详情页承载标签、备注、来源、最近活动和联系记录；批量筛选与导出保留在列表顶部。

### 5.4 营销：唯一正确的数据承载页

累计报名和核销率卡上方空间足以容纳 `7天 / 30天 / 自定义`；卡下方先放真实五步漏斗，再放渠道，不需要增加“数据”一级 tab。

### 5.5 俱乐部管理：核心入口较多，不再扩顶层 tab

项目、探店日期次、商家、项目工具已经较长。新能力应进入现有对象：场次能力进入“开一场/报名名册”，组织能力进入成员和设置。

### 5.6 俱乐部成员管理：角色和治理的自然入口

成员管理位于管理页末段，符合低频组织治理。本轮已将单一“设管理/取消管理”扩展为角色与作用域选择，并把移除与封禁分成不同操作。

### 5.7 俱乐部设置：拆子页，不继续纵向堆字段

施工前弹层已包含形象、资料、类型、活动倾向、会员经营配置和解散。本轮已把“会员与会费”“组织治理”放入独立子场景，没有把会费周期、黑名单和转让继续塞进原长表单。

### 5.8 活动取消人工退款：资金台是主场，俱乐部只放快捷入口

判额、凭证、复核和纠错属于财务风控，因此唯一队列放在 Web 后台“资金与售后→退款处理台”。俱乐部详情的“带队履约”保留带当前 `clubId` 的快捷入口，不重做财务表格；小程序既有 `club-card` 和 `pages/talent/**` 保持零 diff。

## 6. 商家功能补全规格

### M0. 经营团队与最小权限（P0）

#### 用户故事

- Owner 可以邀请店员加入商家团队并撤销邀请。
- Owner 可以分配“核销员、运营、财务、店长”预设角色。
- 店员使用自己的城瘾账号登录，不能共享 Owner 账号。
- 敏感数据默认不可见：核销员看不到完整客户资料和财务，运营看不到结算账户，财务不能改品牌或核销。

#### 预设角色

| 角色 | 默认权限 |
|---|---|
| Owner | 全部权限、角色管理、团队移除；不可移除自己 |
| 店长 | 项目、客户、营销、核销、售后建议；不管理 Owner、不改收款主体 |
| 核销员 | 仅扫码、核销记录、当场名单；电话默认不可见 |
| 运营 | 内容、优惠券、合作、基础客户分群；无财务与退款打款权限 |
| 财务 | 结算、售后金额与凭证；无客户营销和品牌编辑权限；财务文件安全导出链未落地前不暴露假权限 |

#### 技术落点

- 权限数据模型冻结为**分域表**：商家用 `merchant_operator`、`merchant_operator_invite`；俱乐部用 `club_role_assignment`。两者共享权限决策接口和命名规则，但不建统一 `business_role_assignment`，避免不同生命周期互相污染。
- 商家主体 Owner 由现有 `MmsMerchant.memberId` 解析，不额外复制一行 Owner assignment。
- 唯一有效角色码：`MERCHANT_OWNER`、`MERCHANT_MANAGER`、`MERCHANT_CHECKIN`、`MERCHANT_MARKETING`、`MERCHANT_FINANCE`。`MERCHANT_OWNER` 由商家主体关系运行时派生、禁止写入 operator 表；UI“店长/核销员/运营/财务”只做中文映射。
- 权限码使用商家域常量，例如 `merchant:verify`、`merchant:crm:read`、`merchant:finance:read`、`merchant:aftercare:respond`。
- 所有商家 API 先由登录 memberId 解析 `merchantId + operator role`，服务层再校验 owner/scope；不能相信前端传入 merchantId。
- Owner 写入口统一以 `mms_merchant(id) FOR UPDATE → 当前 Owner ums_member active FOR UPDATE → operator/invite/资料子行` 为锁序，并在锁后重验 owner、账号态和权限；商家行 ID 与 Owner memberId 始终分离，多有效门店或转让后的 stale Owner 一律 fail-closed。
- Owner 转让在同一事务撤销全部 ACTIVE operator 与 PENDING invite；商家资料更新还以 `expectedOwner` 和 SQL 的 `id + member_id + del_flag/account_status/status` 双重围栏阻止旧 Owner 覆盖新 Owner 数据。
- 现有 Owner 身份保持兼容，灰度期查不到 operator 记录时只有商家主体本人拥有 Owner 权限。
- 首版优先写清晰的 service guard；只有按组织/活动动态规则膨胀后才接 jCasbin domain RBAC。
- 角色变更统一追加 `business_audit_event(action=MERCHANT_ROLE_*)`；不新建第三套 operator audit 表。

#### 验收

- 核销员能扫码成功，但请求客户导出、结算、角色管理均为 403。
- Owner 移除员工后，该员工下一次请求立即失权；旧 token 不继续获得商家权限。
- 修改角色、移除、重邀均产生不可变审计记录。
- 负控：把核销员错误授予财务权限时，权限契约测试必须从绿变红。

### M1. 售后中心（P0）

#### 设计

- 工作台在 4 个快捷操作下方仅当 `refundCount > 0` 显示“有 N 笔售后待处理”。
- 点击进入 `/pages/merchant/ledger/index?view=aftersale`。
- 售后列表按 `待回应 / 平台处理中 / 已完成` 分段；详情展示退款原因、证据、政策快照、金额、截止时间和处理历史。
- 商家动作只允许：`同意退款`、`拒绝并说明`、`补充凭证`。真金打款和最终复核继续走现有 `RefundService`、微信退款及 maker≠checker 闸。
- 凭证上传使用专用 `merchant_aftercare_evidence` 策略；客户端只提交 `evidenceKeys`，服务端校验受控 object key 后持久化 key，详情再按权限签发 5 分钟预览 URL。直接提交 `evidenceUrl`、外域 URL 或不合规 key 均拒绝。
- Finance 角色可补充凭证，但不能据此获得同意/拒绝退款的决策权；凭证区放在售后详情决定区，不进入客户 CRM。

#### 接口建议

- 复用：`POST /api/merchant/orders/ledger` + `filter=aftersale`。
- 新增：`POST /api/merchant/aftercare/detail`。
- 新增：`POST /api/merchant/aftercare/respond`，载荷含 `refundId`、`decision`、`reason`、`evidenceKeys`、`idempotencyKey`。
- 返回值必须包含服务端终态或最新处理中状态；前端提交成功后重新 GET/POST 读回，不以 toast 为成功证明。

#### 验收

- 只有订单归属商家且具备 `merchant:aftercare:respond` 才能操作。
- 超时、重复提交、已终态退款均幂等，不重复打款。
- 商家同意不等于退款成功；UI 必须区分“已提交意见 / 平台处理中 / 已退款”。
- 上传成功但 object key 或后续权威详情回读缺失时，UI 不得显示凭证已保存；响应行与不可变审计必须同事务成立。
- 负控：篡改 refundId 指向他店订单必须失败，且测试能变红。

### M2. 客户 CRM（P1）

#### 设计

- 客户行可点，打开 `merchant-customer-detail` 场景层。
- 详情固定顺序：客户摘要 → 系统标签 → 商家标签 → 私有备注 → 最近活动/核销/退款时间线 → 联系与触达记录。
- 列表增加标签与来源筛选；支持多选后“加标签、发优惠券、发送合规通知、导出”。
- 自动分段仍由真实报名/核销事实计算，手工标签不得覆盖“待核销、退款异常”等系统事实。

#### 数据与复用

- 标签真源冻结为 `merchant_customer_tag_assignment(merchant_id, member_id, tag_id)`，唯一键为三者组合；`merchant_customer_profile.tags_json` 只做可重建读缓存，不接受直接写入。
- 复用 `merchant_customer_tag` 作为商家标签定义；先核实现网迁移状态再开发。
- 新增 `merchant_customer_note` 保存追加式备注。备注不可原地编辑；纠错新增一条并引用 `corrects_note_id`。删除仅改为隐藏并记录 deletedBy/deletedAt，原文仍为受控审计数据。
- `merchant_customer_profile` 作为画像缓存，由订单/报名/优惠券事件增量更新；保留可重建 aggregate 作为对账工具。
- 手机号、导出和触达必须遵循当前受控可见性；俱乐部带队订单不因进入 CRM 而放开手机号。

#### 验收

- 同一 memberId 跨项目只形成一个商家客户档案，最近事件来自真实业务记录。
- 手工标签、系统标签和备注边界明确；删除标签不删除客户事实。
- 导出文件按操作者权限脱敏、有过期时间、有下载审计；无权限人员拿到 URL 也不能下载。
- 负控：把其他 merchantId 传给详情/导出接口必须失败。

### M3. 营销分析与渠道归因（P1）

#### L2 当前冻结范围

- 时间范围：7 天、30 天；默认 30 天，统一按 `Asia/Shanghai`（北京时间）完整自然日计算。当前产品主要服务中国用户，本轮不扩展多时区配置。
- 五步漏斗：浏览 → 报名 → 支付 → 核销 → 退款。
- 入口触点只展示当前能从权威业务事实证明的主题入口、活动入口、未归因三类，并明确返回
  `coverage=PARTIAL`、`attributed=false`；不能把 ownerType 或前端参数猜成分享卡、海报、优惠券、
  俱乐部合作等渠道。
- 对比：当前周期与上一个等长周期；没有样本时显示“暂无可比较数据”，不计算假百分比。

自定义周期以及分享卡、海报/二维码、优惠券、俱乐部合作等完整渠道归因属于后续扩展：必须先在
报名/支付等事件入口保存受白名单约束的权威 `channel`/`campaignId`，完成迁移、幂等和生产读回后
才能开放。当前 L2 不以假渠道或 URL query 补齐界面，也不把这部分勾成已完成。

#### 技术落点

- 扩展 `/api/merchant/marketing-home`，保持一个聚合入口。
- 复用 `biz_event_log` 的分析事件，新增低基数 `channel`/`campaignId` 时需白名单，禁止写入手机号、姓名、URL query 或自由文本。
- 日聚合可以复用 `BizFunnelDaily` 形态；原始事件和经营审计不可混为同表同保留策略。

#### 验收

- 同一支付/核销事件按幂等键只计一次。
- 任一步骤统计都可下钻到明确口径说明，不用前端当前页数据自行求总数。
- 时间边界固定按 `Asia/Shanghai` 统一；跨北京时间午夜、退款回补和订单关闭有测试。
- 负控：删除支付事件映射后，支付漏斗测试必须失败。

### M4. 名单导出与合规触达（P1）

- 后端复用 RuoYi `ExcelUtil`，不在小程序端拼 Excel。
- 小程序提交导出任务，后端返回 `taskId`；任务完成后返回短期签名下载地址。
- 文件默认脱敏，只有明确权限和业务依据才包含更高敏字段。
- 导出、下载、失败、过期均留审计；文件自动过期清除。
- 触达优先复用站内信、订阅消息、优惠券，不默认批量暴露手机号。
- 下载拆成两个阶段：`authorizeDownload` 只校验当前 Owner/`CRM_EXPORT`、token、任务与私有文件，不提前增加下载次数或写审计；只有 HTTP 文件流写出返回后才调用 `completeDownload`。
- `completeDownload` 在一个短事务中以 CAS 首次完成下载并追加恰好一条不可变审计；状态或审计任一写入不为 1 都整体失败。Owner/门店 lineage 漂移时先在数据库中失效引用，私有文件只能在事务提交后删除。
- 小程序轮询必须把空任务、身份/scope/count/status 不一致和未知状态当失败/待确认，不能在 HTTP 200 空数据时本地合成“导出完成”。

### M5. 预约与口碑（P2）

- **预约短期决策：删除当前假入口。** 只有资源/服务、时段、容量、预约单、取消规则、到店状态和通知都存在时，才恢复为“预约管理”。
- 口碑需新建商家评价 owner type 或独立聚合，支持已核销用户评价、图片、商家回复、举报和平台处理。
- 公开评价与商家私有备注严格分离；商家不能修改用户原评，只能回复/举报。

## 7. 俱乐部功能补全规格

### C0. 角色与按场次授权（P0）

#### 角色模型

| 角色 | 作用域 | 能力 |
|---|---|---|
| Owner/主理人 | 俱乐部 | 全部、转让、解散、会费、角色 |
| Co-owner/联合主理人 | 俱乐部 | 日常运营与成员管理；不能转让/解散/改收款主体 |
| Operator/运营管理员 | 俱乐部 | 帖子、公告、入会审核、通知；无财务 |
| Event lead/活动负责人 | 指定场次 | 编辑当场运营信息、查看当场名册、发送当场通知 |
| Check-in/签到员 | 指定场次 | 仅扫码/手工签到；无全员名单和财务 |
| Member/成员 | 俱乐部 | 参与、发帖、评论、群聊 |

#### 演进方式

- 权限真源冻结为 `club_role_assignment(club_id, member_id, role_code, scope_type, scope_id, valid_from, valid_until, status)`。
- 唯一有效角色码：`CLUB_OWNER`、`CLUB_CO_OWNER`、`CLUB_OPERATOR`、`EVENT_LEAD`、`EVENT_CHECKIN`、`CLUB_MEMBER`；其中 assignment **只允许持久化** `CLUB_CO_OWNER / CLUB_OPERATOR / EVENT_LEAD / EVENT_CHECKIN`。`CLUB_OWNER` 从 `Club.memberId` 派生，`CLUB_MEMBER` 从正常 `club_member` 关系派生，两者写入 assignment 一律拒绝。
- `Club.memberId` 继续是唯一 Owner 真源；`club_member.role=1` 的存量迁移为 club scope 的 `CLUB_OPERATOR`，迁移读回后该字段只作兼容展示，不参与最终授权。
- 当前 `set-member-role` 改为 role assignment 服务；旧客户端的 0/1 请求只映射成员/运营管理员，不得创建联合主理人。
- 平台 Web 后台的旧 `club_member.role` 改岗也必须同步走 canonical assignment：设管理员写 `CLUB_OPERATOR`，撤销只撤 `CLUB_OPERATOR`，不伤及其他有效角色。
- 管理页成员行“设管理”改为“权限”，打开角色 sheet；场次详情单独分配活动负责人/签到员。管理 tab 对 Owner、Co-owner、Operator、Event Lead/Check-in 按权限显示不同工具，未授权模块不渲染且后端仍强校验。
- 俱乐部作用域的 `/api/club/access/me` 返回受控 `eventAccesses` 摘要；只持有 `EVENT_LEAD/EVENT_CHECKIN` 的成员也能发现管理入口，但每个工具仍以摘要中的真实 `activityId + permissions` 二次裁剪，不把活动权限上提为俱乐部全局权限。已删除、跨俱乐部、过期或重复/畸形摘要均 fail closed。
- 成员主动退出、俱乐部/平台移除、临时/平台封禁、Owner 转让都会撤销该成员所有有效 assignment，并追加审计；不只删旧 `club_member` 行。
- 场次物化时，非 Owner 默认负责人必须创建真实 `EVENT_LEAD` assignment；不用场次字段写了 ID 就当已授权。
- Owner 转让必须验证对方已是正常成员、不存在以其为对象的待处理治理案件，二次确认后原 Owner 降级，整个事务只能有一个 Owner。

#### 验收

- 签到员能处理指定场次，不能读取其他场次名册或全体成员。
- 联合主理人不能解散、转让或修改收款主体。
- 撤销场次授权后立即失权；权限缓存不得超过服务端撤销生效窗口。
- 负控：跨 clubId、跨 sessionId 调用必须失败。

### C1. 成员封禁、举报与申诉（P0）

#### 状态区别

- 移除：当前关系结束，允许按俱乐部策略重新申请。
- 俱乐部临时封禁：关系结束且在 7/30/90 天内禁止重新申请，必须有原因、操作者、到期时间和撤销记录；Owner/Co-owner 只能执行这种范围内封禁。
- 平台永久封禁：只有平台治理角色可执行；平台处理俱乐部、活动或用户风险，俱乐部 Owner 不能创建、撤销或抹除。
- 申诉：面向平台复核，不直接回到被举报的主理人单方裁定。

#### UI

- 管理→成员管理→成员操作层：权限、移除、临时封禁（7/30/90 天）。
- 设置→组织治理：黑名单、处罚记录、主理人转让。
- 普通成员：俱乐部详情概览提供 `CLUB` 举报，活动行先解析真实 activityId 后提供 `ACTIVITY` 举报，成员行保留 `MEMBER` 举报；三者共用治理页但不混淆 targetType/targetId。“我的消息/帮助”查看处理与申诉。

#### 验收

- 被封禁用户不能再次加入、不能进群、不能继续发帖或评论。
- 解封不会自动恢复成员关系，只恢复申请资格。
- 俱乐部端 ban API 的 `endAt` 必填且最长 90 天；永久封禁只存在于平台 API，不能通过传 null 或超长日期绕过。
- 举报人、被举报人、证据和处理记录按角色脱敏；Owner 看不到平台敏感风控信息。
- 封禁、解封、转让和申诉结果均有不可变审计。

### C2. 候补、重复活动与出勤闭环（P1）

- “开一场”当前只支持 `ONCE / WEEKLY / CUSTOM_DATES`，并支持结束条件、默认负责人、容量、候补开关。
- 系列只保存规则和模板；每一期生成独立场次，支付、名册、签到、退款和结算仍按具体场次落账。
- 本轮未获批 iCal4j，没有任意 RRULE/ICS 解析。`CUSTOM_RRULE` 、ICS 导出/订阅和“仅本场/以后场次/整组”编辑语义明确延后。
- 名额释放后按队列原子晋级。晋级时会跳过已离会的 stale `WAITING` 候补者，不为其占库存；`OFFERED` 在 quote/claim 两个入口都重新校验活跃会员身份。支付窗口内锁定一个临时名额，始终满足 `confirmed_count + active_offer_hold_count ≤ capacity`；支付成功转 `CONVERTED`，超时/取消在同一事务释放 hold 后再发给下一位。
- 报名名册分为已报名、候补、已到、未到；活动结束后负责人可在有限窗口内更正，所有更正留痕。
- 变更/取消向已报名和候补人群分别通知，不依赖群聊消息可见性。
- “取消本场”只接受当前俱乐部内真实 `activityId`，要求原因和稳定 `requestId`；只有锁后仍为 Owner/Co-owner 且具备 exact activity 的 `ACTIVITY_MANAGE` 才可执行。只持有 `EVENT_LEAD/EVENT_CHECKIN` 的 EVENT-only 角色即使能运营当场，也不能取消或触发退款。
- 取消事务先快检，再锁 series 与 club，锁后用新鲜 assignment/Owner 重新鉴权；随后在**同一数据库事务**中先快照取消前 REGISTERED 与 WAITLIST 两类收件人，再复用真实 `TeamGroupService` 活动取消/退款、CAS 取消 occurrence、撤销活动级角色、终止 `WAITING/OFFERED/CLAIMED` 并释放 hold，最后为两类快照各写 durable campaign/delivery/outbox。任一步失败整笔回滚，不能先发通知再回滚。
- 取消通知使用内部保留的 `cancel-r-` / `cancel-w-` requestId 受众快照，投递资格不重新依赖取消后已失效的报名/候补状态；公共通知 API 明确拒绝伪造这两个前缀，避免普通操作者绕过正常受众复核。
- 外部通知在事务提交后或现有重试任务中投递；响应分别返回退款任务和通知任务状态。`REFUND_REQUESTED` 只显示“退款任务已受理”，不是已退款；取消成功还必须调用 occurrence status 独立回读，证明 occurrence 已取消、activity 已取消且已下架。
- 相同 `requestId` 精确重放只读已有 durable 回执；已取消场次换新 `requestId` 不能再次调用外部退款或重复建通知，状态仍可通过独立查询恢复。
- **人工退款责任单已落源码候选**：已核销父单按 `parent_order_no` 锁定全量行，严格校验活动、主体、会员、支付、报名与核销事实，并要求恰好一个正金额付款人；任一矛盾以 409 失败且不建 case、不退款、不回补库存、不取消活动。责任单恰好一次创建，后台通过专用受控上传获得不可缺失的 OSS `versionId`，后续预览、SHA-256 回读和复核只读取该指定版本；再以登记人与复核人分离、版本 CAS、退回重做和重开评估完成处理。bucket 未开启版本化或上传无 `versionId` 时以 503 失败关闭；“凭证已复核”始终不表述成渠道到账。

#### 验收

- 并发取消只释放一个名额，不会把两个候补同时升为同一席位。
- 修改系列未来规则不改已结算历史场次。

### C4. 会员与会费（P1，兴趣社群可通过 feature flag 暂缓）

#### 最小可用模型

- `club_membership_term`：memberId、planId、开始/到期、状态、宽限期、sourceOrderId；不用 `subscription` 作为表名。
- `club_membership_invoice`：termId、会费订单、应付/实付、支付、退款与对账关联。

- term 状态冻结为 `PENDING / ACTIVE / GRACE / PAST_DUE / EXPIRED / CANCELLED / REFUNDED`；权益只认当前有效 term，不认“历史上付过钱”。

#### UI

- 设置→会员与会费：是否启用、方案、周期、金额、权益、续费和退出政策。
- 俱乐部详情概览：调用 `/api/club/membership/overview` 读取真实 FREE/PAID、生效状态和 term 截止时间，并显示 loading/error/retry/ready。点击后进入现有会员状态/续费页。

#### 安全边界

- 会费不是活动票；两者订单、退款政策、收入确认和结算口径分开。
- 自动续费必须有单独授权、扣款前提醒、取消方式和失败处理；首版可先做手动续费。
- 俱乐部解散、退出、封禁时按冻结的政策快照处理，不按后来修改的新政策倒算。
- 新续费先在独立短事务提交稳定 `PAYING` 意图，再调用微信并在第二事务附着支付参数；`resume/close/callback` 都按稳定 `outTradeNo` query-first，不把微信受理当本地已支付。
- 退出、移除、封禁或解散按 `club → active member → PAYING invoice` 锁序写入 `resume_blocked_at` 并清空支付参数；附着 prepay 的 SQL 同时要求围栏为空。围栏一旦建立，迟到的 prepay/支付回调只能进入取消权益与人工处理路径，不能恢复会籍。
- 迟到支付在锁后再次确认成员关系与 invoice，只记录资金事实并生成 `CANCELLED` term；恢复接口读到 `resume_blocked_at` 必须 fail-closed。该列依赖新增 `migration_club_role_membership_resume_fence_20260826.sql`，落库前会费发布保持 No-Go。

## 8. API 与数据契约原则

### 8.1 通用响应

- 继续使用现有 `AjaxResult` / 分页结构，不创建新包装。
- 写操作必须接受或生成幂等键，并返回业务对象最新状态与 `updatedAt/version`。
- 前端收到成功回执后重新读详情；“提交成功”与“退款成功/邀请生效/通知送达”分开表达。

### 8.2 Owner 与 scope

- 商家和俱乐部写操作的主体 ID 都从登录态和服务端关系解析。
- 请求中的 `merchantId`、`clubId`、`sessionId` 只能用于定位，不能作为授权依据。
- 列表查询同样要做 scope 约束；只保护写接口仍会形成 IDOR。
- 高风险写入口不能只在加锁前鉴权：商家以 merchant→current Owner/member→子行，俱乐部以 club→assignment/业务子行的固定锁序，在拿到权威主体锁后重新解析当前权限。create/update/cancel、ban/unban、notification send/retry 均按此规则关闭撤权 TOCTOU。

### 8.3 状态与审计

- 未知/空值不当成 0 或成功；客户端遇到未知状态显示“状态更新中”。
- 角色、封禁、转让、会费政策、售后意见和导出必须有操作者与时间。
- 分析日志可按保留策略清理；资金、权限与治理审计不能依赖会被聚合/清理的分析事件。
- 写后回读必须来自数据库/外部系统的权威状态，且校验 id、scope、version/count/status；空行、更新计数不为 1 或字段矛盾均 fail-closed，禁止用刚写入的请求值合成成功对象。

#### 逐文件执行与恢复规则

1. 每个 migration 用独立进程/连接执行；结束后必须关闭原连接，再用一个新的只读连接执行该文件的完整终态断言。同一连接上的 exit 0、DDL 回执或末尾 `SELECT 1` 不算跨连接观测。
2. 只有精确结构、约束表达式、索引列序、FK/trigger 集合与必要业务数据断言全部为 `TRUE` 才能记 `COMPLETE`；`NULL`、查询失败、连接中断或无法证明的值一律记 `UNKNOWN`。
3. MySQL DDL 可隐式提交。任一文件中途失败后，禁止盲目重跑整份 SQL；先用新连接按语句核对现状。`COMPLETE` 不重跑，`ABSENT` 仅在重新通过前置后单独授权执行，`PARTIAL/DRIFT` 必须先写针对当前镜像的修复计划，`UNKNOWN` 立即停止。
4. 俱乐部 repair 若在两条 `ALTER TABLE` 之间失败，必须分别回读 `club_post` 与 `club_governance_case` 的约束 hash；不能因第一个已成功就把整份文件写成失败，也不能因第二个未执行就盲跑整份。先冻结为 `PARTIAL`，再授权精确续作。
5. 商家 repair 中任一列改名、回填、索引或约束语句部分成功时，同样按目标表逐项新连接回读；主体映射无法证明时记 `UNKNOWN`，不得自行猜测 `merchant_id`。
