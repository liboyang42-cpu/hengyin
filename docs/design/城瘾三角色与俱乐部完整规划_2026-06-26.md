## 1. 四角色定义(先都分开)

城瘾是一个**三边市场 + 一个组织实体**:

| 概念 | 类型 | 定位 | 能建俱乐部? | 底层 RBAC |
|---|---|---|---|---|
| **玩家** player | 身份 | 消费者:玩、报名、加入俱乐部 | ❌ | `role=player` |
| **商家** merchant | 身份 | 门店/品牌供给:发券、核销、报名主题招募 | ❌ | `role=merchant` |
| **达人** talent | 身份 | 内容创作者/主理人:创建并运营俱乐部、发起成团活动 | ✅(唯一) | 见下 |
| **俱乐部** club | **实体** | 达人创建的长期社群组织(`club` 表) | — | 不是身份 |

### 1.1 达人与现有 RBAC 的映射(关键,避免大迁移)

现有 `ums_member.role` 已有 `player / merchant / club` 三值。**"达人"就是现在的 `role='club'` ——即"已通过申请、拥有俱乐部的主理人身份"。**

- 对外文案统一改称 **"达人"**(talent),底层 role 值**暂保留 `club`** 不动,避免 DB 迁移与权限种子重写。
- `club/apply` = "创建俱乐部 / 成为达人"的入口;**填完即有(D14)**:提交即 `status=1` + role→club 生效,不走人工审核(仅 L1–L5 定级人工,D15)。
- **俱乐部(Club 实体)**= 达人创建的组织。**一个达人可建多个俱乐部**(D3),玩家可加入多个。

> 待你确认:若坚持要 DB 层把 role 值从 `club` 改名为 `talent`,需一次迁移 + 权限种子 + 前端 policy 同步更新;**建议先不做**,只做 UI 文案层"达人"。本文按"达人=role='club'"推进。

### 1.2 权限能力差异(已核对 `migration_m1_permission_full.sql`)

| 角色 | 主题额度 | 单主题节点 | 优惠券 | 核销 | 节点能力 | 数据范围 | 提现 |
|---|---:|---:|---:|---|---|---|---|
| 玩家 player | 1 | 2 | 0 | 否 | checkin | self | 否 |
| 商家 merchant | 3 | 不限 | 3 | 是 | checkin,scan | store | 是 |
| 达人(club) | 5 | 不限 | 3 | 否 | checkin,scan,quiz,puzzle,collect,occupy,minigame | theme+city | 是 |

> 注:达人持有 `can_branch / can_game_mechanic / can_design_medal` 等强游戏化权限,但目前规划的俱乐部功能(主页/活动/动态)尚未用到。见 §11 待办:要么把这些权限落到玩法编辑器,要么明确暂时空置。

### 3.5 协作与邀请体系:达人×商家×商家(★城瘾独有,Strava 没有)

这是城瘾区别于 Strava 的核心商业闭环:**达人出"人流",商家出"场地/优惠",多商家共建一条城市定向路线,双向对接。**

```
商家(不能建俱乐部,是承接方)            达人(带俱乐部成员去消费)
  维护「承接档案」                          浏览商家列表(club home 下方,9635 样式)
   · 店铺规模/容纳人数                        ↓ 发起合作申请
   · 可承接时段                          ┌─────────────────┐
   · 适合/想承接的活动类型      ←申请/邀请→ │  结构化合作(有状态) │
   · 免费 / 收费                         │ 待确认→已接受/拒绝  │
   · 诉求(想要什么)                     └─────────────────┘
  浏览俱乐部/达人(新页面,见 §6.2)          ↓ 接受后
   ↓ 主动发邀请                            达人带俱乐部成员去 → 发城市定向活动落到该商家
```

要点:
- **商家维护"承接档案"**(新数据,见 §7.6):店铺规模/容纳人数、可承接时段、适合活动类型、免费or收费、诉求、联系。
- **双向 + 结构化(D11)**:发「申请/邀请」,带状态(待确认/已接受/已拒绝);**不是裸聊**,可追溯。接受后再转 IM 细聊。
- **入口**:达人侧 = club home 下方"商家列表"(9635 卡片);商家侧 = 新增"商家看俱乐部/达人"页(§6.2,**当前最大缺口**)。

### 3.5.1 多商家共建一条路线(商家发主题 → 邀商家做节点 → 邀俱乐部来)

商家发布城市定向主题后,可邀请其他方加入,**一条主题 = 多方协作路线**:

| 角色 | 谁 | 权限 |
|---|---|---|
| **主办方 host** | 发布主题的商家(或达人) | 编辑路线 + **节点顺序**(复用专业版编辑器/地图Hero)、邀商家做节点、邀俱乐部来 |
| **节点商家** | 被邀请并同意的其他商家 | **只能配置自己节点的游戏**(复用 `merchantapply`),不能改路线顺序 |
| **受邀俱乐部** | 被邀请的俱乐部 | 达人带成员来参加 |

三种邀请(都走"邀请→同意"握手,**新增邀请层**):
1. 商家 → 俱乐部(邀来店里参加)
2. 商家 → 其他商家(邀做节点;同意即写入路线一个节点)
3. 达人 ↔ 商家(§3.5)

**复用现有(已核对):**
- 商家做节点 = `CmsRegistrationMerchant`(已有 `topicId` + `nodeId` + `auditStatus`)
- 节点商家配置自己的游戏 = 现有 `merchantapply1/2/3` 流程
- 主办方编辑节点顺序 = 现有专业版编辑器(地图 Hero 分章节/节点)
- **新增的只有"邀请握手"那一层**(见 §7.6 邀请表)

### 3.6 审核分流(★保留 web 审核,但只给官方)

| 内容来源 | 审核方式 |
|---|---|
| **官方活动发布** | 保留现有 **web 端人工审核**(`CmsTopic.status` 0待审/1通过/2失败,RuoYi 后台)——只有平台自营活动走这条线 |
| **俱乐部创建** | **无审核,填完即有(D14)**:`apply` 直接 status=1 + role→club;后台仅异步 L1–L5 定级(D15,不阻塞) |

## 4. 资金与合规(参考旅游团 app)

### 4.1 资金流(担保交易,复用 registration)

```
玩家报名付款 → 钱进平台(微信商户号托管) → 活动核销完成 → T+N 结算给达人(扣平台佣金)
未成团 / 取消 → 按规则退款(registration.paymentStatus=4 + pointsReturned)
```

- **担保托管**:钱先到平台,核销后再结算给达人,防主理人跑路(对标携程担保交易)。
- **成团保障**:未达 `min_people` → 自动全额退。
- **阶梯退款**:退款规则配置在主题/票种层(参考携程:出发前7天全退 / 3–7天部分 / 24h内不退)。
- **平台佣金**:结算时按 `commission_rate` 抽佣。
- **支付方式**:复用 `paymentType`(纯积分/纯微信/积分+微信),零新增。

### 4.2 合规红线(城瘾要规避资质风险)

- **平台定位为"兴趣社群活动撮合"**,非旅行社业务;达人是组织方,平台仅撮合 + 资金托管。
- **付费话术**走"活动成本分摊 / AA 制",避免被认定为"营业性组团旅游"(无《旅行社业务经营许可证》风险)。
- **达人协议**:明确组织责任、安全责任在达人;平台尽撮合与资金保障义务。
- **线下安全**:活动页强制免责声明;建议达人为活动购意外险;实名报名(registration 已有 realName/phone)。
- **未成年人**:报名年龄限制/监护人确认。
- **内容审核**:`club_post` 动态先发后审 + 举报下架;俱乐部申请已有人工审核。
- **退款纠纷**:资金托管期内平台可介入仲裁。

> ⚠️ 合规为产品/法务联合决策项,本文给方向,落地前需法务确认定位话术与协议。
