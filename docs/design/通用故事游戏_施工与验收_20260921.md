# 手机端通用故事游戏：施工与验收

更新：2026-09-21。状态：实施中，未合并、未部署、未上传；没有真机验收结论。

## 目标与已确认规则

作者用手机，通过 fabu、temp、pages/play 完成通用故事游戏的配置与游玩。《预制人生》是验收内容，不是专用引擎。呈现方式沿用模板 present=inline/fullscreen。主题管理精力/幸运初始值、开局、章节、条件、绑定及结局；模板管理单次交互和结果。手机不要求填写 JSON 或变量代码。

D20：1d20＋模板加值≥作者 DC，优势/劣势，自然 1/20 不自动成败。主题只接精力/幸运效果，不增加通用属性编辑。白色允许一次幸运重掷，红色一次；后续重试不改写已结算历史。文字和录音互动均纳入本轮。四站八章，以完整剧本文档为主，HTML 为首站交互参考。

## 系统设计

复用主题 V2、JourneyRules、ThemeStateKey、TopicRouteSession/Action、现有路线条件与效果引擎、AdvancedGameRuntime、AuditTask。配置随审核及开局冻结；服务端管理状态、幂等、权限、防剧透，客户端管理呈现。先打通基础链，再拓展全剧，不建立第二套主题编辑器或专用主题路由。

用户最新裁决：手机初始状态只提供可选的精力、幸运，不再展示人格、关系、不稳定度及通用数值属性。沿用 journeyRules 中的 hp/luck，精力/幸运保持 sys.hp/sys.luck 唯一状态。旧数据里的扩展属性仅保留兼容，不在本期作者界面继续增加。精力扣除、幸运重掷必须接入具体玩法的权威结算，不能只配数值就宣称游戏已经消费。

## 验收标准

1. 手机新建、配置、保存、重开恢复、预览、提交审核，不改代码。
2. 建档及 D20 两种呈现返回正确故事位置，退出重进不重置进度。
3. 重复请求/并发/断网不重复扣精力/幸运或发奖，旧局版本不漂移。
4. 未解锁文本、隐藏状态、其他人的私有资料不泄漏。
5. 完整跑通四站八章及六结局；录音等失败有真实恢复路径，不造成功。

## 2026-09-22 思维阁与氛围:落到哪一层(用户已拍板)

背景见桌面《预制人生原型_配置能力覆盖核对_20260922》。这两项是原型贯穿全篇的机制,现有三层都接不住,先定层再施工。

### 共同结论:都不进 playkit

playkit 的职责是「单次交互和结果」(本文档开头的口径)。这两项都不是一次交互:氛围是持续的表现基调,思维阁是跨章节的累积状态。

### 氛围 → V2 章节块层,新增 `mood` 标记块

定层依据是原型的真实形状,不是直觉:氛围标在正文节点上(`n.dataset.cos`),滚动时 `if (pick !== COS.target) cosmos(pick)` —— **跟着正文流走,章内会切多次**(如 `cosmos('hush', true)` 老师提问时静止 → `cosmos('chalk', false)` 答完转粉笔灰)。块层是唯一能表达「正文流的这个位置」的层。

- **不进 journeyRules**:氛围不是状态、不参与任何权威结算。进了状态引擎,每个字段都要背 CAS / 幂等 / 回滚,而它一样都不需要。
- **标记块,不给每个块加字段**:接口小得多(只在切换处出现,而不是每段都问一次「氛围?」),复用现有块的稳定 key、排序、复制重映射,与「在正文里插地点 / 插玩法」的作者心智一致。
- `chapterGate(..., cos, ...)` 的进章初值 = 本章第一个 `mood` 块,不再另开章节属性。
- 块形状:`{ type: "mood", id, key, mood: "<预设名>" }`。不带 content / url / nodeIndex(与 `dream` 块同样在编译器里 fail-closed)。不是 node 块,不参与 `projectForPlayer` 截断。

**作者接口粒度(用户拍板):平台预设,作者只选名字。** 原型那 16 个连续 canvas 参数(bg / 粒子色 / 速度 / 光源 / 光束 / 网格 / 散景)不暴露给作者。服务端只校验预设名在枚举内,渲染全在客户端。
> 代价已知并接受:别的主题只能用平台这几种调子。字段设计成以后能扩成参数对象而不破存量配置。

### 思维阁 → 拆两层

| 部分 | 落到哪 | 为什么 |
|---|---|---|
| 念头的定义与效果(`name`/`desc`/`need`/`effect`) | `journeyRules`,与 hp/luck 同层 | 主题级、跨章节、参与权威结算 |
| 「在这里获得一个念头」 | 块层,`{ type:"thought", key, thoughtKey }` | 原型 `gainThought()` 就发生在剧情中间,与 `mood` 同样是正文流里的位置标记 |
| 进度与完成状态 | `TopicRouteEngine.State` 现有容器 | `variables: Map<String,Number>` 存 prog、`tags: Set<String>` 存 done,与 `sys.hp`/`sys.luck`/`sys.opening.done` 完全同构 |

**不需要新状态容器** —— 这是选这个分法的主要理由。

**`journeyRules` 必须扩的一处**:现在 `luck.max` 是静态配置,而念头的 effect 是「幸运上限 +1」。上限要能被运行时效果改写(variables 里放覆盖值,读取时优先于静态配置)。这是绕不开的扩展点,也是本设计对现有状态引擎的唯一侵入。

### 累积源:真实步数(用户拍板)+ 一个硬约束

用户选「真实步数,贴原型」。但核实通路后发现原型的形状搬不过来:

- 步数只能来自 `wx.getWeRunData`,是**微信运动的今日累计步数加密数据**,客户端拿不到明文、解密在服务端,且授权弹窗必须挂在用户手势上(`playkit-walk/index.js:5-7`:步数只能同步不能填,能填这玩法当场作废)。
- 所以 `think(m)` 那种「每走 m 米实时累加」做不到。**能做到的是:开局记步数基线,每次同步取差值,念头进度跳一档。**

**推荐的同步时机:挂在「到站 / 完成节点」上**,不给思维阁单开刷新按钮。玩家到站本来就要操作,顺带同步,念头在到站时前进一截——「走到下一站,想通了一点」在城市定向里比「边走边想」更成立,且复用现有节点完成通路,不新增入口。**此条待用户否决;改它只改入口,不改上面的分层。**
