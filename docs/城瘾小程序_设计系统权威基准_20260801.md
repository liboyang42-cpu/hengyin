# 城瘾小程序 · 设计系统权威基准

> 版本：2026-08-01
>
> 用途：为城瘾微信小程序的上线前 UI/UX 终审、设计重构和前端验收提供一份可执行的外部权威基准。它不是对现有页面的通过结论，也不替代逐路由、真机、真实数据与无障碍测试。
>
> 适用对象：玩家版、商家版、发布/创作工具三类界面；同一产品中的三种体验必须共用同一套基础 token 与交互语言。
> 质量定位：以 Apple HIG 的平台完成度、Material 3 的语义系统、Fluent 2 的 token 与可访问性、Polaris 的商家任务流为参照，建立城瘾自己的设计系统；不复制任何一家产品的外观，也不构成 Apple Design Award、上架或无障碍合规的保证。

## 1. 阅读规则：先分清“来源”与“城瘾决策”

- **[源]**：下文标注的外部一手资料已经明确表达的原则、约束或最低标准。
- **[城]**：结合城瘾“城市探索/玩家社区 + 商家经营 + 创作发布”而提出的内部设计决策；它需要由设计负责人定稿，随后进入 Figma token、组件库与代码。
- **[验]**：上线前可以客观检查的标准。未能验证，就不能宣称“设计系统已落地”。

外部系统的度量单位不能原封不动迁移：Apple 使用 pt，Material 使用 dp，Fluent 使用 px/pt，微信小程序使用 rpx。本文所有“pt”是**以 375 宽视觉稿为参照的设计单位**；在 750rpx 画布中，1pt 约等于 2rpx。真正实现仍须在 iPhone、Android、不同刘海/圆角屏和字体缩放条件下回读。

## 2. 权威来源如何分工

| 来源 | 它回答什么 | 对城瘾的使用方式 | 不应照搬什么 |
| --- | --- | --- | --- |
| Apple HIG | 移动端的上下文、适配、可读性、触控与完成度 | 把“熟悉、清晰、克制、可适配”作为所有页面的高标准 | 不把 iOS 控件皮肤、SF 字体或系统栏样式伪装成微信原生界面 |
| Material 3 | 色彩角色、排版角色、形状、组件状态与紧凑设备导航 | 用“角色而非裸色值”管理主题、状态和组件变体 | 不把 Material 的紫色、动态配色或 Android 控件轮廓当作城瘾品牌 |
| Fluent 2 | Primitive → Semantic token、4pt 空间节奏、跨主题与无障碍规范 | 建设计-开发共同语言，防止页面自行写颜色、圆角和阴影 | 不搬桌面 Drawer、Hover、Segoe 字体、React/ARIA API |
| Shopify Polaris | 商家任务、卡片、表单、空状态、错误与工作流可读性 | 商家版优先采用“清晰任务、单一主行动、可恢复”的经营工具规范 | 不把桌面后台的密度、双栏或复杂卡片直接压缩进手机 |
| WCAG 2.2 | 可测量的对比度、目标尺寸、重排与减动效底线 | 作为小程序内部高标准和验收阈值，不把“视觉好看”当可访问 | 不因小程序不是网页就忽略文本、图标、焦点、标签和动效风险 |

## 3. 城瘾设计系统的总结构

### 3.1 [城] 三个体验模式，不是三套散装视觉

| 模式 | 用户此刻的核心问题 | 体验气质 | 页面优先级 | 禁止事项 |
| --- | --- | --- | --- | --- |
| 玩家 Explore | “附近/现在有什么值得去、参加或收藏？” | 有温度、有城市感，但信息先于装饰 | 内容、地点/活动、行动、信任信息 | 用深色氛围掩盖低对比文字；营销图压过地点与时间；空页不给下一步 |
| 商家 Operate | “我现在的经营状态是什么，下一步做什么？” | 克制、稳定、效率优先 | 任务、数据、状态、下一步 | 每个数据块都套卡；一页多个主按钮；把错误伪装成灰色数据 |
| 创作 Create | “我正在完成哪一步，怎样安全地提交？” | 专注、低干扰、连续进度 | 当前步骤、输入、预览、提交安全 | 普通页面再套全屏 Sheet；地图/预览/底栏彼此遮挡；无保存或返回语义 |

三种模式可有不同品牌表达，但必须共用：颜色语义、排版角色、间距阶梯、圆角阶梯、按钮优先级、状态文本、图标语言、安全区规则、反馈规则。任何页面在根节点只能声明一个模式；不能让同一屏的导航、正文、底栏分别继承深/浅主题。

### 3.2 [源] Token 是跨设计与开发的一致性基础

Fluent 2 将原始数值与语义 alias 分成两层；原始层可承载颜色、排版、圆角、描边、动效等，语义层说明何时使用，并支持 light、dark、高对比和品牌主题。[F1](https://fluent2.microsoft.design/design-tokens)

**[城] 城瘾的强制三层：**

1. **Primitive（原始值）**：色阶、透明度、空间、字号、行高、圆角、描边、阴影、时长；只有 token 文件可定义裸数值。
2. **Semantic（语义）**：例如 background-canvas、surface-raised、text-primary、text-secondary、action-primary、status-warning、border-subtle；页面不得直接读取紫色、灰色或阴影数值。
3. **Component（组件）**：例如 nav-background、card-background、field-border、tab-selected-label、sheet-scrim。组件只读取 Semantic，不回读 Primitive。

**[验]**

- 设计稿、WXSS、组件文档的 token 名称与含义一一对应。
- 任一浅色/深色/商家主题切换后，所有 alias 均有值；不得出现旧 token 漏覆写导致局部黑底、黑字、透明图标或错色。
- 页面 CSS 不新增无说明的十六进制颜色、固定阴影、任意圆角或 z-index。
- 主题问题由一张“模式 × 页面壳 × 导航 × 正文 × 底栏 × Sheet/Modal”矩阵验收，而不是只截一张首页。

## 4. 基础规范

### 4.1 主题、色彩与语义

| 规则 | 来源事实 | 城瘾落地决策 | 验收 |
| --- | --- | --- | --- |
| 使用色彩角色，不用“某个好看的紫/灰” | Material 3 的主题由颜色、排版、形状组成；组件依据颜色角色获得一致且可访问的组合。[M1](https://developer.android.com/develop/ui/compose/designsystems/material3) | 把品牌紫限制为主行动、选中态或少量品牌锚点；不要把它同时当背景、标题、描边、icon、标签和错误提示。 | 搜索页面代码与 Figma 变量：组件应读语义角色而不是裸色值。 |
| 语义色只表达语义 | Fluent 明确将 success/warning/danger/info 视为重要信息，不应当装饰使用，且不能只靠颜色传意。[F2](https://fluent2.microsoft.design/color) | 成功、提醒、危险、信息四类状态必须有“图标 + 文本 + 色彩”至少两种线索；普通营销高亮不得借用 warning/danger。 | 灰度图、色弱模拟和无图标场景仍能区分状态；每个状态 tag 都能读出业务含义。 |
| 深浅主题是同一角色的不同实现 | Fluent token 支持 light、dark、高对比与品牌主题。[F1](https://fluent2.microsoft.design/design-tokens) | 不定义“深色页面专用的随意文字颜色”；同一 text-primary、surface、border、action 在每个主题均有成套配对。 | 主题切换后测 text、icon、tab、input、disabled、sheet、mask、图片蒙层，不允许仅页面背景变色。 |
| 正文对比度有下限 | WCAG AA：普通文本至少 4.5:1，大号文本至少 3:1。[W1](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) | 城瘾把 4.5:1 设为正文、说明、表单标签、可点击文本的下限；3:1 仅允许达到“大字号”定义的标题/数据；交互图标和边界同样按至少 3:1 内部标准审查。 | 用取样工具在最终渲染背景（含图片、遮罩、透明层）上实测，不按设计稿单色背景猜测。 |
| 颜色不替代层级 | Polaris 建议用尺寸、字重、对比度建立层级，非表格内容少用分割线堆层级。[P1](https://polaris-react.shopify.com/design/layout) | 玩家页用空间、字号、图片与少量 surface 表达节奏；商家页用数字、标题、状态和留白表达优先级。不得靠彩色边框、渐变、阴影、分割线同时叠加。 | 关闭品牌色后仍可读出页面一级、二级、操作与状态。 |

**[城] 推荐语义角色清单（名称可调整，职责不可删除）：**

| 类别 | 必需角色 |
| --- | --- |
| Canvas / Surface | background-canvas、background-subtle、surface-base、surface-raised、surface-sunken、surface-overlay、scrim |
| Text / Icon | text-primary、text-secondary、text-tertiary、text-inverse、text-link、icon-primary、icon-secondary、icon-disabled |
| Action | action-primary、on-action-primary、action-secondary、action-ghost、action-destructive、action-disabled |
| Status | status-success、status-warning、status-danger、status-info 及其 on/status-surface 配对 |
| Border / Focus | border-subtle、border-strong、border-critical、focus-ring |
| Media | media-placeholder、media-scrim、media-skeleton-base、media-skeleton-shine |

### 4.2 空间、对齐与页面壳

Fluent 的基础空间阶梯以 4 为基数，强调空间用于建立亲疏、层级和可扫描性，而不是无目的填白。[F3](https://fluent2.microsoft.design/layout) Apple 要求布局尊重安全区、边距与设备上下文。[A2](https://developer.apple.com/design/human-interface-guidelines/layout)

**[城] 空间阶梯：**

| 视觉单位（375pt 稿） | 小程序参考值 | 典型用途 |
| ---: | ---: | --- |
| 2 | 4rpx | 图标与极紧邻元素的光学校正；非普通正文间距 |
| 4 | 8rpx | 小图标、徽标内部缝隙 |
| 8 | 16rpx | 标签内部、标题与副标题、字段 label 与输入框 |
| 12 | 24rpx | 紧密列表项、卡片内相邻信息组 |
| 16 | 32rpx | **标准页左右内容边距**、卡片内边距、普通表单项组、列表行主间距 |
| 20 | 40rpx | 仅用于经组件规范确认的光学校正或局部大间距；不是新页面默认横向边距 |
| 24 | 48rpx | 分区间距、长页面段落间距 |
| 32 | 64rpx | 页面大区块、空状态与主内容的关系 |
| 40 / 48 | 80 / 96rpx | 首屏英雄或重要状态页的呼吸空间，不能当常规空白 |

**[城] 版式合同：**

- 一张普通页面只允许一个主内容栅格：标准页左右边距以 **16pt / 32rpx** 为基线，并与现有 `--cy-page-x` 对齐；Hero 可以满宽，但内部文本仍回到该基线。不得把 20pt / 40rpx 作为页面作者随手取的第二套横向边距。
- 标题、搜索、筛选、第一张卡、空状态、列表、底部按钮必须对齐到同一左/右内容线；图片裁切、吸顶栏、Sheet 内容也须继承这条线。
- 视觉对齐优先于框模型对齐：图标视觉中心、圆角图片与文字基线可做 1–2pt 光学校正，但必须是组件级规则，不能每页写 magic number。
- 任何遮罩、绝对定位容器、负边距、safe-area padding 均需单独审查。页面出现“左边距差一层”“图片/文字整体偏移”时，先查祖先容器、mask、scroll 容器和 box-sizing，而不是只改子元素 margin。
- 普通内容最多两层可见 surface：canvas → card，或 canvas → sheet。第三层只有在它明确是一个独立子任务、可操作的 inset 容器时才允许；不得形成“卡片里再套一张几乎同样的卡片”的视觉噪声。

**[验]**

- 在最终截图叠加内容导线：同类页面关键左/右边应无非设计性漂移；任何 4pt 以上偏移必须有组件规范依据。
- 检查带 tab、键盘、sticky footer、全屏 Sheet、胶囊导航、浮动按钮的页面，内容不会被遮挡或重复预留安全区。
- 低端/小屏、长中文地名、系统大字体时，不产生横向滚动、裁切和双向滚动；WCAG 以 320 CSS px 可读重排作为通用底线。[W3](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

### 4.3 排版与内容

Apple 强调字重、字号、行距共同建立层级，避免轻字重，且在大字号下保持层级并减少截断。[A3](https://developer.apple.com/design/human-interface-guidelines/typography) Fluent 使用语义 type ramp 和原生平台字体来保持跨端熟悉与可读性。[F4](https://fluent2.microsoft.design/typography)

**[城] 中文 Type Ramp（视觉规格，不是要求复制任何外部字体）：**

| Token | 字号 / 行高 | 字重 | 用途 | 禁止用法 |
| --- | --- | --- | --- | --- |
| display | 28 / 36（约 56 / 72rpx） | 700 | 极少数首屏城市名、关键任务成就 | 普通页标题、卡片标题 |
| page-title | 29 / 36（约 58 / 72rpx） | 600–700 | 一级页面标题 | 与导航标题、sheet 标题同时并列重复 |
| section-title | 18 / 24（约 36 / 48rpx） | 600 | 分区标题、商家核心模块 | 每一行列表都写成此级 |
| card-title | 16 / 22（约 32 / 44rpx） | 600 | 内容卡/资源卡主标题 | 叠加彩色、下划线、emoji 来抢层级 |
| body | 14 / 22（约 28 / 45rpx） | 400 | 正文、地点、主要说明 | 紧贴复杂背景图 |
| body-compact | 12 / 19（约 24 / 38rpx） | 400 | 商家列表、表单说明、次要正文 | 长篇说明、法律正文 |
| meta | 11 / 17（约 22 / 34rpx） | 400–500 | 时间、距离、辅助状态、tag | 关键操作、字段名称 |
| label | 12 / 16（约 24 / 32rpx） | 500–600 | tab、按钮、表单标签、小状态 | 多行长文、隐性说明 |

**[城] 排版细则：**

- 中文正文默认字距为 0；不以任意字间距“做高级感”。仅在大标题经过视觉测试后允许极小负 tracking。
- 3 行以上文本使用 1.45–1.6 倍左右的舒适行高；不能为了塞入卡片将正文压成紧行距。
- 左对齐为默认；居中只用于短成就、单一空状态、短步骤标题。商家指标可以数值右对齐，但标签与解释保持左对齐。
- 同一屏最多有一个 page-title，一个清晰的 section-title；页面名、导航标题、卡片标题不能同义重复。
- UI 文案以动词 + 对象命名主要行动，例如“创建活动”“查看订单”；避免“去看看”“立即体验”这类无对象 CTA。Polaris 亦要求空状态的主行动清晰、可预期且以动词引导。[P4](https://polaris-react.shopify.com/components/layout-and-structure/empty-state)

**[验]**

- 字号不可只看 wxss 数值，必须在 iOS 与 Android 的实际字体渲染中检查笔画、截断和基线。
- 所有普通文本与背景的对比度达标；弱化文字也不是“看不清即可”。
- 真实长名称、极长商家名、超长金额、无数据占位符、英文/数字混排、时间单位都具有规则，不出现“¥—”“---”“10min”式内部占位或无格式混用。

### 4.4 形状、边界与层级

Material 3 使用形状和 tonal elevation 区分 surface，而不是仅靠大阴影。[M1](https://developer.android.com/develop/ui/compose/designsystems/material3) Polaris 的卡片默认是有目的地分组信息，而非把所有内容变成漂浮模块。[P3](https://polaris-react.shopify.com/components/layout-and-structure/card?example=card-with-section)

**[城] 形状阶梯：**

| Token | 建议半径 | 适用 |
| --- | ---: | --- |
| radius-xs | 8pt / 16rpx | 输入框、轻量内嵌状态、图片小裁切 |
| radius-sm | 12pt / 24rpx | 列表卡、商家数据卡、Sheet 内分区 |
| radius-md | 16pt / 32rpx | 玩家发现卡、媒体卡、主要 surface |
| radius-lg | 20–24pt / 40–48rpx | 少量全屏 Sheet 或品牌主视觉容器 |
| radius-pill | 999 | 仅 tags、segmented tab、紧凑胶囊操作，不用于大卡片 |

- **边界优先级**：先用背景差异，其次用细描边，再次用极轻阴影；三者不应在同一个普通卡片同时显著。
- **阴影上限**：普通 card 使用 0 或一档轻阴影；浮层/Sheet 才能使用更高层级。card、内卡、按钮、图片都投影，会让页面像叠加的模板而非产品。
- **描边上限**：一张卡只拥有一种可见轮廓；被选中时使用语义 selected/focus，不再额外叠双描边、外发光、彩色背景。
- **圆角一致性**：同一信息层级不得出现随机 8/10/12/14/16pt；组件注册表决定半径，而非页面作者。

### 4.5 [城] 图标尺寸：glyph 与圆框配对

图标尺寸不建立脱离上下文的 `24/32/40/48` 绝对档位。`cy-icon.size` 只表示 **glyph 盒**；圆形操作必须从语义选定一整组 **hit target → visible circle → glyph**，glyph 由圆框配对关系决定，不能拿一个独立 size 到处套。

**三层必须分开：**

- **hit target（点击热区）**：真正响应点击的盒子，可以透明；icon-only 交互一律不小于 **88×88rpx**。相邻控件还需保留误触间距。
- **visible circle（可见圆框）**：用户看到的圆形底、描边或玻璃面；可以小于 hit target，且不得反过来撑大或缩小热区。
- **glyph（图标盒）**：`cy-icon.size` 对应的方形盒。常规配对中 glyph 占 visible circle 的 **40%–55%**；准确值由下表配对给出，不另建一串 glyph 档位。

**常规配对矩阵：**

| 登记 ID / Token 前缀 | 语义 | hit target | visible circle | glyph | glyph : circle | optical scale / offset |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| `compact-floating` / `--cy-comp-icon-pair-compact-*` | 地图或封面上需要较小可见面的浮动圆钮 | 88rpx | 64rpx | 32rpx | 50% | 按 icon 读取 `spec.json`，不得整组平移 |
| `standard-icon-button` / `--cy-comp-icon-pair-standard-*` | 普通 icon-only 圆形操作 | 88rpx | 88rpx | 40rpx | 45.5% | 按 icon 读取 `spec.json`，不得整组平移 |

`searchmap` 的 **64rpx visible circle + 88rpx hit target + 32rpx glyph** 是分层范式：视觉圆留在原页面边缘，透明 wrapper 扩大点击区。后续不能用“可见圆都改 88”冒充 IconButton 统一。

**用户已裁决、必须保留的 exception：**

| exception ID | 语义 / owner | hit target | visible circle / frame | glyph | 比例 | 保留理由 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| `play-primary-action` | Play 底栏开始/暂停主键 | 124rpx | 124rpx circle | 61rpx | 49.2% | Figma 主行动构图；已有精确契约 |
| `merchant-quick-action` | 商家首页四个快捷操作 | 120rpx | 120rpx circle | 44rpx | 36.7% | hero 快捷区构图；允许显式越过常规比例窗口 |
| `searchmap-back` | 搜索地图左上返回 | 88rpx | 64rpx circle | 32rpx | 50% | 已有热区与边缘锚点负控；同时是 compact 范式样本 |
| `roam-history-walk` | RunCard 无封面占位；点击由 `.rc` 卡片承接 | 无独立热区 | 无圆框；138rpx 方形 frame | 61rpx | frame 的 44.2% | RunCard 构图值；不能伪装成圆形 IconButton |

例外不是“门禁不管”。登记必须落在 `components/cy/icon/spec.json` 的 `exceptions` 中，写明 `decision: preserve`、语义、真实源码与契约来源、保留理由；常规比例外的例外还必须显式写 `allowRatioDeviation: true`。配对 token 与登记值必须一致，未登记的比例越界、任何小于 88rpx 的独立 hit target 都由 `tests/unit/cy-icon-pairing-contract.test.js` 判红。

**逐 icon 光学校正元数据：**

- 存放位置：`components/cy/icon/spec.json` 的 `optical.icons.<name>`；55 枚 `icons.wxss` glyph 必须一一对应，禁止漏项。
- 格式：`scale` + `offset: { x, y }` + `review`；offset 单位是 glyph 盒百分比，正 X 向右、正 Y 向下。`pending` 表示仍是中性值 `1 / 0 / 0`，不能据此声称已视觉校正；`bbox-audited` 只表示已有边界证据，也不等于最终视觉验收。
- 不重画 SVG，不把单个 icon 的 offset 下放到页面。未来生成器/组件消费这份元数据后，仍需按 A34/C01 等运行态样本验收。

```json
"play": {
  "scale": 1,
  "offset": { "x": 0, "y": 0 },
  "review": "bbox-audited",
  "evidence": {
    "bboxCenter": { "x": 2, "y": 0 },
    "areaCentroid": { "x": -0.444, "y": 0 },
    "unit": "viewBox"
  }
}
```

`play` 的 bbox 中心向右、面积重心却向左，方向相反；若按 bbox 对全库统一 translate，视觉重心会被推得更偏。因此只能逐 icon 记录并验收 scale/offset，不能一刀切。

本节只建立规格、token、例外与门禁。页面迁移和统一 IconButton 的可见实现属于后续批次；在页面尚未消费配对 token、逐 icon 元数据尚未完成运行态验收前，**不得声称全站图标视觉已改完**。

## 5. 导航、页壳、Sheet 与浮层

### 5.1 [源] 目标数和上下文必须清楚

Material 3 建议紧凑设备底部 NavigationBar 承载不超过五个稳定目的地。[M1](https://developer.android.com/develop/ui/compose/designsystems/material3) Fluent iOS 将 navigation bar 用于表达当前页/流程关系，而 segmented control 仅改变同一上下文内的视图，不承担跨页导航。[F7](https://fluent2.microsoft.design/components/ios/core/navigationbar/usage) [F8](https://fluent2.microsoft.design/components/ios/core/segmentedcontrol/usage)

**[城] 导航合同：**

| 场景 | 唯一允许的主要导航模型 | 必需内容 | 禁止 |
| --- | --- | --- | --- |
| 一级稳定目的地 | 全局 tab bar | 3–5 个互斥、稳定的一级入口；图标、短标签、唯一选中态 | 浮动发布按钮与 tab 内发布入口功能重复；无标签 icon；局部筛选当一级 tab |
| 普通二级页 | 顶部导航 + 页面内容 | 明确返回、短标题、必要的一项右侧操作 | 导航标题 + 页面标题 + Sheet 标题三次重复同名 |
| 同页视图切换 | segmented / 局部 tab | 最多 5 个短、互斥、同上下文视图 | 用它跳转不同任务、不同角色或不同层级页面 |
| 单一任务/编辑器 | 专用工具导航 | 关闭/返回、任务名、保存/提交状态，必要时步骤 | 普通页面壳下再嵌全屏 Sheet；地图、工具栏、底栏互相压住 |
| 选择或补充信息 | Sheet | 触发源仍可理解、清晰关闭、一个主行动 | 常驻 show=true 的 Sheet 伪装成普通页面；Sheet 内再开非必要 Sheet |
| 高风险确认 | Modal/Alert | 后果、取消、破坏性行动明确可辨 | 登录失败、空数据、可恢复异常也用打断型 Alert |

**[验]**

- 每张页面截图中能在 3 秒内回答：“我在哪一层、如何回去、这一屏的主要目标是什么”。
- 用遮罩/层级图检查：一个时刻不出现两个等权导航条、两个固定 footer 或互相竞争的浮动主按钮。
- Sheet/Modal 关闭后回到触发元素或等价上下文；商家表单错误需让用户抵达正确错误位置。Polaris 将“打开 overlay 时移入、表单错误时移到错误消息”的焦点管理作为商家工作流原则。[P5](https://polaris-react.shopify.com/foundations/accessibility)

### 5.2 [城] 安全区和固定底栏

- 顶部：导航内容不与状态栏、胶囊按钮、刘海区竞争；背景是否延伸由 page shell 定义，不能由每页手写 top padding。
- 底部：固定操作栏高度、tab bar 高度、safe-area-inset-bottom 三者只计算一次；滚动内容须留出真实可见的末尾安全空间。
- 键盘：输入聚焦时，提交 CTA 要么随键盘安全上移、要么明确隐藏并允许滚动抵达；不得半遮挡字段或让用户误触底部 tab。
- 浮动按钮：只在不与 tab、bottom action、地图控件、客服入口冲突时出现；同一功能不可既是 FAB 又是底部 tab/页头按钮。

### 5.3 [城] 原生渲染表面的合成合同

`canvas`、`camera`、`map`、video/live-player 等不是普通 DOM 背景。它们可能有独立渲染/命中层，因此“WXML 写了导航、WXSS 提高 z-index”不等于用户真的能看到或点击导航；这一点必须以目标微信版本、目标设备的最终截图和点击验证为准。

| 原生表面 | 不可缺失的前景信息 | 三态验收 | 禁止 |
| --- | --- | --- | --- |
| 地图/路线编辑 | 任务名、唯一退出、定位/加载状态、结果摘要或列表替代 | 定位可用、未授权/地图失败、列表替代 | 用地图遮住返回/CTA；地图是唯一可读信息渠道 |
| 相机/扫码 | 返回、明确快门/扫描动作、授权解释、拍后确认 | 授权可用、拒绝/不可用、拍摄/失败/保存 | 用静态相机外观或透明热区假装可发现操作 |
| Canvas/WebGL | 页面名、返回、对象名称/进度、可访问的对象列表或等价说明 | 正常 GPU 渲染、无 GPU fallback、数据失败/部分失败 | 仅 fallback 有标题/操作；仅靠 CSS z-index 假设 DOM 覆盖 canvas |
| 视频/直播 | 关闭、播放状态、静音/字幕、失败恢复 | 可播、网络失败、权限/音频受限 | 自动播放声音、把关闭/字幕压在不可点击层 |

**[验]**：每个原生表面都要保存三张同视口证据（正常、fallback、失败/权限）和一次退出/主操作回读。若某一态标题、退出或状态文字被合成层吞掉，属于 P1+ 的交付阻断，不能通过“源码里已经写了”来结案。

## 6. 卡片系统：先定义任务，再决定是否用卡

Polaris 定义 card 用于将相近概念和任务分组，强调清晰标题、单一用户流、每张卡至多一个主 CTA；CTA 位于 card footer，持久可选操作才放 header。[P2](https://polaris-react.shopify.com/patterns/card-layout) [P3](https://polaris-react.shopify.com/components/layout-and-structure/card?example=card-with-section)

### 6.1 [城] 卡片分类与统一规格

| 类型 | 解决的问题 | 图片 / 文字排版 | 行动与状态 | 不可做 |
| --- | --- | --- | --- | --- |
| A. 玩家发现卡 | 让玩家快速判断“去不去/点不点” | 两列发现流固定 4:5；单列列表固定 4:3；Hero 仅用 16:9/3:2；图片在上，标题 2 行内，时间/距离/主题为一行 meta | 整卡可点进入；收藏是独立 44pt 目标；售罄/即将开始贴近对象 | 每张卡堆 4 个 tag、两个主按钮、随机图片比例 |
| B. 横向资源卡 | 列表中扫描活动、商家、创作者 | 左媒体固定 84×84pt / 168×168rpx，右侧标题、1–2 行说明、底部 meta；所有媒体左线对齐 | 整行主跳转，局部操作不抢标题 | 让不同列表项图片宽高漂移；把无图当黑块/白洞 |
| C. 商家 KPI 卡 | 回答一个经营问题 | 数值为视觉主角，标签在上/左，趋势与解释紧邻数值；一张卡只表达一个指标或一组不可拆数据 | 异常值要有原因、时间范围和查看详情 | KPI 卡里再嵌多个边框卡；空值显示“—”而无解释 |
| D. 商家任务卡 | 告诉商家下一步 | 标题、状态、简短收益/阻碍、一个明确下一步；可选右上“编辑/更多” | Footer 放最多一个主 CTA；主 CTA 使用动词 + 对象 | Header 放“去完成”大按钮；同卡 3 个等权行动 |
| E. 表单 / 设置卡 | 组织一组相关输入 | card 标题 → 字段组 → 说明/错误 → footer；label 与控件距离小于字段与字段距离 | 仅在整卡提交时用 footer CTA；字段错误贴字段 | 每个字段独占一张卡；把必填说明藏在 placeholder |
| F. 状态/空/错误卡 | 解释缺失、失败或受限并恢复工作流 | 简短插图或状态图标 + 标题 + 1–2 句原因 + 一个主行动；内容保持垂直居中但不空泛 | Error 有重试/返回/替代路径；No permission 有原因与授权/返回 | 用空白、无限 spinner、模糊“系统错误”结束流程 |
| G. 叙事 / 引导卡 | 帮玩家理解品牌、成长、城市主题 | 有意的图文比例（推荐 16:9 或 3:2），短标题和一句解释；文案不压复杂照片 | 一个探索或继续动作 | 与 KPI、表单、交易数据混在同一组件外观 |
| H. InfoPanel / 例外嵌入容器 | 规则说明、轻提示，或 card 内唯一明确的可编辑子任务 | 规则说明优先用无卡/弱 surface；真子任务才用较小半径、较小 padding、无额外大阴影 | 只承载一个真实子范围 | 为了“好看”套第二、第三层框 |

### 6.2 [城] 卡片 anatomy、空间与行动

| 部位 | 规则 |
| --- | --- |
| Header | 标题说明整张卡的目的。右上角只能放影响整卡的持久可选操作，如“编辑”“更多”；图标单独出现时必须可访问命名。 |
| Body | 只放本卡主信息；多个 sections 使用 16pt / 32rpx 大组距、12pt / 24rpx 组内距。列表项是列表，不要将每一行再套 section/card。 |
| Footer | 放“基于上面内容的下一步”；普通一张卡只允许一个 primary CTA，其余收为 secondary/link 或更多菜单。 |
| Padding | 标准 surface/card 为 16pt；高信息密度商家卡可为 12pt；内嵌容器更小，但不能小到文字与边界贴边。 |
| Gap | 文字标签 → 字段或数值 8pt；同一信息单元 8–12pt；卡内不同信息组 16pt；不同 card 默认 12pt、跨区块 16–24pt。 |
| 高度 | 列表卡可随内容增长但应保持行节奏；长清单必须“查看全部/展开”，而不是形成无法一眼理解的超高卡。Polaris 同样建议避免难以总览的过高卡片。[P2](https://polaris-react.shopify.com/patterns/card-layout) |
| 可点击性 | 整卡可点击时，内部的收藏、更多、开关等必须独立为可感知的触控目标，不造成嵌套点击的误触。 |
| 选中 | 通过 semantic selected surface / border / check 等组合表达，不只改文字颜色；被选中不再额外套一层外框。 |

### 6.3 [城] 图片、缩略图与文本的排版合同

Polaris 要求 thumbnail 与文本一起提供对象语境，区分装饰性图片与需要描述的图片。[P8](https://polaris-react.shopify.com/components/images-and-icons/thumbnail?example=thumbnail-with-component-source) Apple 与 WCAG 同时提醒文字叠在复杂图片背景上会损害可读性，应按最终背景检验对比度。[A4](https://developer.apple.com/design/human-interface-guidelines/accessibility) [W1](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

- **媒体先定比例**：发现卡只选一类主比例；横向资源卡只选一个缩略图尺寸；地图封面、视频封面、人物头像各自有组件规则。禁止网络图天然比例撑开布局。
- **文字不漂浮**：图片下的标题、说明、meta 使用固定的内边距与行数策略；图文不能被另一个绝对定位 mask 挤偏。
- **文字叠图是例外**：只用于强叙事 hero。须有稳定、可测的渐变 scrim，正文不得压在高频纹理区；关键地点、价格、时间不可只放在图片里。
- **图片失效即有产品态**：加载中保留同样的比例 skeleton；加载失败使用对象级 placeholder + 文本，不允许出现巨大黑/白色空洞、像素化图案或无意义 demo banner。
- **语义区分**：纯装饰插图可忽略给辅助技术；头像、商家图、活动封面、二维码、地图标记等若传达信息，必须有可读的文本等价物或相邻可见文本。

## 7. 表单、按钮、筛选与交易安全

Polaris 表单要求只索取必要信息、逻辑顺序、清晰 label；placeholder 不是必需说明的替代品。[P6](https://polaris-react.shopify.com/components/layout-and-structure/form-layout) [P7](https://polaris-react.shopify.com/components/selection-and-input/text-field?example=text-field-with-prefix-or-suffix)

### 7.1 [城] 表单字段合同

| 字段状态 | 视觉与文案 | 行为 |
| --- | --- | --- |
| Default | 明确 label、输入面、必要时一句短 help text；label 不能只靠 placeholder | 输入类型匹配手机号、金额、日期等任务；键盘类型正确 |
| Required | label 或同一字段组给出统一的必填标识与原因 | 只在提交/失焦适当时验证，不在首屏对空字段制造满屏错误 |
| Focus | 3:1 以上可见 focus/边界，不仅依赖阴影或颜色深浅 | 焦点顺序与视觉顺序一致 |
| Error | 字段下就地说明“哪里错、怎样改”；长表单提交后顶部有可定位的错误摘要 | 焦点到摘要或首个错误；不能只 toast 后留用户猜 |
| Disabled | 保留 label 与原因，例如“填写营业信息后可提交” | 不可用并不等于不解释；给出达成条件或替代路径 |
| Loading / Saving | 按钮文案/进度显示正在保存；禁止重复提交 | 长任务显示阶段、可等待预期、重试或取消条件 |
| Success | 说明结果与下一步，而非短暂绿色 toast 就结束 | 保留可返回、查看或继续路径 |

### 7.2 [城] 按钮优先级

- 页面/Sheet 同一时刻只有一个 primary action。其他行动为 secondary、text/link、destructive 或 overflow。
- Primary button 最小有效触控面按 44×44pt / 88×88rpx 目标设计；WCAG AA 的绝对最低是 24×24 CSS px，Apple 的推荐移动控制尺寸是 44×44pt，因此城瘾采用更高的 44pt 内部标准。[W2](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) [A4](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- 图标按钮必须有文字等价或相邻不可歧义的 label；不要只用“纸飞机”“三点”“加号”来隐藏核心任务。Polaris 要求无文本图标提供可访问名称。[P9](https://polaris-react.shopify.com/components/images-and-icons/icon)
- 交易、提现、删除、注销、发布等高风险行动要有明确后果、金额/对象核对、撤销可能性和完成回执。不能将“不可逆”做成与普通保存相同的按钮等级。

### 7.3 [城] 筛选、tag 与选择控件

- tag 只表示可筛选维度、状态或用户提供的关键词；不是任何文案的彩色容器。
- 同一筛选组在一屏最多显示用户能一眼理解的少量选项；溢出进入“更多筛选/Sheet”，并显示已选数量/摘要。
- 被选中、未选中、禁用、不可用、加载中应为不同可辨状态，至少包含颜色之外的一项差异（对勾、形状、文案、位置）。
- 不用“筛选 chip + 页面 tab + 二级 tab + 横滑胶囊”四层选择控件竞争同一视线。每个控件必须回答不同层级问题。

### 7.4 [源 + 城] 商家长任务、反馈与入门流程

| 主题 | 官方事实（直链） | 城瘾落地推导 |
| --- | --- | --- |
| 复杂表单 | Shopify 要求复杂表单留出空间、渐进披露；输入项较多时按标题分组，不把大表单塞进受限 Modal，并使用明确保存。[P11](https://shopify.dev/docs/apps/design/user-experience/forms) | 入驻、创建活动、结算配置拆成“基础 → 时间地点 → 价格库存 → 提交”整页段落或显式步骤；保存栏显示草稿/未保存/保存中，而非让用户猜是否已经保存。 |
| 空、筛选无结果与错误 | Shopify 的空状态应解释这里将出现什么，并提供清晰下一步；首建、筛选无结果与功能激活都属于不同情境。[P12](https://shopify.dev/docs/api/app-home/patterns/compositions/empty-state) | 将 empty、filter-zero、error 分成三个组件状态：首建给“创建/邀请”，筛选无结果给“清除筛选/调整条件”，错误给“重试/返回”；三者不共用一张模糊插图。 |
| 一次性机会提示 | Shopify 的 callout card 只用于稀疏的新功能/机会提示，参与完成后应移除，窄屏自动纵向堆叠。[P13](https://shopify.dev/docs/api/app-home/patterns/compositions/callout-card) | “认证、补资料、首建活动”可以使用一次性任务卡，但必须可完成或关闭，不让商家首页长期被多条横幅广告/提醒淹没。 |
| 反馈分级 | Shopify 区分持续系统信息的 Banner、就近需解决问题的 Inline、短成功反馈的 Toast；需要处理的错误不能只依赖 Toast。[P14](https://shopify.dev/docs/apps/design/user-experience/alerts) | 城瘾统一为：字段/上传问题用 inline；资质、账户、持续系统状态用 banner；保存成功用短 toast。会阻断任务的失败必须有页面内恢复路径。 |
| 新手引导 | Shopify 提倡短、直接、只收必要信息、可稍后完成；独立步骤给进度反馈，通常不超过五步。[P15](https://shopify.dev/docs/apps/design/user-experience/onboarding) | 商家开店、首建活动、核销设置建立最多五项可续做 checklist；完成状态持久化，允许稍后继续，不用一次性强塞全套资料。 |
| IA 与移动优先 | Shopify 建议围绕用户任务减少分类，tabs 仅作二级视图；移动端优先纵向滚动并保证核心能力完成，不把关键任务推往桌面/外跳。[P16](https://shopify.dev/docs/apps/design/navigation) [P17](https://shopify.dev/docs/apps/build/mobile-support) | 商家 IA 按“要完成什么”组织而不是按内部模块命名；详情/编辑有显性返回；复杂数据改为筛选、摘要卡和详情页，不用横滑表格或外跳完成核心流程。 |

**[验]**

- 任一商家任务从首页进入、完成/保存、失败、返回的路径能够在手机一手操作中走通；不需要依赖浏览器返回、长横向表格或临时弹窗。
- 同一业务规则只选择一种反馈通道。若有 Banner，又有 Inline，又有 Toast，三者必须分别承担持续状态、字段问题、短成功回执，不能重复播报。
- 商家首页同时出现的 callout 不超过一个主机会；已经完成/关闭的提醒不再无期限回流。

## 8. 加载、空、错误、权限与成功：不是边角状态

Material 3 要求组件状态有一致且可辨的视觉指示；状态可组合，但不能互相矛盾。[M2](https://m3.material.io/foundations/interaction/states/overview) Polaris 将空状态视为帮助商家理解价值并完成下一步的机会，且只应有一个 primary CTA。[P4](https://polaris-react.shopify.com/components/layout-and-structure/empty-state)

| 状态 | 必须回答 | 城瘾页面合同 | 验收反例 |
| --- | --- | --- | --- |
| Loading | 正在加载什么？界面最终会是什么形状？ | 只对将出现的模块做结构一致 skeleton；小于 1 秒可不展示，长于 1 秒显示明确进度/说明 | 无限 spinner、整页灰骨架、骨架与最终卡片比例不同 |
| Empty | 为什么没有？用户能做什么？ | 标题说明对象为空，正文说明原因/价值，一个主要 CTA；没有创建权限时改为解释与可行下一步 | 只有“暂无数据”；空白大区域；没有 CTA |
| Error | 什么失败？能否恢复？ | 用户可理解的原因、重试、返回或替代入口；保留已加载内容 | 内部错误码、像素化异常图、暗色 error icon 看不见、同时写“失败/成功” |
| Permission | 为什么被拒绝？如何获得？ | 说明所需角色/条件，给申请、切换身份或返回 | 只弹“无权限”然后暴露不可操作的完整表单 |
| Offline / partial | 哪部分不可靠？上次更新何时？ | 局部 banner/状态，保留可用功能，给刷新 | 用“—”“---”伪装成真实数值 |
| Success | 发生了什么？下一步在哪？ | 结果、影响对象、查看/继续/返回 | 短 toast 消失后用户不知道是否完成 |
| Destructive confirmation | 会失去什么？是否可恢复？ | 精确对象与后果，安全的取消与明确破坏性按钮 | 红色仅作装饰；确认弹窗没有对象名称 |

**[验]**

- 每个数据型、表单型、权限型、编辑型页面至少有一套正常、loading、empty、error、no-permission 截图/录屏。
- 状态测试使用真实或受控可辨数据，不能把 DevTools 登录失败、路径参数缺失、网络异常当作“页面设计已验收”。
- banner 只用于重要且持续的上下文信息；Polaris 要求其位于对应页面/分区标题下，且不要用它代替把行动本身设计清楚。[P10](https://polaris-react.shopify.com/components/feedback-indicators/banner?example=banner-in-a-card)

## 9. 无障碍、可理解性与减少动效

Apple 强调可感知、直觉、可适配，且控制尺寸与控制间距同样重要。[A4](https://developer.apple.com/design/human-interface-guidelines/accessibility) Fluent 建议从结构、标题、逻辑阅读顺序、对比度和辅助技术规格一开始设计。[F5](https://fluent2.microsoft.design/accessibility)

### 9.1 [城] 强制无障碍清单

- 文本：普通文本至少 4.5:1；大文本才可降至 3:1；关键文字不要压图；不使用细字重做小字号正文。
- 目标：所有主要触控目标 44pt；紧邻 icon 仍保留误触间距。地图密集点可例外，但必须提供列表/搜索等等价路径。
- 非色彩线索：错误、选中、成功、营业中/暂停、会员等级不只靠颜色；加图标、文字、形状或位置。
- 标签：输入框有可见 label；icon-only 操作、图片、二维码、地图、加载和成功状态都有可读语义；装饰图不制造重复朗读。
- 图标实现：`×/✕/‹/›/✓` 这类字体字形不能直接承担可点操作。统一 IconButton 负责固定图标、≥44pt 热区、pressed/disabled、可读 label；删除 label 还须指出对象，必要时给撤销或确认。
- 焦点/阅读顺序：临时 Sheet/Modal 打开后进入其中；关闭后回到发起处或同义位置；错误摘要能导到字段。即使微信的实现接口不同，交互语义不能丢。
- 内容适配：长中文、英文、数字、金额、时间、放大字体、横竖屏/小屏不会盖住关键 CTA；必要时从横排改纵排，不以缩小字体解决。
- 手势：拖动、长按、地图拖拽、滑动删除等必须有可见替代操作。Apple 同样建议为手势提供替代路径。[A4](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- 测试：至少在高/低亮度、深浅主题、颜色识别差异、系统大字体、读屏/辅助技术可及情境下复查主路径。

### 9.2 [城] 动效合同

Fluent 将动效限定为解释关系、变化和结果，要求短、自然、可关闭无动效。[F6](https://fluent2.microsoft.design/motion) WCAG 对交互触发动效要求：非必要动效可禁用，并建议尊重系统减少动效偏好。[W4](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)

| 动效类型 | 城瘾允许范围 | 建议时长 | 禁止 |
| --- | --- | ---: | --- |
| 微反馈 | button press、toggle、收藏、成功标记 | 120–160ms | 用跳动/抖动替代错误说明 |
| 页面/Sheet | 进入、退出、层级关系 | 180–240ms | 背景与前景多方向同时滑动；无意义弹跳 |
| 内容加载 | 轻 skeleton shimmer 或 opacity | 160–240ms | 无限骨架、强闪烁、全页扫光 |
| 重点庆祝 | 完成成长、打卡、获得徽章 | 最短且可跳过 | 普通保存、每次点击、交易错误也做庆祝 |

时长是**[城] 内部建议**，不是任何外部系统的硬性数字。关键要求是：动效必须帮助理解、不能阻塞操作、不能成为唯一反馈；减少动效时用即时切换或淡入替代。

## 10. 玩家、商家、创作三类页面的差异化规则

### 玩家 Explore

- 首页/发现：先展示可靠的地点、活动、时间、距离、可信组织与明确行动，再展示氛围插图。卡片可有温度，但资料密度不可被品牌装饰吞没。
- 社区/话题：内容卡的作者、时间、正文、媒体、互动必须具有稳定次序；不显示假昵称、乱码、样例 logo 或无解释占位。
- 地图/搜索：地图是二维例外，但其选中地点必须有可读的底部摘要/列表路径；地图控件和返回/筛选/FAB 之间留足触控距离。
- 个人成长：深色或沉浸感只用于有品牌叙事的入口，所有数据、tab、关闭、返回、状态仍遵循同一 token 与对比度。

### 商家 Operate

- 首页：按“需处理任务 → 关键经营信号 → 可复盘数据 → 扩展工具”排序。未初始化数据必须说明“为什么暂无、何时有、下一步做什么”。
- 数据卡：先定义指标、周期、口径、趋势、异常；不能用醒目数字和“—”同时冒充可用仪表盘。
- 列表/订单/资金：金额、状态、时间、对象必须可快速扫描；筛选层不超过一层主筛选 + 一层按需筛选。
- 表单/入驻：一屏只解决一个步骤；上下文、字段、帮助、错误、提交从上到下可读；提交条件不能被低对比 disabled 按钮藏起来。
- 商家不能被玩家版的密集圆角、浮动品牌图、横滑卡、无标签 icon 干扰。商家版要“像可靠的经营工具”，而非“像营销落地页”。

### 创作 Create

- 创建/发布任务应设为专用 shell：一个明确进度模型、一套输入栅格、一个提交出口。
- 地图、封面、预览和内容编辑的视觉层级必须写入规格；若是全屏工具，就不要套普通页导航 + 页面标题 + full sheet。
- 自动保存、草稿、发布失败、权限不足、离开未保存等状态需要可恢复的证据，不用弹窗掩盖。
- 预览是辅助，不应覆盖提交、输入和系统安全区；预览按钮和真实发布按钮职责不同。

## 11. 设计到代码的交付合同

### 11.1 设计文件必须交付

- 基础变量：Primitive、Semantic、Component 三层，包含 light/dark/merchant/high-contrast（若支持）模式。
- 组件集：page shell、nav、tab、segmented、button、icon button、card A–H、media、field、selector、tag、banner、empty、error、skeleton、sheet、modal、sticky action。
- 组件状态：default、pressed、selected、disabled、loading、error、success、focus（适用时）、long text、no data。
- 真实样例：正常、长文本、空数据、失败、权限、加载、深/浅主题、图片失效。
- 量注与说明：触控范围、视觉边界、safe area、层级/z-index、关闭/返回语义、读屏文本、动态字体行为。

### 11.2 开发实现必须交付

- token 映射表：Figma 变量 → WXSS token → 组件 alias；没有映射的页面样式不得上线。
- 容器责任图：每页谁负责背景、左右 padding、safe-area、scroll、sticky footer、mask、sheet；以此排除“代码看起来对但多包一层”的视觉偏差。
- 状态契约：接口/权限/空数据/加载异常对应到同一组件状态，不能由每个页面手写 error 文案和空白布局。
- 路由-模式矩阵：每个请求路由在玩家/商家身份下的预期实际路由、主题、一级导航、页面标题、异常回退路径。
- 原生合成说明：页面是否使用 canvas/camera/map/video、前景信息和命中区由哪一层绘制、正常/fallback/失败态如何保证页面名/退出/CTA 同时可见。
- IconButton 台账：所有 icon-only 操作的视觉图标、最小热区、读屏 label、危险等级、确认或撤销策略；禁止页面内散落裸 glyph 控件。
- 视觉回归素材：每个路由、每个关键状态的可复现截图脚本与 manifest；DevTools 异常图必须标为无效证据并单独补拍。

### 11.3 上线前验收门禁

| 门禁 | 必须为真 |
| --- | --- |
| 视觉基础 | 主题、导航、正文、固定底栏、Sheet、图片、状态在相同模式下无错色、错位、重复壳、裁切或遮挡 |
| 组件一致性 | 任何卡片、按钮、字段、tab、sheet 都能归类到已定义组件；发现“第 N 种临时卡片”即视为设计债务 |
| 信息层级 | 每屏只有一个主行动；标题、卡片、数据、状态和 CTA 的视线顺序符合任务 |
| 状态完整性 | 正常、loading、empty、error、permission、success 有可执行恢复路径，且不互相矛盾 |
| 无障碍 | 对比度、触控面积、文字、图标 label、状态非色彩线索、减少动效、长文本/大字体已检验 |
| 原生合成 | canvas/camera/map/video 的正常、fallback、失败/权限态均能看到页面名、退出、状态和主要行动，并已回读点击 |
| 真实性 | 截图使用真实或明确受控数据；不以登录失败、参数缺失、编译异常、网络断开代替正常设计截图 |
| 平台 | iOS/Android 真机与微信环境复查安全区、字体、滚动、键盘、授权、返回和支付/交易关键流 |
| 回读 | 视觉通过只能说明被测版本/状态；每条截图记录 HEAD、路由、身份、数据状态、设备与时间，避免把历史证据混入当前版本 |

**实现级硬门（不受 `ds-ok` 视觉豁免影响）**

- WXSS 负值 token 必须写成 `calc(-1 * var(--token))`；`-var(--token)` 是非法函数，整条声明会在渲染器中被丢弃。门禁必须扫描真实声明（剥离注释）并做一条“接回 `-var(` 必须失败”的负控。
- `var()` 的别名必须在消费主题的作用域重新求值；不能把 `page{}` 早先解析出的暗色快照当成浅色页的动态主题。主题、导航、卡片和正文要用同一语义真值或组件钩子，并以商家/玩家两种主题各拍一张回归图。
- `quiet` 只表示视觉上不再重复解释短暂失败，不等于从辅助技术树删除状态名称；加载、成功、错误、权限状态仍需保留可读语义，装饰图才使用 `aria-hidden`。

## 12. 如何引用本基准到终审报告

终审主报告应把每个发现写成以下格式，避免“看着不统一”的模糊结论：

> **P级别 · 路由/组件 · 证据**：在某身份、某数据状态、某设备截图中出现什么可见问题。
>
> **违反的城瘾合同**：例如“普通页只允许一个导航模型”“图片失效必须保留对象级 placeholder”。
>
> **权威依据**：例如 [A2](https://developer.apple.com/design/human-interface-guidelines/layout)、[P2](https://polaris-react.shopify.com/patterns/card-layout)。
>
> **修复责任**：token、通用组件、页面壳、业务状态或素材；避免只改表层 margin。
> **验收证据**：修复前后同一状态截图 + 代码 token/组件引用 + 真机关键路径。

这样既能发现单页问题，也能发现“单页看起来没问题、但全局主题、tab、标题、卡片、字色、页壳不一致”的系统问题。

**结论**：专业设计系统不是“统一圆角、统一紫色”而已。它把用户模式、信息层级、token、页面壳、组件、状态、可访问性、动效、真实数据和验收证据连成一个可回读的合同。城瘾要达到高水平移动产品的完成度，必须先让这份合同在所有路由和状态上成立，再追求更强的品牌表达。

**品牌签名层（天花板）**：本基准是地板合同，不含品牌辨识度建设。签名系统的八个方向（线路图母题、深空底色阶、三个签名时刻、票券实体隐喻、数据叙事分享卡、占位素材系统、number token、商家端保持克制）及其执行顺序，见终审报告第 12 节《天花板方向：签名系统与设计奖评估》。地板未清零（P0/P1）前不启动签名层投入。

**漫游场景层（交互架构）**：地图内的历史、足迹、定向与自由探索遵循“同一内容页，按入口换承载方式”：`peek` 半屏、`scene` 近全屏、`page` 独立路由各有边界，分享/深链不被塞入弹层；唯一内容、路径和验收合同见终审报告第 13 节《漫游场景层》。本基准不重复定义另一套 Sheet 规则。
