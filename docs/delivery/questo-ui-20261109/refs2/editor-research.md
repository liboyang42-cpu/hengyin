# Story/chapter editor: X-Articles-style block editor with drag reorder — research

Date: 2026-11-09. Read-only research; nothing installed or changed in the repo.
Project facts checked: `chengyinhub-xcx/app.json` uses `componentFramework: glass-easel`, no `renderer: skyline` -> **WebView renderer**. WXS is already used in several components (e.g. `components/cy/funds-stages`), and `wx.vibrateShort` is already used.

## Bottom line

No open-source native mini-program project ships "X Articles editor + drag-reorderable mixed blocks". The workable path is to **build a block-list editor ourselves** and **copy the proven WXS drag core from wxp-ui**, adapting it to variable-height blocks. Do not try to make one big native `<editor>` hold all blocks: it has no API to move a block, and its custom-block support (`editor-portal`) is new (base lib 3.7.11) and limited to the WebView renderer.

Web interaction-model references (do not port, just copy the behaviour):
- **Lexical `DraggableBlockPlugin_EXPERIMENTAL`** ([facebook/lexical](https://github.com/facebook/lexical), MIT, 24k): one floating grip beside the hovered top-level block, plus a separate **target line** drawn between blocks during the drag (the dragged block is not moved live). The simplest, most robust model.
- **Tiptap DragHandle** ([ueberdosis/tiptap](https://github.com/ueberdosis/tiptap), MIT, 39k): floating-ui-positioned grip at `left-start`, `onNodeChange` to highlight the target block, lock/unlock commands, optional nested handles.
- **BlockNote** ([TypeCellOS/BlockNote](https://github.com/TypeCellOS/BlockNote), core MPL-2.0, 10k): Notion model. A side menu with `+` (insert below) and `⋮⋮` (drag; tap opens a block menu: delete / turn into / colour), a slash menu, and a formatting toolbar on selection. This is the closest match to the owner's "插入 ▾ + per-block grip".
- **Editor.js** ([codex-team/editor.js](https://github.com/codex-team/editor.js), Apache-2.0, 32k): JSON block array output `{blocks:[{id,type,data}]}`, `+` toolbox and per-block tunes (move up/down/delete). **Its data shape is a good model for our chapter JSON.**
- **dnd-kit sortable** ([clauderic/dnd-kit](https://github.com/clauderic/dnd-kit), MIT): TouchSensor activation `{delay: 250, tolerance: 5}`. The finger may drift 5 px during the press, but more movement cancels the drag so scrolling still works. Neighbours animate with transforms only, and the DOM order changes once on drop.
- **pragmatic-drag-and-drop** ([atlassian](https://github.com/atlassian/pragmatic-drag-and-drop), Apache-2.0): its auto-scroll package scrolls faster the deeper the pointer goes into an edge zone, with time-based acceleration so it does not jump at the first frame. Copy this speed curve.

## Native `<editor>` facts (official docs, WebView renderer only)

- Base lib 2.7.0+. It is Quill-based and stores content as delta, exporting html/text/delta.
- Supported tags: `p h1–h6 hr ol ul li`, inline `span strong b em i u a del s sub sup img`. `class` and `id` are stripped, `div` becomes `p`, and event bindings in inserted html are removed. Paste is plain text only.
- `format()` supports bold, italic, underline, strike, header H1–H6, list ordered/bullet/check, align, indent, colour, and others. **It has no `blockquote` format and no link API**. `<a>` survives `setContents` only.
- `insertImage`, `insertDivider`, and `insertCustomBlock({nowrap})` (**base lib 3.7.11+**) are available. `insertCustomBlock` returns a `blockId`. You then render `<editor-portal key="{{blockId}}">…</editor-portal>` inside `<editor>`. The delta keeps only the blockId, so the block's data must be stored separately and keyed by blockId. **There is no API to move a block or range.** Reordering would mean rewriting the delta and calling `setContents`, which loses the cursor and history and causes a flash. The doc's platform list names Windows, Mac and HarmonyOS, with renderer WebView only. Verify on a real iOS or Android device before relying on it.
- Tips: `catchtouchend` on toolbar buttons keeps editor focus (2.8.3), and the page is pushed up on focus. Not recommended inside `scroll-view`.
- Conclusion: one `<editor>` per **text block** works. A single `<editor>` for the whole article blocks drag reorder.

## Recommended architecture for 城瘾

Data: `chapter = { cover, title, blocks: [{id, type, data}] }` (Editor.js shape). Types: `paragraph{html, style: body|heading|quote}`, `list{html}` (or keep lists inside paragraph html), `image`, `audio`, `gameplay{refId}`, `divider`, `location{poiId}`. Text html uses the editor's tag whitelist and is rendered read-only with `rich-text` or mp-html.

Page layout (all custom WXML; nothing to reuse except the drag core):
1. **Top toolbar** (sticky; mirrored above the keyboard while typing, as in paff's `keyboard-area`): B / I / S call `editorCtx.format` on the **focused** text block, with active state from `bindstatuschange`. The **style dropdown 正文/标题/引用** changes the block's `style` field instead of calling `format`. Quote is a block style because `<editor>` has no blockquote. The list buttons use `format('list', 'bullet'|'ordered')`. Link opens a sheet that writes `<a>` via setContents, though external links are refused per the product decisions, so this may be internal links only or dropped. Emoji calls `insertText`. **「插入 ▾」** opens a sheet (image / audio / gameplay / divider / location) that splices a new block **after the focused block**.
2. Cover area, then the title (`textarea auto-height`), then the block list.
3. **Only the focused text block mounts a live `<editor>`**. Other text blocks render static html (`rich-text`) and swap to an editor on tap. This keeps one Quill instance alive, avoids N editors' memory and keyboard fights, and lets long-press on a static block start a drag without conflicting with text selection.

Drag mechanics (adapted from wxp-ui, WebView renderer):
- **Use WXS response handlers, not movable-view.** movable-view needs `movable-area` with absolute positions and known heights, and moving the neighbours needs `setData` through the logic layer on every frame, which is janky on Android. It also conflicts with page scroll and handles variable-height blocks poorly. WXS runs in the render layer: `ins.setStyle({transform})` on the dragged block and its neighbours with no setData per frame.
- **Start**: `bind:longpress` (about 350 ms) on the block body when it is not focused, or on an always-visible grip `⋮⋮`. A tap on the grip opens a block menu (move up / move down / delete), which also serves as the accessible fallback. In WXS, record `startY` and `scrollTop`, add a `lifted` class (scale 1.02, shadow), and `callMethod('vibrate')` -> `wx.vibrateShort({type:'light'})` (the `type` parameter is needed on newer base libs; skip on devtools as wxp-ui does). Set `dragging=true` once with setData so `catch:touchmove="{{dragging ? h.move : ''}}"` engages. This is the wxp-ui trick: page scroll stays normal until a drag starts.
- **Variable heights**: after each render or reorder, measure every block with `createSelectorQuery().selectAll('.blk').boundingClientRect()` and pass `tops[]`/`heights[]` to WXS through a `change:` observer prop, as wxp-ui's `baseData` does. Hit-test the dragged item's **centre** against neighbours' midpoints. When it crosses one, translate the blocks between by `±draggedHeight` with a CSS transition of about 200 ms, and fire a light haptic on each slot change, debounced. The dragged block follows the finger 1:1 with no transition.
- **Auto-scroll**: an edge zone of about 80 px under the top toolbar and above the bottom safe area. Drive a loop with `ownerInstance.requestAnimationFrame` in WXS while the finger stays in the zone. Speed is proportional to depth (pragmatic-dnd curve, capped at about 12 px per frame). Each tick calls `callMethod('scrollBy', dy)`, then `wx.pageScrollTo({scrollTop, duration: 0})` or a `page-meta scroll-top` binding. Add the accumulated scroll delta to the dragged item's translateY so it stays under the finger. Throttle the logic-layer scroll calls to about 30/s. This is the riskiest part on real devices and needs testing on iOS and Android. A fallback that avoids round-trips: during the drag, translate the whole list container instead of scrolling, and commit the real scroll on drop.
- **Drop**: WXS calls `callMethod('commitOrder', {from, to})` -> one `setData({blocks})` reorder, then clears all transforms in the setData callback (transition off for that frame to avoid a snap-back flash), re-measures, and fires `vibrateShort({type:'medium'})`. Also handle `touchcancel` the same way, since an incoming call or a system gesture must not leave blocks shifted.
- **Simpler alternative if live sliding misbehaves**: the Lexical model, where only a target line moves and neighbours stay still. It has the same WXS plumbing and less to go wrong.
- If the app ever moves to Skyline, `pan-gesture-handler` + worklet + shared values is the official path. But `<editor>`/`editor-portal` are WebView-only, so stay on WebView for this page.

Reuse vs build:
- **Reuse/adapt**: the wxp-ui `drag` WXS structure (MIT; keep the notice). This covers the longpress-to-WXS handoff, conditional `catch:touchmove`, the `callMethod` vibrate/scroll bridge, and the state in `ownerInstance.getState()`. The toolbar-above-keyboard approach comes from paff (MIT). mp-html can render stored chapters if `rich-text` is not enough (audio/video).
- **Build**: block data model and (de)serialisation, toolbar and insert sheet, variable-height sort core, auto-scroll loop, focus management between the single live `<editor>` and the static blocks, and the block menu.
- **Avoid**: movable-view sorters, unlicensed repos (chellel, DragSort, GXYOG), uni-app/Taro-only plugins, and a single-`<editor>` article with `editor-portal` blocks (no reorder API; 3.7.11+ only).

Real-device test checklist: long-press then drag in one continuous touch on iOS and Android, including after scrolling. No accidental drag while scrolling quickly. Auto-scroll both directions on a 30-block chapter. Keyboard open while dragging: blur first, or disallow drag while typing. `touchcancel` recovery. Haptics fire on both platforms (some Android devices ignore `type`). 60 fps with image-heavy blocks.
