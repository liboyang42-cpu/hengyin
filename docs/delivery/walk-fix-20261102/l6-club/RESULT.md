Branch `claude/walk-fix-1102-l6-club` from `origin/master` 014fc0d8. Findings are from `docs/delivery/cloud-walk-20261101/club/REPORT.md` (branch `claude/cloud-walk-20261101-club`).

Screenshots come from the walkthrough rig (real backend, real MySQL and Redis, the real mini-program bundle in the rig's browser runtime). They are not from a phone. `-before` shots are master 014fc0d8 and `-after` shots are this branch, replayed with the same fixtures and steps (`shots/`). HTTP records with database read-backs are in `http/`. The replay scripts are in `rig-replay/` (run against a fresh rig with `CAND=<candidate worktree> bash rig-replay/run-all.sh <before|after>`). The rig's MySQL runs at `+00:00` while Java writes Shanghai wall time; production runs `+08:00`. The club walk hit the same mismatch, and it is why `NO_SHOW` reads 0 through the API in the rig. `noshow_check.py` runs this branch's SQL with the session clock at `+08:00`.

## Deploy order

`migration_20261102_club_session_gather_point.sql` must be applied by hand **before** the jar is deployed (read-only precheck plus your confirmation, through the chengyin-db-migrate skill). It fills only empty `cms_activity.latitude/longitude` on club sessions that have not ended or been cancelled, and it is safe to run more than once. Until it runs, sessions opened before this deploy keep failing 「我到了」. Sessions opened after the new jar is live are fine either way.

## Needs owner

1. **C-20: what does 「引流型 · 无分成」 mean for the club?** The code has no clear earnings meaning for `share_mode=0`. The walker found the organiser slot is PLATFORM and the club is DISTRIBUTION, so any line about what the club earns would be a guess. **Recommended default:** leave the card as it is until you state the rule. I'll add one line once you do.
2. **C-05: full sign-up name on the roster.** The session's leader and staff with roster access now see the full name the member typed for 报名核验. The CRM keeps the masked 「周*」. Phone numbers stay hidden, per the roster's existing rule. **Recommended default:** keep the full name on the session roster only, since that is what check-in at the meeting point needs.
3. **C-27: the 核销 section on city-orienteering themes with no shops.** The section is how a club checks players' tickets at the gathering, so I kept it and removed only the 「到店」 wording. **Recommended default:** keep it. If you want it gone for themes without shops, say so.
4. **C-04: chapter release now applies to every city-orienteering session run from the workbench that has two or more chapters with stations.** Before this, players could play every chapter of such a session as soon as it started. Now chapter 2 onward waits for the leader. Sessions that were already running when this deploys have no current chapter, so they stay ungated until the leader releases the first chapter. **Recommended default:** keep the release rule (your 「等队长放行」 decision). Ask if you want themes to opt out.
5. **C-02 / P-05: may non-platform themes take online payment at launch?** L3 owns the player side. This lane only tells the organiser. When the rule opens, the notice disappears by itself.

## Rig replay

Fixtures and steps (the same for before and after): the leader (fixture 9008, club 7002) becomes a leader through `/api/club/become-leader`. A club-owned city-orienteering theme with 2 chapters and 4 stations is published through the V2 create API and approved by the admin endpoint. A session is opened through open-session 40 minutes ahead, and 4 players sign up. Then: gather check-in over HTTP; fixture time shift (the session start moved to one minute ago through the rig's `seed-walk.py shift-session`); PREPARE; two teams through `/api/team/create|join`; START; release; two arrivals marked through the roster API; FINISH. These handlers were called directly, as the walker did, where a tap did not register in the rig runtime: `leadArrive` and `openTeamSheet`.
