## 3. 关键发现：`xcx` 路径过滤恒为 true（未修，列为提案 P1）

证据：PR #483 只改了 `docs/delivery/doc2-survey-20261022/survey.{json,md}`，`Detect changed areas` 的日志如下：

```
predicate-quantifier: some
Filter xcx = true
Matching files:
docs/delivery/doc2-survey-20261022/survey.json [added]
docs/delivery/doc2-survey-20261022/survey.md [added]
```

根因：dorny/paths-filter 默认 `predicate-quantifier: some`，同一个 filter 下的规则是「任一命中即 true」。`'!chengyinhub-xcx/docs/**'` 在 `some` 下的含义是「任何**不在** chengyinhub-xcx/docs 下的文件」都命中，所以几乎所有 PR 的 xcx 都是 true，`Mini program static gates` 加 20 个分片每次都跑。

**为什么不在本 PR 修：**

1. 这次「误跑」实际上一直在提供覆盖。小程序单测/门禁会读 chengyinhub-xcx 以外的文件，例如 `docs/assets/template-covers/**`、`docs/delivery/gg-r5-zeroview-fixtures/**`、`docs/DESIGN.md`、`docs/chrome-spec.md`、`docs/UI*`、`docs/design/miniprogram-page-cleanup-1009.md`、`docs/DS*`（ds-hardcode-gate），还有 `docs/` 整目录扫描（cy-icon-pairing / play-overlay-spec）。要是照字面把 docs/** 排除掉，或者把过滤收窄到真正的 xcx 路径，改这些文件的 PR 就会 skip 掉本该变红的门禁，也就是假绿。按车道规则，有降覆盖风险的改动只能提案。
2. `ci/test_ci_cost_contract.py` 逐字钉住了 `- '!chengyinhub-xcx/docs/**'` 这一行。要修就得同时改这个合同（`ci/` 下的文件），超出「只改 workflow」的范围。

**估算收益（如果按 P1 修好）：** 19 个近期 PR 里有 4 个（#472 #473 #483 #485）没碰任何 `chengyinhub-xcx/**`。这类 PR 每次能省 `mini_static` 406 s + 20 分片 × ≈20 s ≈ 13.4 runner-min。其中纯 docs PR（#483）的墙钟能从 ≈6 min 降到 ≈1 min；碰后端的 PR 墙钟不变（被 Backend tests 卡住）。

## 4. 未实施的提案（都需要 owner 决定，或要动 `ci/` 脚本/check 名）

- **P1 修 xcx 过滤（最大收益）**：给 filter 加 `predicate-quantifier` 不行，它对所有 filter 生效，会破坏其他正向列表。可行写法是去掉否定行，改用 picomatch extglob：`'chengyinhub-xcx/!(docs)/**'` 加 `'chengyinhub-xcx/*'`。**同时**要把 §3 列出的那些 docs 输入（以及小程序门禁读到的其他 `ci/`、`sql/`、后端文件）逐条登记进 xcx filter，最好由 `ci/xcx-unit-manifest.js` 生成一份「测试输入清单」再做合同校验；并把 `ci/test_ci_cost_contract.py` 的断言换成新写法，配一条负控（纯 `docs/delivery/foo.md` 不命中、`docs/delivery/gg-r5-zeroview-fixtures/x.json` 命中）。
- **P2 分片平衡**：分片 8 中位 173 s，其余大多 < 10 s。眼下 mini_unit 墙钟（≈190 s）小于 mini_static（≈406 s），不在关键路径上，重排**不会缩短墙钟**，只是让分片之间更均匀。真要做，得给 `ci/xcx-unit-manifest.js` 加一个按历史时长分组的入口，并同步改 `ci/test_ci_cost_contract.py` 钉死的 `--test-shard` 命令。
- **P3 `test:e2e:contract` 跑两遍**：`Admin UI build gate` 里 `ci/ui-build.sh` 已经跑过 `npm run test:e2e:contract`，`Admin UI E2E contract gate` 又跑一遍。后者是独立 check 名（可能是 required），前者是部署链路的同一份脚本，两边都不宜删。每个 UI PR 重复约 50 s runner 时间，墙钟没有影响（两者并行）。
- **P4 Mini followup 与 Backend tests 重叠**：`Mini followup focused regression` 的 5 个类里，`NpcChatUserDataMyBatisIT` 也在 `ci/backend-test.sh` 的 MYBATIS_ITS 里；但它有独立的 39 例计数与证据 artifact，属于独立 check，不动。
- **P5 拆 `Mini program static gates`**：`ci/xcx-check.sh` 单步 390 s，是非后端 PR 的关键路径。拆成 2–3 个并行 job 能把这一族的墙钟降到 ≈3 min，但需要改脚本入口，而且要么新增 check 名、要么让现有 `Mini program static checks` 汇总 job 多 needs 几个 —— 要先确认 required check 配置。
- **P6 拆 `Backend tests`**：`mvn clean test` 397 s、原子迁移 IT 109 s、隔离启动 99 s 串行。把后两步拆成并行 job（用同一个已测 jar 的 artifact）理论上能把后端墙钟从 ≈11 min 降到 ≈8 min，但 `Describe the tested Boot Jar` 要求「同一 job 内启动通过」(`startupPassedInThisJob: True`)，属于部署证据链语义，不宜在 CI 提速车道里改。
- **P7 小程序分片浅克隆**：mini_unit 每片 `fetch-depth: 0` + `blob:none` checkout ≈8 s。要确认单测不需要 merge-base 后才能改浅克隆；收益只有每片几秒 runner 时间，墙钟可以忽略。
