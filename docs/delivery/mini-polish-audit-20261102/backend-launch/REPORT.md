# Backend launch review (lane: backend-launch), 2026-11-02

Base: `master` at a1d30fb (code identical to this branch's base). This was analysis only: nothing outside this file was changed, and no production, VPS, database or payment service was contacted.
Evidence labels: `code` means read directly. `replay` means the rendered SQL was checked offline against the real Druid 1.2.28 jar (the version pinned in `pom.xml`) using `MySqlWallProvider` with this repo's wall config (`multi-statement-allow: false`, all other settings default). `inferred` means reasoned from code but not executed.

## Summary
1. **Fix before launch: the Druid wall rejects `... and 1 = 0` mid-WHERE.** Most pages of `/api/creativesquare/list` (profile "posts" tab) and `/info` that contain a post linked to an activity or topic will throw and return an error. This was confirmed by replay; see BL-01.
2. **Fix before launch, if master rather than 963b351c is what ships:** 12 migrations merged after the 10-29 release pack are missing from it. Without them, the club feed, topic list/unlist and the roam retention purge hit missing columns (BL-02, BL-03).
3. **Fix before launch:** image upload calls WeChat `img_sec_check` with 30 s timeouts and has no rate limit, so it can tie up Tomcat threads (BL-04).
4. **Fix before launch (one line):** the admin "edit member" endpoint still writes `point` straight to the database, with no points ledger row (BL-05).
5. **Fine:** the money core (pay and refund callbacks, refund caps, withdrawal debit/CAS, coupon redemption, settlement claims), admin `@PreAuthorize` coverage, owner checks on mini-program writes, secrets handling, Druid console and Swagger exposure, pagination caps, and Quartz overlap settings. Details are in "Checked and fine".
6. Everything else is "can wait". The two most worth scheduling soon are an anonymous, uncached full template scan on `/api/template/homeData` (BL-07) and a server-wide cap of 2 AI calls at a time per provider (BL-08, which needs an owner decision).

Assumptions: the launch jar is built from current master (a1d30fb or later), not from the 10-29 pack's FINAL SHA `963b351c`. Where that matters, the row says so. Proposed SQL appears only as text and is **awaiting owner approval**.

## Checked and fine
- **Earlier wall worry not reproduced:** `GameSessionRuntimeMapper.xml:971` (`<otherwise>and 1=1</otherwise>`, the broadcast-to-all branch) **passes** replay. The `information_schema` + `database()` probe in `ClubMapper.xml:309-315` also **passes**, so private clubs do not silently fall back to public. No `BINARY x = BINARY y` remains (a contract test enforces this). There are no multi-statements and no `SELECT ... INTO`. The only `${}` uses are RuoYi's server-built `dataScope` and the admin generator.
- **Missing columns:** every identifier in all 304 mapper XMLs was compared against the base schema plus all 583 migrations, and nothing is missing once BL-02 is applied. No migration in the pack ALTERs a table created later in the pack, and every seed insert is guarded by `NOT EXISTS`.
- **Payments:**
  - The pay and refund callbacks are the only anonymous money routes. Signatures are verified by the SDK `NotificationParser`.
  - Duplicate notifications are dropped by an inbox keyed on `transaction_id:state`.
  - Amounts must match the frozen order amount to the fen, and status changes use CAS.
  - The original-order facts are re-checked (`WechatPayServiceImpl.java:102-118`). Club and commerce invoices follow the same pattern.
- **Refunds (registration):**
  - The registration history is locked before refunding, and the total refunded cannot exceed what was paid.
  - Only one pending request is allowed at a time, refund numbers are deterministic, and the dispatch claim is leased.
  - An UNKNOWN result is never resubmitted, and approval enforces maker ≠ checker.
- **Withdrawals:**
  - The bank path uses a unique request id, debits only above the frozen floor, and uses CAS for cancel and review.
  - The funds-correctness fix from 10-24 is in the code: the transfer intent is persisted before the SDK call, the SDK call is made outside the transaction, and UNKNOWN is never auto-credited back.
- **Settlement and coupons:**
  - Activity settlement runs one transaction per activity, with an `is_settlement` claim.
  - Coop payouts take a row lock and use `markPaidIfPending`.
  - Coupon redemption uses `FOR UPDATE` plus a `use_status` CAS and requires the dynamic QR token.
  - All balance and point debits are conditional. There is no float or double money arithmetic.
- **Authorization:**
  - Every write in the 90 `controller/business` files has `@PreAuthorize`.
  - The mini-program write paths traced (activity, coupon, withdrawal, club, comment, topic config, merchant applications, registration, gift, city node, verify) check owner or merchant scope in SQL or under a lock.
  - The known activity IDOR fixes are intact.
- **Configuration that must not ship:**
  - All secrets come from environment variables with empty defaults, and only the variable names appear in the repo. `cert/` contains only a readme.
  - The Druid console is off by default, limited to 127.0.0.1, with its password from an environment variable. Springdoc is off by default.
  - Actuator exposes only `health`/`info`. Log levels are info/warn.
  - The backend has no fake-user or dev-token fallback. In the mini program, `?mock=` is gated by `isDevEnv()`, and the production API base is the production domain.
- **Launch load:**
  - `PageUtils.startPage` caps the page size at 50, and the anonymous lists use it.
  - Login, SMS, play and AI endpoints are rate-limited per member or IP, with daily AI caps.
  - Quartz runs in memory on a single instance; every seeded job has `concurrent='1'` and misfire policy `3`.
  - The Druid pool is 40 connections with `maxWait` 5 s. Tomcat has 200 threads. All other outbound HTTP calls have 3-10 s timeouts.
  - Redis keys without a TTL are bounded (config/dict caches, `wx_access_map`, per-scene QR codes).

Not covered in depth: FreeExplore bundle refund quotes, coop deposit refund internals, `RefundReconcileTask` / `WithdrawTransferQueryTask` beyond their claim pattern, and a line-by-line read of every one of the 127 mini-program controllers (they were covered by grep of update/delete paths, request bodies bound to entities, and anonymous routes).
