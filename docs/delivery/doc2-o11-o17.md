### (b) 关键路径失败事件（本 PR 新增）

每次失败只发**一行**，固定格式，便于 grep：

```
[CY-CRITICAL] code=<事件码> kind=<FAULT|REJECTED> op=<子操作> cause=<异常类名> root=<根因类名>
```

- logger 名为 `com.chengyinhub.critical`，沿用现有 `com.chengyinhub` 日志级别配置。FAULT 记 ERROR，REJECTED 记 INFO。
- **不含 PII**：行内只有枚举码、固定字面量 `op` 和异常类名。不带异常 message，不带堆栈，也不带会员 / 订单 ID、openid、手机号、金额。`op` 不匹配 `[a-z][a-z0-9_]{0,31}` 时一律写成 `invalid`。
- **指标**：`chengyin.critical.path.failures{code,kind}` 是 FunctionCounter，7 个码 × 2 种 kind，共 14 条序列，基数固定。由 `CriticalPathMetrics` 注册进现有 Actuator / Micrometer。本 PR **不改** `management.endpoints.web.exposure`（仍是 `health,info`），要不要对外暴露由 owner 决定。
- **kind 的判定**：本仓库的业务拒绝习惯抛 `IllegalArgumentException`、`IllegalStateException`、`ServiceException` 或裸 `RuntimeException`，这四类记为 REJECTED。其余（数据访问、事务、连接池超时、Redis 连接、NPE 等）记为 FAULT。**告警只看 FAULT。**
- **只发一次**：`@CriticalPath` 切面排在 RateLimiter、死锁重试和事务通知器外层，所以死锁重试成功的调用不发事件，提交阶段的失败也能被看到。同一个异常实例（含 cause 链）沿嵌套的关键路径向外抛时，只按最内层的码发一次。举例：支付回调里结算入账失败，只发 `CP_SETTLEMENT_ACCRUAL_FAILED`，不再追加 `CP_PAYMENT_INBOX_FAILED`。既有的 `payment.callback.*` 告警不受影响。
- 事件代码自身绝不抛异常，不改变任何业务返回值或异常。

| 事件码 | 关键路径 | 接入点（op） | 建议告警 |
|---|---|---|---|
| `CP_PAYMENT_INBOX_FAILED` | 微信支付回调 inbox | `WxPaymentCallbackInboxServiceImpl.process` 的 catch（`process`） | FAULT ≥ 1 / 5 分钟 → 立即通知值班。微信会重投，但持续失败意味着已付未确认 |
| `CP_REDEMPTION_FAILED` | 核销 | `SmsCouponHistoryServiceImpl.redeemCoupon`（`coupon`）、`PerkLedgerServiceImpl.redeemChapter`（`chapter`） | FAULT ≥ 3 / 10 分钟 → 通知。REJECTED 只看看板 |
| `CP_REFUND_FAILED` | 退款 | `RefundServiceImpl.reviewRefund`（`review`）、`handleRefundNotify`（`notify`）、`markPayoutResult`（`payout_result`）；`RefundPayoutServiceImpl.payoutAfterReview`（`payout`） | FAULT ≥ 1 / 5 分钟 → 立即通知（资金） |
| `CP_SETTLEMENT_ACCRUAL_FAILED` | 结算入账 | `SettlementEntryServiceImpl.recordOnPayment`（`payment`）、`recordPaidRegistration`（`paid_registration`）、`recordCouponVerification`（`coupon_verification`） | FAULT ≥ 1 / 5 分钟 → 立即通知（资金，与 `monitor.settlement.*` 对账互补） |
| `CP_CONSENT_WRITE_FAILED` | 同意记录 | `ConsentRecordServiceImpl.record`（两个重载，`record`） | FAULT ≥ 3 / 10 分钟 → 通知（合规留痕缺失） |
| `CP_AUDIT_DECISION_FAILED` | 审核决定 | `AuditTaskServiceImpl.review`（`review`）、`revert`（`revert`） | FAULT ≥ 3 / 10 分钟 → 通知 |
| `CP_DEREGISTRATION_FAILED` | 账号注销 | `AccountDeregistrationServiceImpl.apply`（`apply`）、`cancel`（`cancel`），到期批次逐条 catch（`execute`） | `op=execute` 任意一次 → 通知（既有 `注销执行异常` 告警之外再给一个固定码）；其余 FAULT ≥ 3 / 10 分钟 |

### (c) 告警出口：只文档化，不配置生产

告警通道归生产 owner 管（现有 `ALARM_WEBHOOK` / `alarm.failure-webhook` 也是在生产注入的）。本 PR 只定义事件码和规则。可选落地方式如下，都不需要改代码：

1. **基于日志**：在生产日志采集侧按 `\[CY-CRITICAL\] code=(CP_[A-Z_]+) kind=FAULT` 计数，按上表阈值告警。最快，也不用改暴露范围。
2. **基于指标**：把 Actuator 的 `metrics`（或 Prometheus registry）在受限网络内暴露出来，按 `increase(chengyin_critical_path_failures_total{kind="FAULT"}[5m])` 告警。需要 owner 改 `management.endpoints.web.exposure` 并评估鉴权。
3. **复用 AlarmService**：以后如果要把 FAULT 直接推到值班群，可以在 `CriticalPathEvents` 外加一个监听，调 `alarmThrottled("critical." + code, …)`。这会改变告警流量，需要 owner 先同意，本 PR 没做。

合同：`CriticalPathContractTest` 钉住上面每个接入点的码和 op、每个码至少接了一条真实路径，以及本表每个码只登记一次。新增或改名事件码时，必须同时改这里。

### 发现 1：连接池恢复门禁一直是空壳（已修）

`f97fcacf`（移植 #69）给 `ci/upgrade-startup-smoke.sh` 加了 `CHENGYIN_CI_POOL_RECOVERY` 分支，用来调用 `pool_recovery_probe.py`。按 `git log --full-history`，这段钩子只出现在移植分支那条线上（`f97fcacf` … `b72c0dc7`）。master 那条线上，2026-10-21 的 `dbc3163a`（「隔离启动追踪工具的加载器与依赖」）重写了启动方式；两条线合流后保留的是不带钩子的版本，当前 master 的脚本里已经找不到 `CHENGYIN_CI_POOL_RECOVERY`。结果是 **Isolated pool recovery 作业只跑了普通启动冒烟就报绿**。最近一次绿的 run 是 39643176283（2026-10-21）：上传的 5 个文件里没有 `pool-recovery.json`，日志里也没有任何池探针输出。

修复，均为加强、不放宽：
- 把三处钩子（启动参数 `POOL_PROFILE`、执行环境自检、启动后调探针并复测 health）按原提交恢复进当前脚本。
- workflow 在冒烟后**强制**要求恰好一份 `pool-recovery.json`，并且 `result == PASS_BOUNDED_POOL_TIMEOUT_RELEASE_SAME_PROCESS_RECOVERY`，否则失败。
- 触发路径补上 `ci/upgrade-startup/**` 和两个打包配置文件。连接池或 Tomcat 配置一改，就要重新证明恢复。
- `CapacitySizingConsistencyTest.poolRecoveryGateExercisesTheShippedPoolDefaults` 静态钉住两点：冒烟脚本必须真的调用探针；探针校验的 `maxActive / maxWait / socketTimeout` 必须等于打包默认值（20 / 5000 / 60000），避免门禁证明的配置与上线的配置不一致。

### 发现 2：配置数值与建议（仅建议，本 PR 不改任何生产配置）

当前打包默认值，以及测试钉住的不等式：

| 项 | 当前 | 钉住的不等式 | 结论 |
|---|---|---|---|
| Druid `maxActive` | 20 | `minIdle(10) ≤ maxActive`，`initialSize(5) ≤ maxActive` | 保持 |
| Druid `maxWait` | 5000 ms | `0 < maxWait ≤ 小程序默认超时(12000)/2` | 保持。池满时客户端拿到的是明确的 500，而不是自己的超时 |
| Druid `socketTimeout` | 60000 ms | `≥ maxWait` | **建议评估降到 15000–20000 ms**：比客户端 12 s 长得多，慢 SQL 会在客户端放弃后继续占住连接最多 60 s。需先确认后台导出类慢查询的耗时 |
| Tomcat `threads.max` / `accept-count` | 200 / 200 | 都 `≤ 10 × maxActive`（=200） | **已到上限**。若后续同规格压测出现线程排队等连接，建议降到 100 / 100（可用 `CHENGYIN_TOMCAT_*` 环境变量回调，不改包） |
| Redis `timeout` | 10 s | `< 客户端 12 s` | **建议 3 s**（与池等待一致）。现在 Redis 卡住时请求要 10 s 才失败，只比客户端超时早 2 s |
| Redis `lettuce.pool.max-wait` | 3 s | `0 < 值 < 12 s` | 保持 |
| Redis `lettuce.pool.max-active` | 8 | `> 0` | 观察项：classpath 上有 commons-pool2，池生效；200 个请求线程共用 8 条连接，Redis 变慢时会排队到 3 s。是否调到 16 需要压测，不建议拍脑袋改 |
| `threadPoolTaskExecutor` | core 50 / max 200 / 队列 1000 / CallerRuns | 有界队列 + 背压，不静默丢任务 | 保持 |
| `scheduledExecutorService` | core 50（`AsyncManager` 的登录 / 操作日志写库、通知等共用） | — | **建议降到 ≤ 10（maxActive 的一半）**：极端情况下 50 个异步写库线程可以占满 20 条连接，把请求线程饿死。这是代码常量，改它属于行为变更，单独立项 |

以上都不是容量结论。真实容量要在同规格隔离环境压测，按约束本次不做。
