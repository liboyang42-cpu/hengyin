## 1. 交付目标与共同基线

用户要求所有游戏集中可发现、可采用、可跨主题复用；每个 agent 获得完整目的和交付链，不能只领一个小修复。四项已批 TG1–TG4 是本方案的共同目标：完整内容单元、审核发布与运行绑定、玩法机制复用、发布前组合校验。答题是第一条样例，不是总范围。

共同公开源码基线为 `fa5c263440573992701263d6bee60830844a49b8`；施工约束提交为 `d4fecb55dc48d9722b8fe6c2b918aada68ce718d`。root 工作树还包含按作者摘要精确集成的后续源码，未形成新验收候选。固定公共 master `51f05499c1523648a328f57bcd7927f6d9546003` 的祖先关系保留，不无限追逐实时 head。

本方案覆盖全部实际游戏，不等于授权支持所有想象中的新游戏。每个现有条目必须明确是可采用的内容、机制、附加规则、主题进度能力，还是仅供特定模式使用的入口；未接完成证明、渠道或设备的条目不能改个标签就宣称可用。原完整 WP00–WP17／Q1–Q10／A01–A15／T01–T22／G0–G5 仍保留，资金、身份和恢复验收不会被本方案代替。

## 2. 推荐结构：复用现有五层，不重建游戏引擎

| 层 | 城瘾现有落点 | 本层最终结果 |
|---|---|---|
| 玩法机制 | `GameplaySupportMatrix`、`GameplayTemplateRules`、实际 judgement／runtime 服务、客户端 playkit | 同合同玩法只有一个权威判定及必要展示组件；主题不分叉实现 |
| 完整小游戏内容 | `cms_member_template`，公开投影 `cms_template_library` | 内容、素材、玩法参数、反馈、互动与资源槽一起被编写、检索和采用，不只保存题目 |
| 主题与场景绑定 | chapter／node 的个人 `templateId`、原 `templateBindings`、`TemplateResourceSlots` | 同一机制配不同内容，已有内容按实际 owner／引用重映射规则复用或派生 |
| 审核与发布内容 | `TopicBundleReviewService`、`TopicRoutePublicationCompiler`、原 publication 服务 | 送审、批准、发布使用一致内容；实际配置、答案、引用被稳定冻结 |
| 玩家／队伍实例 | 原 GameSession／RuntimeSession／StoryState 及相应玩法状态 | 局与局、主题与主题状态隔离；新版本不静默替换已开的局 |

“集中”指同一套目录、采用流程、权威机制和可追溯身份，不要求把所有文件搬进一个文件夹。主题作为完整游戏内容单元可以组合多个小游戏；完整主题复制继续走原主题模板功能，不把它与小游戏公共库混为一种对象。

两种复制有必要保留：跨 owner 采用成为自己的草稿，以及发布／开局复制成冻结快照。应禁止的是复制判题、状态机或 renderer 成为主题专属实现。普通题、偏好调查、剧情选择、掷骰、实物／地点证明和多人机制的合同不同，不能强迫它们使用一套提交协议。

## 3. 已核实的现存能力和真实缺口

以下均为当前源码结论，不是运行签收：

1. `cms_member_template` 已保存媒体、感应器、偏好组、高级配置、剧情、反馈、奖励、互动规则和资源槽，不需要再建“完整游戏表”。公共库是原个人模板的审核货架投影，不能独立伪造一份来源。
2. `POST /api/template/adopt-draft` 已服务端复制可见来源，生成采用者个人草稿。公开详情会剥秘密字段，客户端不能用“详情 JSON 复制”代替采用入口。`originalTemplateId` 在此指公共库 ID，节点 `templateId` 指个人模板 ID；路线 preset 的 `playTemplateId` 又指公共库 ID，转换必须明确。
3. 主题复制已有 owner 和 NPC／节点引用重映射逻辑；同 owner 无需重映射时可沿用 ID，跨 owner 或带原主题引用时派生是正确隔离。商家据点也使用原个人模板，没有必要另造一套内容库。
4. 发布编译与运行快照已有实现。`originalTemplateId` 不是完整内容版本，`slotDigest` 只覆盖资源声明，主题 `configVersion` 也不是库级版本。优先用原审核 hash／发布快照闭合实际使用身份；没有真实消费者需求不新增版本表。
5. 初步展开后端注册源码为 32 个 type、10 个 addon，共 42 个 key。这只是后端注册维度，不是 42 个独立小游戏，也不是实际库中上架数量。A／D 必须交付逐项前后端对照；`compare` 等有判定路径但不在 matrix 的条目须单列，不能扩大完成证明白名单凑齐数量。
6. 答题已确认 `qaPick → qa.mode=PICK → AdvancedActionJudgement.submitQa`，普通和引导题组复用同一权威判题；客户端已有 `playkit-qa`。已补的实例／异步围栏和跨主题测试源码只是一个子任务。
7. 后台旧模板库页面已转模板中心，但现模板中心编辑器主要覆盖原验证方式 1／2／3，不能据此称已覆盖所有高级玩法。先找已有完整编辑入口，补发现、采用和无损保存链，不复制另一套玩法编辑器。
8. G 的 `edf731c15090d2289553dd7f966f6c7d8ec7f5e2` 12文件已按供体后像精确集成：原 hash／有序锁保留，编译消费同次锁定投影，作者运行配置进入原 hash；13条新增测试声明未执行。仍有明确消费接缝：部分展示文字取 live 模板，新 Advanced 节点局的 template 身份取 live 引用，独立 state-key 声明还未证明同源绑定。它们由 G／H／F 按下表闭合，不把 RR 片当全部发布内容冻结。

主要收益排序：优先补完整库／机制索引、正确采用与绑定、发布快照一致、实例隔离；随后按真实缺口补编辑／检索入口。每主题一套后端、所有玩法重写成 JSON 脚本、动态加载任意代码、无消费者的新 SPI／数据库版本框架、全仓搬目录，均不是本轮解决方案。

## 4. 三条作者工作流必须一起成立

复用有两个内容粒度：**整套主题游戏**沿原 `cms_topic.is_template`／`ApiTopicTemplateController` 的 `POST /api/template/topic-template/use {id,scope}`／主题复制服务采用为新主题草稿，须保全章节、节点、小游戏引用和需要重映射的场景资源；**小游戏内容**沿个人模板／公共货架采用。再下一层才是共用机制。三者都纳入目的，不能只交 42 个后端 key 清单就宣称完整游戏可复用。入口可以统一发现并区分资源类别，实际 ID、采用与权限合同仍沿原对象，不合并成一张万能表。B／D 在现入口及 copy 链内一并核实，G 验证采用后的实际主题发布冻结；已满足的路径保留，不重写完整主题复制器。

### 4.1 采用已有完整小游戏

已有目录检索／筛选 → 查看原允许的说明和演示 → 原服务端 adopt-draft → 获得自己有权编辑的个人模板 → 按原资源槽绑定地点／角色／道具 → 主题节点绑定个人模板 → 原组合审核／发布 → 玩家实例消费冻结配置。采用之后不修改来源作者内容，不自动追随来源后续编辑。

### 4.2 用已有机制制作新的内容

在同一能力目录选择已有类型 → 原编辑器填写内容和参数 → 原校验 → 原个人模板／审核／公共货架流程。新增题目、剧本或美术不会产生新的 backend handler、主题专属 Controller 或 `xxx2` 玩法。资源、秘密字段、商家优惠券权限不能随复制被扩大。

### 4.3 出现确实不存在的新机制

先列现有 key、实现和不适用原因，再给出具体新行为；仅在现有机制不能表达时扩展原权威 owner、注册、配置校验、renderer／adapter、完成证明及测试源码。缺少真实证明时保留明确不支持／UNKNOWN，不以注册成功替代业务完成。不得因内容名称不同新增机制。
