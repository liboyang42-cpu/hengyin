### 当前发布边界

- 生产只读预检已连到 MySQL `8.0.45`，相关表存在且均为 InnoDB，但“表存在”反而暴露了早期候选的部分成功：两个俱乐部 CHECK 仍可被 `NULL/UNKNOWN` 绕过，售后结构缺门店 `merchant_id`/反向查找索引，CRM 导出任务仍保留 `merchant_row_id`；新增 `resume_blocked_at` 与活动取消人工退款责任表尚无生产回读。当前快照为 **18 个 pre-deploy schema + 3 个已执行但台账缺失的不可变 job 历史 + 1 个新 Quartz 暂停 repair，共 22 份 SQL**。新增第 18 个 schema 为 `migration_event_cancel_manual_refund_case_20260826.sql`；所有 schema 必须按生产当前镜像逐文件授权、执行与新连接回读，三份历史 job SQL 则必须保持原 bytes/checksum，禁止重跑。
- 三个目标 Quartz job 并非“尚未注册”：`job_id=125/126/127` 的 create_time/config/remark 与三份原 job SQL 一致，证明它们已实际执行并以 `status='0'` 启用，只是 `cy_migration_history` 对这三条仍为 0 行。当前生产制品不包含 `ClubEventOpsTask`、`ClubPostMediaReviewTask`、`MerchantCrmDeliveryRecoveryTask`，`sys_job_log` 每分钟持续写入 `NoSuchBeanDefinitionException`；这是已发生的生产调度故障。
- 新 `migration_merchant_z_quartz_jobs_pause_repair_20260826.sql` 仅将 exact-three DB 持久态收敛为 `status='1'`。它不会自动暂停当前 JVM 里已装载的 Quartz trigger；真实止血必须走 scheduler-aware pause，或在运行该 repair 后受控重启旧 jar，然后新连接回读并跨 cron 周期观察无新失败。

### 商家最高优先级缺口

1. **P0：经营团队 RBAC。** 至少拆出 Owner、核销员、运营、财务；名单和财务不能依赖共享商家主账号。
