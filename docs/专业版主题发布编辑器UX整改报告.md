# 城瘾小程序专业版主题发布编辑器 UX/UI 整改报告

更新时间：2026-06-25  
范围：微信小程序专业版主题发布、节点编辑、节点内游戏绑定/创建、发布前预览  
涉及主路径：`chengyinhub-xcx/pages/publish/fabu/index.*`、`chengyinhub-xcx/pages/publish/temp/index.*`、`chengyinhub-xcx/pages/play/index.*`

## 1. 结论

专业版主题发布现在最大问题不是功能缺失，而是创作者工作流被拆散：

- 地图只作为顶部展示，不是主要编辑画布。
- 节点编辑在列表和弹窗里完成，用户需要在“地图预览、路线设置、剧情内容、通用设置、节点弹窗、模板弹窗”之间切换。
- 节点可以绑定游戏，但游戏必须先在主题外创建为模板，再回到节点里选择，创作状态被中断。
- 页面已经有 Strava 风格路线 Hero 和统计数据，但交互模型仍是传统表单编辑器。

建议一次性重做为“地图画布式主题编辑器”：地图成为主工作台，节点在地图上创建/选中/移动，底部抽屉完成节点信息、剧情、游戏和奖励编辑。游戏编辑不再要求先离开主题，而是在节点抽屉内就地快速创建，并可选择保存为模板。

关键技术判断：微信小程序里不建议做真正的 marker 长按拖拽。更稳的方案是“点击地图/POI 添加节点 + 中心准星移动节点 + marker 点击打开编辑抽屉 + 节点列表拖拽排序”。这能达到接近拖动的体验，同时兼容微信 map 原生组件限制和真机性能。

## 2. 当前现状流程

### 2.1 入口与页面结构

专业版主题发布页在 `pages/publish/fabu/index.wxml`：

1. 顶部是路线地图 Hero，使用 `<map>` 渲染 `markers`、`polyline`、`include-points`。
2. 地图下方显示站点、里程、时长、模板数。
3. 主编辑区分为 3 个 tab：路线设置、剧情内容、通用设置。
4. 发布按钮只在通用设置 tab 底部出现。

现状优点：

- 已经有路线地图、marker、polyline、统计数据的基础能力。
- `buildRouteMap()` 已经能从 `chapters[].nodes[]` 展平生成地图 marker 和折线。
- `updateAllStatistics()` 已经把节点变化、统计数据、地图刷新串起来。

现状问题：

- 地图是“结果展示”，不是“编辑入口”。
- 用户添加节点时仍要进入章节列表，点“添加节点”，再在弹窗里选择地点。
- 地图 marker 没有成为节点操作入口，无法点 marker 直接编辑。
- tab 把一个连续的创作任务切成三段，创作者很难形成“我正在设计一条城市路线”的直觉。

### 2.2 节点编辑流程

当前节点编辑弹窗在 `pages/publish/fabu/index.wxml`：

1. 点“添加节点”或节点卡片。
2. 打开 `popChapterNodes` 弹窗。
3. 在弹窗里选择地点、上传图片、选适配时间、开关添加模板、选择我的模板、写节点描述、设置活动时间。
4. 点完成后 `confrimNode()` 校验地址、描述、节点时间，再写回 `formData.chapters`。

现状优点：

- 节点字段相对完整：地点、地址、经纬度、图片、营业时间、描述、时长、模板。
- 已有 `roleGuard` 节点上限校验，玩家 Lite 与俱乐部/商家权限可区分。
- 已复用 `pickLocation()` 做地点选择。

现状问题：

- 节点编辑像“表单弹窗”，不是“地图上的点位编辑”。
- 节点顺序隐藏在章节列表里，空间关系和顺序关系割裂。
- 删除节点、移动节点、复制节点、预览节点都不够直接。
- 校验失败使用系统 toast，缺少编辑器内的状态反馈和错误定位。

### 2.3 游戏模板流程

当前游戏创建页在 `pages/publish/temp/index.*`：

1. 用户进入创建游戏页。
2. 填游戏标题、描述、玩家人数、时长、难度、材料、场所、封面、类别。
3. 添加“完成方式”模块，选择扫码、文字题、拍照、选项题、GPS/无需验证等。
4. 可配置提示、奖励、剧情、语音等模块。
5. 发布后调用 `/api/template/publish`，保存到“我的模板”。
6. 回到主题专业版，在节点弹窗中打开“添加模板”，从 `/api/template/my-list` 返回的模板中选择。

现状优点：

- 游戏编辑器本身已有较完整字段和校验。
- 后端已有 `/api/template/publish`、`/api/template/draft`、`/api/template/my-list`。
- 游玩页已识别 `validationMethod`，并调用 `/api/play/checkin`、`/api/play/answer`、`/api/play/photo`、`/api/play/arrive`。
- `/api/play/nodes` 已下发模板呈现字段，并避免下发敏感答案。

现状问题：

- “设计主题”和“设计节点游戏”是两个不同页面，创作心流中断。
- 创建一个节点游戏至少要跳出主题、发布模板、回来刷新/搜索模板、绑定模板。
- 对新用户来说，“模板”是系统概念，不是自然创作概念。用户想的是“这个点怎么玩”，不是“先创建一个模板”。
- 节点里只能选已有模板，不能快速创建、复制当前节点游戏、临时保存草稿。

## 3. 竞品参考与可借鉴原则

### 3.1 Strava Route Builder

Strava 移动端路线创建支持：

- 点地图添加路线点。
- 点已有点后移动或删除。
- 用画笔在地图上画路线，并自动吸附道路/路径。
- 可撤销上一步。

对城瘾的启发：

- 地图必须是主编辑器，而不是预览图。
- 添加节点应从“点地图/点 POI”开始，而不是从表单开始。
- 撤销、移动点、删除点是路线编辑器的核心操作。
- 城瘾不必一开始做路线吸附，因为城瘾节点是城市点位/关卡，不是跑步导航路线；先做点位和折线即可。

参考：https://support.strava.com/en-us/articles/15401660-creating-routes-on-mobile

### 3.2 Komoot Route Planner

Komoot 路线规划支持：

- 直接在地图上加 waypoint。
- 从底部面板查看路线详情。
- waypoint 可拖拽排序。
- 地图图层、回到当前位置、路线方向等作为工具存在。

对城瘾的启发：

- 地图负责空间选择，底部面板负责详情编辑。
- 排序更适合放在 waypoint 列表中，而不是强行在地图上拖线。
- 路线数据应实时更新，让创作者立刻看到距离、时长、节点数。

参考：https://support.komoot.com/hc/en-us/articles/10206792140826-Plan-routes-in-the-app

### 3.3 AllTrails Custom Routes

AllTrails 支持：

- 点地图连续创建路线。
- 点路线点编辑。
- 拖动路径点调整路线。
- 底部或侧边显示路线预览、照片、统计信息。
- 支持路线选项：反向、闭环、减少爬升、风景路线等。

对城瘾的启发：

- 城瘾可以保留“主题预览”和“玩家视角预览”，让创作者在发布前看到真实游玩体验。
- 对每条路线应有“完整度评分”：是否有封面、节点是否都有地点、是否有游戏、是否有奖励、是否有票务。
- 复杂路线工具不要第一屏全露出，应藏在更多菜单或高级设置里。

参考：https://support.alltrails.com/hc/en-us/articles/37270479773204-How-to-create-custom-routes

### 3.4 Nike Run Club

Nike Run Club 的价值不在路线编辑，而在“轻陪伴”和“低压力引导”：

- 出发前提供本地天气、日出日落等提示。
- Guided Runs 用内容和教练感降低用户压力。
- 位置共享让运动过程有安全感和社交感。

对城瘾的启发：

- 创作者编辑器也需要“教练式引导”，但不要写成长说明。应用内可以用完成度、缺口提示、下一步建议来引导。
- 游玩预览要突出“玩家会怎么走、在哪里停、怎么玩”，而不是只展示字段。

参考：https://about.nike.com/en/newsroom/releases/nike-run-club-app-new-features

## 4. 目标产品形态

### 4.1 新信息架构

专业版编辑器从“三个 tab + 多弹窗”改成“一张地图 + 一个底部编辑抽屉”。

页面主结构：

1. 顶部工具栏
   - 返回
   - 主题名
   - 草稿状态
   - 预览
   - 发布

2. 地图画布
   - 节点 marker
   - 路线 polyline
   - 当前选中节点高亮
   - 空态引导
   - 中心准星模式

3. 地图工具
   - 添加节点
   - 回到路线
   - 撤销
   - 更多

4. 底部抽屉
   - 收起态：节点数、里程、预计时长、游戏数、完整度。
   - 半展开：节点横向 rail、当前节点摘要、主要动作。
   - 全展开：主题/节点/游戏/票务/发布检查。

### 4.2 核心交互

#### 添加节点

推荐流程：

1. 点击“+ 节点”。
2. 地图进入添加模式，显示中心准星和提示“移动地图选择位置”。
3. 用户拖动地图到目标位置，或点击地图 POI。
4. 点“设为节点”。
5. 底部抽屉自动展开到节点编辑。
6. 系统自动填入地点名、地址、经纬度；无法识别地址时显示坐标兜底。

保留辅助入口：

- 从节点列表点“添加到末尾”。
- 从某两个节点之间点“插入节点”。
- 从地图 POI 点“添加为节点”。

#### 编辑节点

推荐流程：

1. 点击地图 marker 或底部节点 rail 的节点。
2. 地图居中到节点。
3. 底部抽屉展开节点编辑。
4. 抽屉内分区：地点、剧情、游戏、奖励。

节点抽屉字段：

- 地点：节点名、地址、图片、适配/营业时间、预计停留时间。
- 剧情：节点描述、到达前提示、完成后文案。
- 游戏：无游戏、快速创建、选择已有、复制已有节点游戏。
- 奖励：积分、徽章、优惠券、完成反馈。

#### 移动节点

不做长按 marker 拖拽，改为准星移动：

1. 点 marker。
2. 点“移动位置”。
3. 地图进入移动模式，准星锁在屏幕中心。
4. 用户拖动地图到新位置。
5. 点“保存位置”。
6. 更新节点经纬度、地址、地图折线、总里程。

原因：

- 微信小程序 map marker 没有稳定通用的拖拽交互能力。
- map 是原生组件，覆盖层和手势竞争容易在真机出问题。
- 中心准星模式在小程序里更稳，也更符合移动端地图选点习惯。

#### 排序节点

推荐放在底部节点 rail 或全展开节点列表：

- 长按节点卡片拖拽排序。
- 支持“移到上一章 / 下一章”。
- 支持“设为起点 / 设为终点”。
- 排序后重算 `sortID`、polyline、总里程。

不要把排序做成地图上拖线。地图用于空间，列表用于顺序，认知更清楚。

#### 预览

必须新增“玩家视角预览”：

- 复用 `pages/play/index` 的游玩呈现逻辑，使用本地草稿数据预览。
- 显示路线、节点锁定规则、游戏启动页、答题/扫码/拍照等状态。
- 发布前能发现“玩家看到什么”和“创作者填了什么”之间的差异。

## 5. 游戏编辑整改方案

### 5.1 新模型：节点内游戏，而不是先模板后节点

用户心智应从：

> 我先创建一个游戏模板，再回主题节点选择模板。

改为：

> 我正在编辑这个节点，这个节点可以有一个玩法。

节点游戏入口：

- 无游戏：纯剧情/打卡节点。
- 快速创建：在节点内创建一个新游戏。
- 选择已有：从我的模板中引用。
- 复制已有：复制其他节点或模板后微调。

### 5.2 快速创建游戏

节点抽屉点“快速创建游戏”后，打开当前抽屉内的二级面板，不跳转页面。

最小字段：

- 游戏名：默认取节点名，可改。
- 完成方式：无需验证、扫码、文字题、选择题、拍照、GPS 到达。
- 问题/答案：按完成方式动态展示。
- 提示：一级提示、二级提示、兜底答案。
- 完成反馈：文字反馈、积分、徽章、优惠券。
- 是否保存为模板：默认关闭，用户需要复用时再打开。

保存行为：

1. 点“保存到节点”。
2. 前端调用 `/api/template/draft` 或新增轻量接口创建私有草稿模板。
3. 返回 `templateId` 后写入当前 `nodesForm.templateId` 和 `templateInfo`。
4. 如果用户打开“保存为模板”，调用 `/api/template/publish` 或将草稿标记为模板库可见。

如果后端不想新增接口，第一版可复用 `/api/template/publish`，但前端文案不要叫“发布游戏”，叫“保存玩法”。后端仍落到 `CmsMemberTemplate`。

### 5.3 模板选择优化

当前“我的模板”是网格列表 + 搜索。建议改成：

- 顶部：搜索、类别筛选、最近使用。
- 模板卡片：标题、完成方式、时长、难度、是否已被其他节点使用。
- 操作：绑定、复制后绑定、预览。
- 空态：没有模板时直接显示“快速创建游戏”，不要只给空列表。

### 5.4 安全与数据原则

- 敏感答案仍不在游玩接口下发，沿用现有 `/api/play/nodes` 只下发展示字段的做法。
- 节点里保存 `templateId`，玩法细节仍由模板表承载，避免大改 topic node 表。
- 新增“节点内临时游戏草稿”也必须归属当前 member，不能让其他用户绑定。
- 删除节点时不默认删除模板，只解除绑定；如果是仅当前节点使用的草稿，可提示“同时删除玩法草稿”。

## 6. UI 设计方向

### 6.1 视觉原则

延续当前城瘾深色地图方向，但专业版编辑器要更像工作台：

- 地图为第一视觉，不再用大块表单压过地图。
- 主色保留城瘾橙 `#FC4C02`，只用于当前节点、路线、主按钮。
- 信息面板用深色半透明或深色实底，避免花哨玻璃拟态影响可读性。
- 控件数量克制：默认只露出下一步动作，高级操作折叠。
- 所有按钮和字段必须能在 iPhone SE 尺寸下完整显示。

### 6.2 关键界面

#### 空态

当前空态是“在路线设置添加站点，路线会显示在这里”。建议改为更直接：

- 地图中心显示准星和“点地图或拖到位置，添加第一个节点”。
- 底部只有一个主按钮“添加第一个节点”。
- 同时提供“从预设路线开始”入口，复用建议版路线能力。

#### 有节点态

地图上：

- 当前节点 marker 用橙色放大。
- 已完成编辑的节点用实心编号。
- 缺信息节点用虚线/空心编号。
- 有游戏节点在 label 或 callout 上加小图标。

底部抽屉：

- 收起：`5 节点 · 2.4km · 约60min · 3游戏 · 完整度82%`
- 半展开：横向节点 rail，节点卡片显示编号、节点名、游戏类型、缺口。
- 全展开：当前节点表单。

#### 发布检查

发布不应该只在最后一屏出现。顶部一直有“发布”，点击后弹发布检查：

- 必填通过：主题名、封面、时间、类别、至少一个节点、每个节点有地点和时长。
- 建议优化：至少 2 个节点、至少 1 个游戏、至少 1 张节点图、已预览玩家视角。
- 风险提示：定位玩法需要位置权限；扫码玩法需要现场码；拍照玩法若人工审核需要运营承接。

## 7. 微信小程序兼容、性能、合规

### 7.1 地图兼容

可用能力：

- `markers`
- `polyline`
- `include-points`
- `bindmarkertap`
- `bindregionchange`
- `bindpoitap`
- `cover-view` / `cover-image`

应避免：

- 依赖 marker 原生拖拽。
- 在地图上覆盖复杂普通 `view` 并指望所有机型层级一致。
- 每次地图移动都高频 setData 全量 markers。
- 一页多个 map 实例。

地图实现建议：

- 只保留一个 map。
- marker 数量超过 30 时只显示关键节点或启用简化模式。
- `regionchange` 只在 end 时更新中心点，不在 begin/drag 中高频刷新。
- polyline 只用节点直连，不做实时路径吸附，避免外部路线 API 和性能成本。

参考 map 能力：https://docs.taro.zone/docs/components/maps/map

### 7.2 位置权限合规

专业版编辑器可以优先使用 `chooseLocation`/`choosePoi` 类选点，不强依赖 `getLocation`。

只有在用户点“定位到我”时才申请位置权限。文案必须说明用途：用于将地图移动到当前位置以便添加主题节点，不用于持续追踪。

如果新增 GPS 到达玩法：

- 游玩页才需要精确定位。
- 需要确认小程序后台“地理位置接口”和隐私保护指引已经覆盖。
- 坐标统一使用 gcj02。

### 7.3 游戏合规

节点内游戏应避免：

- 现金抽奖、随机中奖、博彩式对抗。
- 诱导分享才能过关。
- 未成年人不适内容。
- 需要持续后台定位的玩法。

推荐玩法：

- 到点打卡。
- 扫码验证。
- 文字问答。
- 选择题。
- 拍照任务。
- 收集线索，但第一版可先不做复杂背包系统。

## 8. 数据与接口整改建议

### 8.1 前端数据模型

当前 `chapter.nodes[]` 已包含：

- `name`
- `description`
- `address`
- `longitude`
- `latitude`
- `imgUrl`
- `nodeTime`
- `showTemplate`
- `templateId`
- `templateInfo`
- `businessTime`
- `sortID`

建议补充前端态字段：

- `_localId`：前端临时唯一 id，避免未发布节点排序/编辑错位。
- `_dirty`：是否未保存。
- `_missingFields`：节点缺口，用于 UI 完整度。
- `_selected`：当前选中态。
- `_gameDraft`：节点内临时玩法草稿，保存后转为 `templateId`。

这些字段提交前剥离，不进入后端。

### 8.2 后端最小改动

一次性优化可以不大改后端，优先复用：

- `/api/topic/create`
- `/api/template/publish`
- `/api/template/draft`
- `/api/template/my-list`
- `/api/play/nodes`

建议新增但非强制：

- `POST /api/template/quick-save`：节点内快速保存玩法，返回 `templateId` 和摘要字段。
- `POST /api/template/preview`：不落库，仅返回玩家预览结构。
- `POST /api/topic/preview`：用草稿 topic payload 返回 play-like 预览数据。

如果不新增接口，前端可先本地拼预览数据，发布时仍走 `/api/topic/create`。

## 10. 推荐交付顺序

一次性产品完成，但工程提交建议如下：

1. 地图画布骨架 + 抽屉骨架。
2. marker 点击、准星添加/移动节点。
3. 节点抽屉迁移与节点校验。
4. 节点排序、撤销、完整度。
5. 游戏内联创建与模板绑定。

7. 发布检查、性能和真机 polish。

每一步都可以单独回滚，避免把专业版发布主链路一次性改坏。

## 11. 验收标准

产品验收：

- 新用户能在 3 分钟内创建一个含 2 个节点、1 个游戏的主题。
- 用户不需要离开主题编辑器即可完成节点游戏创建。
- 用户能从地图上理解路线、节点顺序、当前编辑对象。
- 发布前能看到所有缺失项，并能一键定位到对应字段。
- 玩家视角预览能解释“发布后用户怎么玩”。

技术验收：

- 微信开发者工具无编译错误。
- iOS/Android 真机地图无黑屏、无层级遮挡、无明显卡顿。
- `/api/topic/create` 仍兼容旧后端。
- `/api/template/publish` 或 quick-save 返回的 `templateId` 能正确绑定节点。
- 游玩页能正常识别节点模板的 `validationMethod`。
- 不新增不必要的位置权限，不绕过现有 RBAC/roleGuard。

## 12. 最终建议

这次不应该继续在现有 tab 和弹窗上做小修小补。现有能力已经足够支撑一次产品级重构：地图、节点、模板、游玩校验、统计都已存在，真正需要重做的是创作者操作模型。

最佳方向是：

> 专业版主题发布 = 城市路线地图画布 + 节点关卡抽屉 + 节点内游戏快速创建 + 玩家视角预览 + 发布完整度检查。

这会让城瘾从“复杂表单发布工具”变成真正的“城市游戏设计器”。这才符合专业版的定位，也更接近 Strava / Komoot / AllTrails 这类成熟路线产品的低负担编辑体验。
