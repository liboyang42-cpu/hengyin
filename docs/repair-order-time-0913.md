# R9-10：订单时间跨时区一致性

基线 `e9da4017b`；来源为桌面全产品审查第九轮 R9-10。仅本地修复，未发布、未修改数据库。

## 问题与修复

- Jackson 原来使用 JVM 默认时区，使本地洛杉矶服务器把北京时间活动序列化为前一天。现固定 `Asia/Shanghai`，与既有 JDBC `serverTimezone=GMT+8`、小程序 `utils/datetime.js` 的裸时间字符串合同一致。
- `CmsRegistration.paymentTime` 原来只输出日期，现保留 `HH:mm:ss`，取真实支付时间，不生成替代支付记录。
- `formatRefundDeadline` 原来先按北京时间解析，再取设备本地日历字段，造成二次偏移。现复用 `chinaParts`；订单状态、退款资格与截止比较逻辑保持原实现。

## 验证

- 修复前，真实 ApplicationConfig + 实体 Jackson 序列化测试失败：期望 `2026-09-18 02:26:14`，洛杉矶实际 `2026-09-17 11:26:14`。客户端实际格式化函数同样 RED。
- Java 合同测试覆盖洛杉矶、上海、UTC，验证活动/创建/支付时间、精确秒往返及空支付时间；另覆盖主题日期输入和优惠券中国午夜边界。
- Node 三时区测试验证裸字符串、带时区字符串、epoch、空/非法输入与原订单状态；订单、日期及父列表刷新相关 75 项通过。
- 真实订单组件 handler 的受控回包验证：三时区创建及支付时间均显示 `2026-09-13 17:27`，活动日期为 `2026.09.18`。证据 `/tmp/r9-10-time-probe/client-handler-green.json`。这不是原生截图或真实支付证据。
- DeepSeek 通过 Orca/OpenCode 独立只读复核，实际重跑 Node 15 项通过，确认三处修复符合合同；报告 `/tmp/cy-order-time-independent-review.md`。Java 由总控单独运行，不能归为复核方执行。

## 影响边界

JSON 时区是全局配置，不限订单：无显式 timezone 的日期序列化和反序列化均受影响。北京时间 JVM 的现代业务日期语义保持一致；非北京时间 JVM 从当地墙钟改为项目规定的北京时间。本次增加跨日期输入/输出检查，不据此声称所有实体已逐一验收。

手工创建的 ObjectMapper 不受 Spring customizer 管理；独立报告列出的相关调用未逐项验证，本次不顺手替换它们。历史已丢失的支付时分秒不能从旧缓存或日期字符串补造；修复后的新接口从数据库 Date 返回完整时间。
