# 城市定向分支剧情开源方案调研

- 调研日期：2026-08-23
- 调研目标：回答“模板里的选项或节点结果，能否改变城市定向下一站并解锁不同地点”，并从成熟开源互动叙事项目中提炼可复用的节点、选择、条件、副作用、随机、存档和校验设计。
- 方法：只采信项目官方仓库、官方文档、规范和源码；不把社区教程当作实现依据。
- 边界：本文研究架构与产品方案，不代表任何业务代码、数据库迁移或线上配置已经实现。
- 执行清单：[城市定向分支剧情路线 TODO](../design/城市定向分支剧情路线TODO_2026-08-23.md)

## 一、结论先行

可以做，而且不应把它理解为“把现有地点列表随机打乱”。更成熟、也更适合城市定向的模型是：

> **把主题从固定数组升级为带状态的有向剧情图；玩家完成当前节点后，由服务端根据“所选选项 + 实际验证结果 + 已积累状态”筛选下一站候选，再按优先级或带种子的权重随机选出下一站。**

核心不是随机，而是这条稳定决策链：

```text
当前节点完成
  → 验证这次选择/答题/GPS/扫码结果可信
  → 应用选项副作用（设置变量、加标签、拿道具、加减数值）
  → 过滤满足条件的下一站
  → 最高优先级候选中固定选择或权重随机
  → 服务端保存“为什么解锁了这个地点”
  → 小程序只展示服务端已解锁的下一站
```

开源项目给出的共识很一致：

1. **节点和地点分开**：叙事节点负责内容与决策，地点只是节点可绑定的现实资源；同一地点可以承载不同剧情节点，汇合节点也可以没有新地点。
2. **Choice 至少包含条件、效果和目标**：按钮不是只存文案，点击时既改变状态，也决定或参与决定下一节点。
3. **随机必须可重放**：保存 seed、抽取次数和最终选中项，不能刷新页面就换一条路线。
4. **存档保存“状态 + 当前指针 + 已走历史”，模板保存静态图**：发布后正在进行的局使用配置快照，避免作者改模板把玩家卡死。
5. **发布前要验证图，发布后要模拟跑图**：查悬空目标、不可达节点、无出口状态、无终点、无限环、条件类型错误；对随机线做成千上万次可复现遍历。

推荐城瘾采用“**Ink/Yarn 的运行时与状态思想 + Twine 的图形编辑体验 + ChoiceScript 的随机线路测试**”，但不直接把这些浏览器/Unity/Python 引擎塞进 Java 后端或小程序。

## 二、成熟开源项目是怎么做的

### 2.1 Ink：把内容编译成可执行故事，选择会修改状态并 divert 到不同节点

Ink 用 `knot/stitch` 表示层级剧情节点，用 choice + divert（`-> target`）表示边。不同选择可去不同目标，也可以在后面汇流；choice 前可以放变量或访问历史条件，不满足条件的选择不会进入当前合法选项集合。[knot/stitch](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/WritingWithInk.md#L202-L226)、[分支与汇流](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/WritingWithInk.md#L301-L355)、[条件选项](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/WritingWithInk.md#L543-L592)

divert 目标也能存入变量，因此可以把“选项或结果先算出 `next_stop`，再经公共出口跳往该地点”写成数据驱动流程。`TURNS_SINCE` 和 visit count 可表达“访问过才解锁”“若干回合后重开”“同一地点不重复”。[动态 divert](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/WritingWithInk.md#L1263-L1279)、[访问与回合状态](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/WritingWithInk.md#L793-L830)

随机方面，Ink 支持 stopping/cycle/once/shuffle 序列和 `RANDOM(min,max)`。`SEED_RANDOM` 能固定随机序列；运行时保存 `storySeed` 与 `previousRandom`，恢复后继续同一条随机轨迹。Ink 没有独立 weighted-edge 原语，如要权重需以整数区间或宿主侧选择表达，不能把“支持随机”误写成“原生支持带权边”。[序列与 shuffle](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/WritingWithInk.md#L618-L681)、[`RANDOM`](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/WritingWithInk.md#L1350-L1355)、[随机实现源码](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/ink-engine-runtime/Story.cs#L1484-L1528)

Ink 的存档不是只记“当前章节”：`state.ToJson()`/`LoadJson()` 会保存 flow/call stack、当前 choices、变量、访问次数、turn index 和随机状态。[存档接口](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/RunningYourInk.md#L77-L99)、[StoryState 序列化字段](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/ink-engine-runtime/StoryState.cs#L654-L700)

安全边界也很清楚：正常运行时只接受 `currentChoices` 中的合法索引，再恢复该 choice 生成时的上下文并跳到真实 target；任意路径跳转 API 会重置 call stack，源码明确提示可能危险。这正支持城瘾采用“客户端提交节点玩法的原始选择，服务端校验并生成稳定 outcome，再重算合法 target”，而不是接收客户端自报的剧情结果或下一站。[`ChooseChoiceIndex`](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/ink-engine-runtime/Story.cs#L1790-L1809)、[`ChoosePathString` 风险](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/ink-engine-runtime/Story.cs#L1729-L1767)

Ink 还允许用 `EXTERNAL` 接入宿主业务，但官方文档专门区分纯查询和带副作用 action，因为引擎可能预读内容。城瘾应同样把“店铺是否营业、是否有角色、当前分数”等做纯 condition，把解锁、加线索、发奖励放到最终提交事务里。[EXTERNAL 与 lookahead safety](https://github.com/inkle/ink/blob/35c63e52f1d36060930dc7ed3cfba38ea224b528/Documentation/RunningYourInk.md#L268-L334)

### 2.2 Yarn Spinner：节点图 + 选项条件 + 命令/变量存储，宿主应用负责现实世界动作

Yarn Spinner 的 node 可以携带地点等 header；options 可以嵌套，`<<jump Target>>` 让不同选择直达不同节点。条件选项为 false 时仍会传给宿主，但带 unavailable 标志，宿主可选择隐藏或禁用；全部不可用时可提供 fallback。[节点](https://yarnspinner.dev/docs/yarn/02-fundamentals/01-lines-nodes-and-options/)、[选项](https://yarnspinner.dev/docs/yarn/02-fundamentals/02-options/)、[Jump](https://yarnspinner.dev/docs/yarn/02-fundamentals/03-jumps/)、[Flow Control](https://yarnspinner.dev/docs/yarn/02-fundamentals/06-flow-control/)

除了显式选项，Yarn 的 Node Groups 更像“地点候选池”：多个同名内容各带 `when:` 条件，Saliency 先过滤合格候选，再从中选择。内建策略包括 First、Best、Best Least Recently Viewed、Random Best Least Recently Viewed，默认是最后一种；官方还给出 weighted saliency 示例，先去掉条件失败项，再按 weight 随机。这一模型非常适合“先排除未营业、已玩过、不适合当前角色的 POI，再从剩余地点择优或抽签”。[Node Groups](https://yarnspinner.dev/docs/yarn/03-advanced/01-node-groups/)、[Saliency](https://yarnspinner.dev/docs/yarn/03-advanced/03-saliency/)、[官方 Weighted Saliency 示例](https://github.com/YarnSpinnerTool/YSDocs/blob/main/docs/yarn-spinner-for-unity/samples/storylets-and-saliency/custom-saliency-strategies.md)

Saliency 特意把只读 `QueryBestContent` 与会改变访问状态的 `ContentWasSelected` 分开。映射到城瘾就是：

- `GET state/options` 只解释哪些地点合格，不抽签、不增加访问次数；
- `POST choose` 才确认选择或随机结果，并用 CAS 原子落库。

Yarn 的 functions 适合纯查询，commands 用于向宿主发动作。城瘾可把 `isShopOpen`、`hasRole`、`score` 做白名单纯函数，把 `unlockNode`、`grantClue`、`setFlag` 做提交期 effect。[Functions](https://yarnspinner.dev/docs/yarn/02-fundamentals/11-functions/)、[Commands](https://yarnspinner.dev/docs/yarn/02-fundamentals/10-commands/)

变量、`visited()`/`visited_count()`、`random()`/`random_range()`/`dice()` 足以表达结果条件与随机路线；官方 FAQ 建议存 current node 与 variables，并允许替换变量存储。源码中的 VM 保存当前 node/指令状态，生成带 enabled 与 destination 的 options，并只在提交选项后跳转。[变量与逻辑](https://yarnspinner.dev/docs/yarn/02-fundamentals/05-logic-and-variables/)、[Functions](https://yarnspinner.dev/docs/yarn/02-fundamentals/11-functions/)、[状态保存 FAQ](https://yarnspinner.dev/docs/faq/)、[`VirtualMachine.cs`](https://github.com/YarnSpinnerTool/YarnSpinner/blob/ec1a680fae4c0fc8aae73b23c7b87f3e5f894100/YarnSpinner/VirtualMachine.cs)

校验边界不能高估：编译错误会让 `CompilationResult.Program=null` 并返回 Diagnostics，但用于检查软锁、不可达线路等问题的 Story Solver 仍是 Coming Soon/closed alpha。因此城瘾必须自己实现图可达性、无出口状态和随机模拟门禁。[Compilation Diagnostics](https://docs.yarnspinner.dev/api/csharp/yarn.compiler/yarn.compiler.compilationresult/yarn.compiler.compilationresult.diagnostics)、[Story Solver 当前状态](https://www.yarnspinner.dev/storysolver)

### 2.3 Twine + SugarCube/Harlowe：最值得借的是可视化剧情图和“点击时改状态再跳转”

Twine 本身主要是非线性故事编辑器：一个故事由多个 passage（节点）组成，链接在 Story Map 中显示为有向线；找不到目标 passage 时显示红色断链。官方文档还明确说明，条件、变量等运行能力由 story format 提供，而不是 Twine 编辑器本身。[Twine 基本概念](https://twinery.org/reference/en/getting-started/basic-concepts.html)、[链接 passage](https://twinery.org/reference/en/editing-stories/linking-passages.html)、[Story Map 与 broken links](https://play.twinery.org/reference/en/editing-stories/navigating.html)

这对城瘾最有价值的不是 HTML 输出，而是编辑器形态：

- 地点/剧情节点显示为卡片；
- 下一站关系显示为箭头；
- 条件关系可显示为虚线或带条件标签的边；
- 悬空目标直接红线；
- 改节点名或删除节点时能立即看到受影响的线路。

SugarCube 负责更完整的状态机。官方文档中：`<<link ... passage>>` 可以在点击后先执行内容再跳往 passage；`<<set>>` 修改 story variable；`<<if>>` 控制哪些选项或内容可见。story variable 会进入历史，每次 passage 跳转创建一个包含当前 passage 和全部 story variables 的 moment。[`<<link>>`](https://www.motoslave.net/sugarcube/2/docs/#macros-macro-link)、[`<<set>>`](https://www.motoslave.net/sugarcube/2/docs/#macros-macro-set)、[`<<if>>`](https://www.motoslave.net/sugarcube/2/docs/#macros-macro-if)、[Story History](https://www.motoslave.net/sugarcube/2/docs/#guide-tips-story-history)

SugarCube 的另一个关键做法是可重放随机：`State.prng.init()` 把 seedable PRNG 集成进 story state 和 saves，seed 与 pull count 都进入存档；同一存档恢复后不会因为刷新而重新抽到别的结果。[Seedable PRNG](https://www.motoslave.net/sugarcube/2/docs/#state-api-method-prng-init)、[Playthrough Session](https://www.motoslave.net/sugarcube/2/docs/#guide-tips-playthrough-sessions)

Harlowe 的语法更适合给非程序作者解释“选项改状态再跳转”：`(link-reveal-goto:)` 会在跳转前执行 `(set:)`；`(if:)`/`(else-if:)` 控制条件内容；`(either:)` 可随机选择一个目标 passage；`(history:)` 返回已经访问过的 passage 列表；`(save-game:)` 保存当前游戏。[选择效果与跳转](https://twine2.neocities.org/#macro_link-reveal-goto)、[条件](https://twine2.neocities.org/#macro_if)、[随机目标](https://twine2.neocities.org/#macro_either)、[访问历史](https://twine2.neocities.org/#macro_history)、[存档](https://twine2.neocities.org/#macro_save-game)

映射到城瘾：

```text
passage              → 主题剧情节点
link / link-goto     → 选项或结果边
story variable       → 本局剧情变量
set                  → 选项效果
if                   → 解锁条件
either / seeded PRNG → 候选下一站中的可复现随机
history              → visitedNodeIds / completedNodeIds
moment / save        → 服务端 game session 状态
```

需要明确的边界：Twine/SugarCube/Harlowe 默认是浏览器端故事运行时，浏览器本地存档不适合作为城瘾的权威进度。GPS、扫码、付费权益、奖励和下一站解锁仍必须由 Java 服务端判定，小程序不能提交一个任意 `targetNodeId` 就完成跳转。

### 2.4 ChoiceScript：最接近“条件地点池中随机下一站”，并且有自动跑图工具

ChoiceScript 用 `*choice` 定义选择，以缩进块描述该选择的结果；`*set` 改变量，`*if` 根据此前选择形成的状态改变剧情，`*goto`/`*goto_scene` 跳转到标签或场景。其官方入门文档明确用“早期选择改变 leadership，后来条件分支读取 leadership”解释跨场景状态。[ChoiceScript 官方文档源码](https://github.com/dfabulich/choicescript/blob/main/doc/index.html)

更重要的是，运行时源码已经实现了 `*goto_random_scene`：

1. 解析候选场景及每个候选的 `*if` 条件；
2. 排除已经使用、且未声明 `allow_reuse` 的场景；
3. 从通过条件的候选中随机选一个；
4. 没有候选时默认报 `No selectable scenes`，只有显式 `allow_no_selection` 才允许空结果；
5. 选中后把场景名记入状态，防止后续重复。

这几乎就是城市定向“从当前已解锁地点池里随机下一站”的原型。当前源码还留有 `TODO weights`，说明其主线实现是等概率随机；城瘾可以在此基础上增加权重，但不能照搬源码后假定它已有权重能力。[`goto_random_scene` 源码](https://github.com/dfabulich/choicescript/blob/main/web/scene.js#L4412-L4542)

ChoiceScript 最值得直接借鉴的是验证体系：Quicktest 会发现缺失场景、缩进/语法错误，并收集 `goto_scene`/`gosub_scene` 指向；Randomtest 接受 iteration 和 seed，多次随机跑完整故事、统计行覆盖率，遇到异常输出 `RANDOMTEST FAILED`。[Quicktest 源码](https://github.com/dfabulich/choicescript/blob/main/quicktest.html)、[Randomtest 源码](https://github.com/dfabulich/choicescript/blob/main/randomtest.js)、[Randomtest 页面默认参数](https://github.com/dfabulich/choicescript/blob/main/randomtest.html)

许可边界也要注意：ChoiceScript 仓库使用自定义 CSL，非商业使用才免费，商业使用需联系授权。因此这里适合借测试思想和数据模型，**不应把其解释器源码直接并入商业项目**。[ChoiceScript LICENSE](https://github.com/dfabulich/choicescript/blob/main/LICENSE.txt)

### 2.5 Quest：地点本身是世界模型对象，出口可以锁定、动态创建或随机选择

Quest 比纯分支故事更偏“世界模拟”。它把房间、出口、命令和游戏都视为 WorldModel element；普通对象的字段在游戏中可改变，WorldModel 维护变化、Undo，并复用同一套 save/load 机制。[Quest 开发者文档](https://docs.textadventures.co.uk/quest/developers.html)

对城市定向有直接启发的机制有：

- 地点是 room，路线是 exit；出口有 `to` 目标，并可锁定/解锁；运行时还能创建单向或双向出口；
- `ShowMenu` 显示选择，选择结果进入后续 script；对象 attribute 保存世界状态，attribute change script 可响应变化；
- `PickOneExit`/`PickOneUnlockedExit` 从当前房间出口中随机选择；`RandomChance`、`PickOneString/Object` 提供其他随机方式；
- Quest 的原生存档保存整个已修改的世界，因此升级内容时旧存档仍是旧世界，这反向说明城瘾更应保存“模板版本快照 + 最小运行状态”，而非把整份模板复制成任意对象图。

来源：[Exits](https://docs.textadventures.co.uk/quest/exits.html)、[Attributes](https://docs.textadventures.co.uk/quest/attributes.html)、[Blocks and scripts / ShowMenu](https://docs.textadventures.co.uk/quest/blocks_and_scripts.html)、[Randomisation](https://docs.textadventures.co.uk/quest/random.html)、[When the Player Saves a Game](https://docs.textadventures.co.uk/quest/about_save.html)、[官方 GitHub](https://github.com/textadventures/quest)

Quest 证明“地点图”和“剧情状态机”可以结合，但整套世界模型、脚本语言和编辑器远超城瘾当前所需。更合适的做法是吸收 room/exit/attribute 概念，不引入其引擎。

### 2.6 Adventurelib：可借地点图，不能作为分支剧情引擎

Adventurelib 的 `Room` 可以通过方向建立双向关系，`room.exit(direction)` 查询出口；任意属性和 Python `if` 可表达条件，command context 可按游戏状态隐藏或启用命令。但官方文档同时明确：它不跟踪玩家当前所在房间，状态、规则和故事推进都由开发者自己写。[Rooms](https://adventurelib.readthedocs.io/en/stable/rooms.html)、[Command Contexts](https://adventurelib.readthedocs.io/en/stable/commands.html)、[官方 GitHub](https://github.com/lordmauve/adventurelib)

因此 Adventurelib 适合作为“地点是节点、出口是边”的极简教学参考，不具备城瘾需要的模板 DSL、服务端存档、发布校验和随机跑图能力，不应列为主方案。

## 三、横向比较

| 项目 | 节点/边模型 | 条件与效果 | 随机 | 存档/历史 | 校验能力 | 对城瘾的价值 |
|---|---|---|---|---|---|---|
| Ink | 编译后的 story/knot/stitch/choice/divert | 变量、表达式、选择副作用 | 序列/洗牌等 | 可序列化 StoryState | 编译器错误/警告与测试 | 最适合参考运行时语义和可重放状态 |
| Yarn Spinner | node、option、jump/command | 条件、变量、命令与宿主回调 | 运行时/命令扩展 | VariableStorage 与运行状态 | 编译诊断、节点图/调试工具 | 最适合“剧情决定，宿主执行 GPS/地图”等边界 |
| Twine + SugarCube/Harlowe | passage + link 有向图 | set/if + 点击后跳转 | either 或 seeded PRNG | passage history + variables + saves | Story Map 断链；运行时校验较弱 | 最适合参考创作者图形编辑体验 |
| ChoiceScript | scene/label + choice/goto | set/if；候选可有条件 | 条件池过滤、默认不重复后随机 | stats + 已用场景 | Quicktest + seeded Randomtest/coverage | 最适合参考发布前随机线路自动跑图 |
| Quest | room/object + exit | attribute + script/menu | 随机出口/对象/概率 | 整个可变 WorldModel | 类型/脚本测试 | 适合参考现实地点与动态出口 |
| Adventurelib | Room + direction/exit | Python if/context | 需自行写 | 需自行写 | 无故事图校验 | 只作极简地点图参考 |

## 四、城瘾模板应如何改变

### 4.1 不改“节点内容真源”，新增主题级路线图

现有节点继续负责地点、故事、题目、GPS/扫码/文字/选项验证。主题模板只新增“节点之间怎么走”的图，不复制节点内容和答案。

建议最小 schema：

```json
{
  "schemaVersion": 1,
  "startNodeId": 101,
  "routeMode": "BRANCH_GRAPH",
  "variables": {
    "routeStyle": { "type": "STRING", "default": "UNKNOWN" },
    "clue": { "type": "INT", "default": 0 }
  },
  "edges": [
    {
      "id": "e_start_history",
      "fromNodeId": 101,
      "trigger": { "type": "CHOICE", "outcomeCode": "HISTORY" },
      "conditions": [],
      "effects": [
        { "op": "SET", "var": "routeStyle", "value": "HISTORY" },
        { "op": "INC", "var": "clue", "value": 1 }
      ],
      "toNodeId": 203,
      "priority": 100,
      "weight": 1,
      "once": true
    },
    {
      "id": "e_start_art",
      "fromNodeId": 101,
      "trigger": { "type": "CHOICE", "outcomeCode": "ART" },
      "conditions": [],
      "effects": [
        { "op": "SET", "var": "routeStyle", "value": "ART" }
      ],
      "toNodeId": 305,
      "priority": 100,
      "weight": 1,
      "once": true
    },
    {
      "id": "e_result_recovery",
      "fromNodeId": 203,
      "trigger": { "type": "ADVANCED_RESULT", "outcomeCode": "ASSISTED" },
      "conditions": [
        { "var": "clue", "op": "LT", "value": 2 }
      ],
      "effects": [],
      "toNodeId": 207,
      "priority": 200,
      "weight": 1,
      "once": true
    }
  ],
  "fallbacks": [
    { "fromNodeId": 101, "toNodeId": 102 },
    { "fromNodeId": 203, "toNodeId": 204 }
  ],
  "terminalNodeIds": [999]
}
```

这里有三个刻意设计：

1. `trigger` 区分玩家主动选项和客观验证结果，避免把“答错”伪装成一个选项；
2. `effects` 只允许白名单操作，不保存 JavaScript、SpEL 或任意脚本；
3. `fallbacks` 保证旧线性主题或意外无候选时仍有安全下一站。

### 4.2 模板编辑器里怎么让作者配置

不需要新增一个独立产品入口。在现有主题/模板节点编辑流程中，每个节点增加“完成后路线”卡：

- `按原顺序`：兼容所有旧主题，等同当前行为；
- `按玩家选项分支`：每个选项选择一个目标节点，并可设置变量效果；
- `按验证结果分支`：正确、使用提示、查看答案、GPS/扫码成功等结果指向不同目标；
- `从条件地点池选择`：为多个候选配置条件、优先级、权重、是否允许重复；
- `结束主题`：明确终点，不再推断“列表最后一个就是结束”。

页面内同时提供一个只读缩略图：节点卡 + 路线箭头 + 条件标签。点击“全屏查看路线图”可以是编辑器辅助视图，但配置真源仍在原模板节点中，避免同一条边在两个页面分别维护。

### 4.3 服务端如何决定下一站

小程序完成请求只提交本次玩法所需的原始输入与路线并发上下文，不直接声明剧情结果或下一站：

```json
{
  "sessionId": 7788,
  "nodeId": 101,
  "choices": { "routeStyle": "history" },
  "routeActionId": "client-generated-idempotency-key",
  "expectedRouteVersion": 7
}
```

服务端先用现有玩法规则把原始输入转换成可信 `NodeOutcome`，再进入路线引擎。客户端不能提交 `outcomeCode` 或 `targetNodeId`。

服务端执行：

1. 读该局冻结的模板快照和权威 `state`；
2. 校验 `nodeId` 就是当前可操作节点、选项确实属于该节点、验证回执有效且未用过；
3. 以 `routeActionId` 做幂等，防双击和断网重试重复生效；
4. 在内存副本中应用 effects；
5. 过滤 `fromNodeId` 匹配、trigger 匹配、conditions 为真、once/访问次数允许的边；
6. 先取最高 `priority` 层，再按 `weight` 选一条；普通分支只有一条时无需随机；
7. 随机源使用会话 seed，并保存 RNG pull/抽取结果；
8. 用 `version` CAS 一次性保存变量、历史、已选 edge、下一节点和决策原因；
9. 返回服务端已解锁节点，小程序不能覆盖 `toNodeId`。

建议状态最小集：

```json
{
  "currentNodeId": 203,
  "unlockedNodeIds": [203],
  "completedNodeIds": [101],
  "visitedNodeIds": [101, 203],
  "takenChoiceIds": ["history"],
  "usedEdgeIds": ["e_start_history"],
  "variables": { "routeStyle": "HISTORY", "clue": 1 },
  "rng": { "seed": "session-7788", "pull": 0 },
  "decisionLog": [
    {
      "from": 101,
      "edgeId": "e_start_history",
      "to": 203,
      "reason": "choice=history",
      "at": "..."
    }
  ],
  "version": 8
}
```

`decisionLog` 对客服、作者调试和争议处理非常重要：能回答玩家为何没解锁某地点，而不是只看到最终 `currentNodeId`。

## 五、随机剧情应怎样设计，才不会变成失控的随机

### 5.1 四种路由强度

建议从确定性到随机逐步开放：

1. **显式选择分支**：玩家选 A 去地点 A，选 B 去地点 B；最容易理解和测试。
2. **结果分支**：答题正确走捷径，提示/看答案走补线索地点；注意不能用失败分支惩罚到无法完赛。
3. **状态条件分支**：持有道具、累计线索、访问过某点、队伍角色、当前时段等决定候选。
4. **条件池内权重随机**：先排除不合法地点，再随机；不能从全主题节点盲抽。

V1 最适合先做 1 + 2，并让 3 只支持少量白名单变量；4 等编辑器校验和模拟器成熟后再开放给普通作者。

### 5.2 城市现实约束要先于叙事随机

候选下一站除了剧情条件，还必须通过现实约束：

- 该节点当前可用、未删除、未下架；
- 对当前活动/票种/角色可见；
- 营业时段允许，或有明确的关闭时 fallback；
- 与当前位置的距离不超过模板上限；
- 不要求玩家穿越不可达区域；
- GPS/扫码/到店等真实验证不能因剧情分支被绕过；
- 奖励、积分、商家权益继续走原有幂等发放链路。

换言之，剧情引擎只提出“叙事上可去哪些点”，业务规则再决定“现实中此刻哪些点真能去”。

## 六、发布前必须做的图校验与随机跑图

### 6.1 静态校验

- `startNodeId` 和全部 `toNodeId` 必须存在且属于同一主题；
- edge id、choice id 在作用域内唯一；choice id 必须是源节点真实存在的选项；
- 变量先声明再使用，类型与比较操作匹配；effects 的目标变量和 value 类型匹配；
- weight 为正整数并有上限，priority 为受限整数；
- 每个非终点至少有一个无条件 fallback，或能够证明所有状态下都有候选；
- 从起点至少能到一个终点；所有可发布节点均可达，或被明确标成隐藏彩蛋；
- 环路必须显式 `allowLoop=true` 并设置 `maxVisits`，否则拒绝发布；
- terminal 节点不能仍配置普通下一站；
- 不允许 effect 修改服务端保留字段、奖励余额、owner、权限或验证结果。

### 6.2 路径模拟

借 ChoiceScript 的 Quicktest/Randomtest 思路分两层：

- **穷举显式选择**：每个 choice 至少被走一次，验证所有目标、effects 和汇合点；
- **种子随机模拟**：用固定 seed 跑 1,000–10,000 局，统计节点/边覆盖率、平均路长、最短/最长路长、终点分布、无候选次数、重复地点次数。

发布门禁至少应为：

```text
悬空目标 = 0
无候选死锁 = 0
无终点模拟 = 0
非预期无限环 = 0
所有普通 edge 覆盖 > 0
总步行距离和节点数都在模板约束内
```

还要做负控：故意把一个目标节点删掉，应出现“悬空目标”；故意让一个条件池全部为 false 且无 fallback，应出现“无候选死锁”；把终点唯一入口条件改成永假，应出现“终点不可达”。只有这些红灯真的会红，发布校验的绿才可信。

## 七、建议的实施顺序

### V1：确定性分支，先把“选择改变下一站”做实

- 旧主题保持 `LINEAR`，零迁移即可继续玩；
- 新增 `BRANCH_GRAPH`，支持 choice/result → target；
- 支持 `SET`、`INC`、`ADD_TAG` 三种 effect 和等值/数值/已完成条件；
- 每个分支节点强制 fallback；
- 服务端权威决定下一站，保存配置快照、状态、CAS version、幂等 actionId 和 decision log；
- 编辑器显示路线图和静态校验；
- 做一条“两分一合”的官方主题负控试跑。

### V2：条件地点池与可重放随机

- 增加 priority、weight、once、maxVisits；
- 增加 seed/pull 和随机决定回放；
- 上线 Randomtest 式批量模拟与覆盖率报告；
- 加营业时间、距离等现实候选过滤和安全 fallback。

### V3：叙事工具完善

- 变量面板、道具/标签、分支模板、子图复用；
- 作者预览任意状态，查看“为何这条边不可用”；
- 版本迁移策略和旧存档兼容；
- 数据分析按 edge/choice/终点统计路线偏好与卡点。

## 八、不建议做的方案

1. **每次完成节点后直接 shuffle 剩余地点**：没有剧情因果，可能路线折返、商家关闭、绕过必做节点，也无法向玩家解释为何解锁。
2. **把 `condition` 存成任意 JavaScript/SpEL**：安全、兼容、可测试性都不可控；应使用受限 JSON DSL。
3. **由小程序计算并上报目标节点**：客户端可篡改，离线重试还可能产生双重奖励；客户端只报 choice/result receipt。
4. **只存当前节点，不存变量与历史**：无法恢复、无法判 once、无法解释路线，也不能稳定随机。
5. **直接嵌入 Twine/Ink/Quest 整个运行时**：它们的宿主、许可、存档和安全假设不同；城瘾真正需要的是一小段可审计的服务端路由内核。
