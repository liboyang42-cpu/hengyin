## 1. 结论先行

这个方向值得做，但不要把它收窄成“店铺上传一张 AI 头像”。真正能改变店铺装修和漫游体验的产品模型是：

> **每家店拥有一个可被发现的“城市分身”，分身驻守在经过核验的店铺主点位，并通过附近的故事点、任务点和彩蛋点与玩家发生事件。**

它把目前彼此分散的四类能力连成一条线：

```text
店铺品牌资料
  → 生成有一致视觉与性格的城市分身
  → 分身驻守真实门店主点位
  → 商家配置少量卫星点位和触发事件
  → 玩家在地图发现／靠近／到达／完成
  → 分身回应、发线索、留下收藏或引出下一站
  → 店铺获得可验证到访、内容互动和复访
```

建议的产品命名：

- 面向商家配置：**店铺城市分身**；名称清楚，不会让商家误解成全自动客服。
- 面向玩家展示：可以测试更有情绪的名称，如 **店灵**、**守店人**、**城市角色**。
- 内部技术模型：继续使用 `Merchant NPC`／`npc_profile scope_type=2`，避免为了营销名称重造领域模型。

最重要的设计判断有五个：

1. **角色不是装饰，是入口。** 玩家点击头像后要能听故事、接任务、查看营业和前往，而不是只看一张 AI 图。
2. **地图类别与任务状态必须分开编码。** “餐厅／好玩／故事／彩蛋”回答这是什么；“未发现／可行动／已完成／暂停”回答现在能做什么，不能混成一套颜色。
3. **商家不能无限撒点。** 一家店只有一个经核验的主点位，首发最多增加 3 个卫星点位；超范围、公共安全和跨商家点位必须审核。
4. **AI 默认预生成，运行时只在明确入口对话。** 地图气泡、到店欢迎、任务提示优先使用审核后的缓存话术；不能让每次靠近都发起自由 LLM 请求。
5. **漫游保持统一暗色，只切换信息状态。** 平时发现附近店铺时采用头像化、卡片化的信息层级；进入任务后减少发现信息、强化当前目标与玩法状态。两者共享现有黑白 Play 语言，不切成浅色地图，也不复制第二套地图页面。

## 2. 用户参考图值得借什么

参考图的右屏不是传统导航地图，而是一张“附近的人和场所”关系图。它的价值不在底图本身，而在以下信息层级：

### 2.1 值得采用

1. **头像直接成为 marker。** 人、组织或店铺先以面孔被识别，再补地点名称；比统一 pin 更有情绪记忆。
2. **选中后只出现一张悬浮地点卡。** 地图保持可见，卡片提供名称、短描述、参与人数、图片和主要动作，不急着跳详情页。
3. **视觉层级轻。** 参考其“低噪底图、单张选中卡、marker 与道路信息不争抢”的层级关系；城瘾应翻译为现有暗色底图、实色深色浮层与白色高对比文字，而不是沿用浅色皮肤。
4. **搜索、筛选和当前位置都悬浮在地图上。** 用户能随时改变发现意图，不需要离开地图。
5. **地图和列表是同一批内容的两种表达。** 左屏的附近列表与右屏地图应共享筛选、排序和选中状态。

### 2.2 不能直接照搬

1. 图中头像适合展示少量“人”，但城瘾同一区域可能同时有商家、任务、故事和彩蛋；全部用头像会迅速失去分类能力。
2. 图中地图主要用于发现和社交，缺少未发现、可行动、已完成、暂停等游戏状态；危险点应被阻断发布，不应成为可见玩法状态。
3. 大头像暴露精确实时位置时有隐私风险。城瘾应显示店铺分身的固定驻点，不默认显示玩家或商家的实时位置。
4. 普通地图底图 POI 已很密，如果再叠加所有城瘾点位，会出现文字、图标和卡片三层冲突；必须主动隐藏非必要底图 POI。

因此推荐的组合不是“全图头像”，而是：

```text
店铺主点位      → 圆形城市分身头像
餐厅／体验点    → 带类别图标的品牌 marker
故事／任务点    → 书页／旗帜等功能 marker
未揭晓彩蛋      → 微光／问号，不显示完整内容
当前选中点      → 放大头像或图标 + 单张悬浮卡
```

## 4. 城瘾建议产品模型

### 4.1 一家店不是一个 POI，而是一个微型世界

每家参与商户由五层组成：

| 层 | 回答的问题 | 例子 |
|---|---|---|
| 身份层 | 我是谁 | 山丘咖啡的店灵“豆丘”、深夜补给站守店人 |
| 事实层 | 我在哪里、什么时候可用 | 核验店址、营业时间、服务标签、活动状态 |
| 叙事层 | 为什么值得来 | 店史、街区关系、老板故事、空间细节 |
| 玩法层 | 玩家到这里能做什么 | 找隐藏菜单、观察墙面符号、拍照、答题、扫码 |
| 关系层 | 完成后发生什么 | 获得章、解锁下一站、记住到访、开启回访彩蛋 |

店铺装修页不应继续堆字段，而应把这五层组织成三个用户能理解的入口：

1. **我的城市分身**：形象、人设、口吻、欢迎语、知识和预览。
2. **我的地图据点**：主店位置、卫星点位、开放时段和审核状态。
3. **玩家来店里能玩什么**：故事、任务、彩蛋、奖励和复访触发。

### 4.2 城市分身的最小配置

首发建议让商家完成一个 5 步向导，而不是面对 Prompt 输入框：

#### 第 1 步：选择角色原型

- 守店人：温暖接待、讲店铺故事。
- 向导：推荐附近路线和店内体验。
- 收藏家：用印章、物件和隐藏细节引导探索。
- 谜语家：负责暗号、线索和剧情。
- 补给官：突出休息、餐饮、权益和活动服务。

角色原型只决定默认信息结构和触发事件，商家仍可改名称和文案。

#### 第 2 步：生成视觉形象

输入只使用商家已经拥有或明确授权的素材：Logo、门头、代表产品、品牌色、品牌故事。输出建议固定为：

- 1 张头像：地图主 marker 和聊天头像；
- 1 张半身像：地点卡／店铺主页；
- 3 个状态：欢迎、发现彩蛋、完成任务；
- 1 组安全区与裁切预览：地图 48px、卡片 96px、详情 240px。

商家从 3 个方向中选 1 个，再做有限修改。禁止上传无授权真人照片生成近似形象；涉及真实店主时必须明确选择“本人授权形象”。

#### 第 3 步：确定性格与口吻

不使用十几个抽象滑杆。只让商家选择：

- 语气：温暖／幽默／神秘／专业；
- 句子长度：简短／正常；
- 主动程度：安静守候／适时提醒；
- 禁止事项：不讲折扣、不评价竞品、不承诺库存等。

系统生成欢迎语、靠近提示、到店话术和完成话术；商家逐条预览并提交审核。

#### 第 4 步：绑定可信知识

知识按风险分层：

| 级别 | 内容 | 回答方式 |
|---|---|---|
| A 权威事实 | 店名、地址、营业、审核通过的菜单／服务、活动规则 | 只读服务端当前事实，可直接回答 |
| B 商家故事 | 品牌故事、空间细节、创始经历 | 使用已审核文本检索回答 |
| C 玩法内容 | 当前线索、任务、提示、彩蛋 | 按玩家状态和解锁条件回答 |
| D 禁止自由回答 | 价格承诺、库存保证、食品过敏、医疗／法律、竞品评价 | 引导查看官方信息或联系商家 |

#### 第 5 步：预览触发事件

至少预览五种状态：地图初见、进入附近范围、到达店门、任务完成、再次来访。商家确认后进入审核；审核通过前不能出现在玩家地图。

### 4.3 点位模型：一个主点，最多三个卫星点

#### 主点位

- 绑定商家档案中已核验坐标；商家必须在地图再次确认。
- 展示城市分身头像、店名、营业状态和主玩法。
- 商家权益核销、付费兑换和门店归属只能从主点位发起；玩法进度和非商业虚拟奖励可由已审核的卫星点触发。

#### 卫星点位

首发只允许以下四种 preset：

| 类型 | 地图标识 | 内容 | 典型范围 | 完成方式 |
|---|---|---|---|---|
| 故事点 | 书页／对白 | 街区故事、建筑细节、商家来历 | 主点周边步行范围 | 到达＋阅读／听取 |
| 发现点 | 闪光／眼睛 | 拍照角度、隐藏细节、橱窗物件 | 店内或门口 | 观察问答／拍照 |
| 任务点 | 旗帜 | 暗号、扫码、选择、轻互动 | 店内或合作场地 | 服务端验证 |
| 彩蛋点 | 微光／问号 | 隐藏菜单、限定话术、复访内容 | 默认不直接公开 | 条件满足后揭晓 |

治理规则：

- P1 试点假设为最多 3 个卫星点；这是为控制地图密度和审核成本设定的待验证上限，不是付费就能无限扩容。
- 卫星点与主点的步行距离和可达性由平台校验；超出建议范围必须说明剧情理由。
- 放在公共空间时不得要求危险动作、进入非开放区域或长时间驻足阻塞。
- 放在另一家商户时必须获得对方同意，并明确奖励和数据归属。
- 点位编辑后需要重新审核；进行中的活动读取已发布版本快照。

### 4.4 “餐厅、好玩、剧情、彩蛋”地图标记体系

建议把 marker 设计拆成两个正交维度。

#### 维度 A：内容类别——它是什么

| 类别 | 主图形 | 推荐语义 | 示例 |
|---|---|---|---|
| 餐厅／饮品 | 碗／杯 | 吃喝与补给 | 面馆、咖啡、酒吧 |
| 好玩／体验 | 星芒／玩具 | 参与型体验 | 手作、展览、运动、桌游 |
| 剧情／故事 | 书页／对白 | 听、读、观察城市故事 | 老建筑、人物、街区记忆 |
| 任务／挑战 | 旗帜／菱形 | 有明确完成动作 | 答题、拍照、扫码、暗号 |
| 彩蛋／隐藏 | 微光／问号 | 未完全揭晓 | 隐藏菜单、复访内容、随机碎片 |
| 俱乐部／活动 | 双人／火苗 | 可加入的组局 | 集合、周末路线、主题活动 |

“店铺城市分身”不是第七个内容类别，而是商家主点的实体与表现方式。例如，咖啡店主点显示圆形分身头像，右下角叠加“餐饮”小角标；卫星故事点则使用书页 marker。

#### 维度 B：交互状态——现在能做什么

| 状态 | 视觉变化 | 说明 |
|---|---|---|
| 未发现 | 降低细节或只显示微光 | 不提前泄露彩蛋内容 |
| 已发现 | 正常 marker／头像 | 可打开地点卡 |
| 可行动 | 外圈脉冲或小旗标 | 当前距离、时段和前置条件允许 |
| 当前目标 | 放大 1.15–1.25 倍＋定向光环 | 全图只有一个最高优先级目标 |
| 已完成 | 实心章／对勾／低饱和 | 仍可回看，不与未完成抢注意力 |
| 暂停／关闭 | 斜线／灰环 | 明确原因和恢复时间，不直接消失 |
| 受限 | 锁 | 尚未解锁、超时段或需组队 |

颜色只作为辅助，图形、外圈、明暗和文案必须共同表达状态，保证色弱用户也能区分。

“危险”不是玩家可见的交互状态，而是发布阻断／紧急下线原因：审核或投诉证实点位危险时，不得继续导航或以“暂停”伪装为可恢复内容。

### 4.5 唯一产品合同：节点、标记与动作映射

| 场景 | `entity_type` | `point_role` | `content_kind` | marker 表现 | 可触发动作 | 权益边界 |
|---|---|---|---|---|---|---|
| 餐饮商家主点 | `MERCHANT` | `PRIMARY` | `FOOD` | 城市分身头像＋餐饮角标 | 看店卡、导航、到店、开始玩法 | 可核销商家权益 |
| 体验商家主点 | `MERCHANT` | `PRIMARY` | `EXPERIENCE` | 城市分身头像＋体验角标 | 看店卡、导航、预约／开始玩法 | 可核销商家权益 |
| 商家卫星故事点 | `MERCHANT` | `SATELLITE` | `STORY` | 书页／对白 marker | 阅读、听取、观察问答 | 只推进玩法，不核销商家权益 |
| 商家卫星发现点 | `MERCHANT` | `SATELLITE` | `DISCOVERY` | 闪光／眼睛 marker | 观察、拍照、回答 | 可发非商业章／线索 |
| 商家卫星任务点 | `MERCHANT` | `SATELLITE` | `CHALLENGE` | 旗帜／菱形 marker | 扫码、暗号、轻互动 | 可发非商业章／线索；不可付费兑换 |
| 商家卫星彩蛋点 | `MERCHANT` | `SATELLITE` | `SECRET` | 微光／问号 marker | 条件解锁、隐藏话术 | 可发虚拟收藏；实物权益回主点核销 |
| 平台城市故事点 | `CITY_POI` | `STANDALONE` | `STORY` | 书页／对白 marker | 阅读、听取、收藏 | 无商家权益 |
| 俱乐部活动集合点 | `EVENT` | `PRIMARY` | `SOCIAL` | 双人／火苗 marker | 报名、签到、进入路线 | 按活动规则，不冒充商家核销 |

所有行再叠加同一组 `interaction_state`；类别图形回答“它是什么”，外圈／明暗／角标回答“现在能做什么”。

### 4.6 不同缩放级别的信息密度

```text
城市级（远）
  → 只显示区域聚合：12 家店、3 条故事、1 个活动

街区级（中）
  → 显示类别 marker；主店城市分身头像优先

步行级（近）
  → 显示主点 + 卫星点；可见距离、状态和微型标签

选中态
  → 只展开一张地点卡；其余 marker 降低视觉权重
```

聚合不能只显示数字。建议以“图标 + 数量”表达构成，例如 `餐饮 8 · 故事 3`；玩家能在放大前判断这个街区值不值得去。

## 5. 统一暗色漫游的两种信息状态

视觉基线直接继承当前小程序 Play tokens：页面 `#050505`、基础面 `#0A0A0A`、次级面 `#111111`、悬浮面 `#181818`、主文字与当前目标使用白色。地图上的卡片保持实色深底，避免半透明卡压在已揭开的亮底图上导致对比度漂移。

### 5.1 暗色发现态：近人、有生活感

适用：打开漫游首页、找附近店铺、浏览俱乐部活动、决定去哪。

视觉建议：

- 保持现有暗色底图与迷雾语言，降低默认商业 POI、次要道路文字和非当前图层的亮度；
- 主店用圆形城市分身头像，2px 浅色外环和暗色投影；头像是固定门店角色，不是店主或玩家实时位置；
- 类别点使用统一 28–34px marker，不使用表情符号；
- 顶部为深色实底的搜索／类别筛选悬浮条，底部为当前位置和筛选按钮；
- 选中点出现一张深色实底浮动卡：头像／封面、城市角色名、距离、营业、玩法摘要、主按钮；
- 地图和“附近列表”共享选中状态，横滑地点卡时地图同步平移。

地点卡建议只保留一个主动作，并按状态改变：

```text
未到附近  → 去看看
已在附近  → 听听它怎么说
可开始    → 接任务
已完成    → 看我的发现
已关闭    → 收藏下次来
```

### 5.2 暗色游玩态：沉浸、克制、状态优先

适用：已经开始一局漫游、跟随路线、寻找彩蛋、执行任务。

视觉建议：

- 底图进一步降低无关 POI；继续沿用同一套深色／迷雾探索语言；
- 城市分身退到陪伴层，不持续占据中央；
- 当前目标、可行动点和玩家位置具有最高层级；
- 彩蛋未发现时只显示微光或模糊范围，避免导航直接破题；
- 已完成点留下印章或照片缩略图，形成“走过的城市”；
- 屏幕底部固定回答“下一步做什么”，地图不承担长篇说明。

两种状态共享同一页面、同一批 POI、同一进度和同一暗色 token；只改变信息密度、marker 优先级与可操作信息，不复制两套业务数据。

## 6. 玩家体验闭环

### 6.1 第一次发现一家店

```text
地图看见城市分身头像
  → 点头像，地图原地展开地点卡
  → 看见“它是谁／这里能玩什么／离多远／是否营业”
  → 选择“去看看”
  → 进入附近范围后，分身出现一条审核后的欢迎语
  → 到达主点或卫星点，开放任务／故事／彩蛋
  → 服务端确认完成
  → 分身回应，并留下章、故事片段或下一站线索
```

### 6.2 再次来访

复访不能只是重复同一句欢迎语。建议读取有限、可解释的事实：

- 上次来访日期；
- 已完成的该店任务／彩蛋；
- 尚未发现的一个内容；
- 当前是否有新活动或新故事。

示例：`“你上次找到了窗边的蓝鸟，但楼梯口那句暗号还没人告诉你。”`

这类话术可以由服务端结构化事实拼装或预生成，不需要把完整聊天记录塞给模型。

### 6.3 角色不应该一直说话

主动触发最多放在以下事件：

1. 本次漫游第一次看见该店；
2. 首次进入附近范围；
3. 到达或完成关键点；
4. 解锁新彩蛋；
5. 结束漫游的回顾。

同一事件有会话配额和冷却；玩家可关闭角色提示。自由聊天只在玩家主动打开角色卡后发生，不阻断地图和任务主流程。

## 7. 商家端配置流程

建议将现有“店铺装修”首页改成结果导向的四张卡，而不是继续增加表单行：

| 卡片 | 结果 | 完成态展示 |
|---|---|---|
| 品牌门面 | 店名、封面、Logo、标签、故事 | 公开主页预览 |
| 城市分身 | 头像、人设、话术、知识、审核 | 地图头像＋角色预览 |
| 地图据点 | 主点确认、卫星点、时段、审核 | 小地图＋已上线点数 |
| 玩家玩法 | 当前主玩法、故事、彩蛋、权益 | 玩家路径预览 |

### 7.1 点位编辑器

地图长按不应直接发布点位。正确流程：

```text
选择“新增点位”
  → 选择 preset（故事／发现／任务／彩蛋）
  → 在允许范围内放置
  → 填写玩家到场能观察到的真实对象
  → 选择验证方式和异常兜底
  → 玩家视角预览
  → 提交审核
  → 审核通过后进入下一发布版本
```

编辑器应同时提示：与主店步行距离、GPS 精度风险、营业／开放时段、是否位于道路或非开放空间、是否需要其他主体授权。

### 7.2 AI 生成只帮助商家起稿

AI 可以：

- 从品牌故事提炼 3 个角色方向；
- 从店铺照片建议可观察的故事点／拍照点；
- 把商家口语描述改成简短玩家任务；
- 生成同一角色的多状态视觉草图；
- 检查任务是否缺少现场证据、兜底或完成条件。

AI 不可以：

- 自动把未确认坐标发布到地图；
- 自动承诺折扣、库存或奖励；
- 用网络上抓取的他人图片生成商家角色；
- 自动通过内容和位置安全审核；
- 编造街区历史并标成事实。

## 8. 当前城瘾已有能力与缺口

以下只说明当前源码基线，不代表生产库或微信线上版本已具备同等能力。

### 8.1 已有，应连接起来

1. 店铺装修已有“城市角色名”、品牌故事、特色标签、相册、常备权益和“成为城市节点”入口：`chengyinhub-xcx/pages/merchant/decor/index.*`。
2. 商家节点申请已经复用完整玩法模板，支持城市故事卡、隐藏菜单、拍照点、扫码、文字暗号、问答、GPS 等，并要求商家确认店址：`chengyinhub-xcx/pages/merchant/citynode/create/index.js`。
3. `RoamPoi` 已有商家据点、模板、标签、封面、排序、审核和商家归属字段：`chengyinhub-system/src/main/java/com/chengyinhub/business/domain/RoamPoi.java`。
4. `NpcProfile` 已明确 `scope_type=2` 是“门店分身”，并已有头像、人设、欢迎语、审核和启用字段：`chengyinhub-system/src/main/java/com/chengyinhub/business/domain/NpcProfile.java`。
5. 漫游已有 NPC 协调器、事件配额、缓存话术、气泡和 Chat 闸门：`chengyinhub-xcx/utils/roam-npc-coordinator.js`。
6. 漫游已有商家／公园／地标、彩蛋光点、POI 完成状态、商家去重、附近卡片、足迹和会话：`chengyinhub-xcx/pages/roam/index.js`、`components/cy/free-map/*`。

### 8.2 真实缺口

1. `scope_type=2` 虽然存在，但还没有完整的商家自助创建、素材生成、审核、发布和按商家 POI 解析的闭环；`NpcProfileService.resolveForActivity()` 的注释说包含门店分身，当前实现却只查询 `scope_type=1`，也没有 `resolveForMerchant(merchantId)`。
2. `RoamPoi.type` 目前主要区分地标／公园与商家，不足以同时表达餐厅、体验、故事、任务、彩蛋和状态。
3. 店铺装修中的“城市角色名”只是文本字段，没有和 NPC 头像、人设、知识、事件绑定。
4. 商家节点目前更像“一家店配一个玩法＋一个坐标”，还没有主点／卫星点的轻量编排。
5. 暗色漫游发现态的类别 marker、头像 marker、筛选、选中卡和缩放聚合尚未形成统一视觉语法。
6. 现有全局漫游 NPC 与门店分身的责任边界需要明确：全局 NPC 负责整局陪伴，门店分身只在自己据点和授权内容内说话。

### 8.3 建议的数据边界

不要继续扩大 `RoamPoi.type` 让一个字段承担所有语义。冻结以下统一合同：前三个维度描述内容本身，第四个维度按玩家进度派生，不作为 POI 的全局静态状态落库。

```text
entity_type       = CITY_POI | MERCHANT | EVENT
point_role        = PRIMARY | SATELLITE | STANDALONE
content_kind      = FOOD | EXPERIENCE | STORY | DISCOVERY | CHALLENGE | SECRET | SOCIAL
interaction_state = HIDDEN | DISCOVERED | ACTIONABLE | TARGET | COMPLETED | PAUSED | LOCKED
```

玩家 `/api/roam/pois` 当前直接返回 `List<RoamPoi>`。实施时应新增玩家侧地图投影 DTO，返回 `entityType / pointRole / contentKind / interactionState / npcSummary`，避免把数据库实体继续扩成公开 API 合同。`npcSummary` 只包含已审核、已启用角色的公开字段，不下发 `persona` 或商家草稿。

NPC 继续使用：

```text
npc_profile.scope_type = 2
npc_profile.scope_id   = merchant_id
```

卫星点可以在现有商家据点申请／审核链上扩展 `parent_poi_id` 与 `point_role`，是否单独建表应在技术设计阶段根据现有查询和迁移风险决定；本文不提前冻结数据库实现。但以下服务端规则不可变：每商家恰好一个发布主点、卫星点必须继承同一商家且最多 3 个、内容类型走白名单、位置安全与距离要校验、所有写操作必须在 `WHERE merchant_id = 当前登录商家` 下完成、编辑已发布内容后退回待审、玩家只读取 `status=1 AND audit_status=1` 的发布内容。卫星点不得绑定实物券或发起付费权益核销。

完整读回链路应为：商家读取自己的 NPC／点位草稿 → 保存并提交 → 管理端审核 → 玩家地图只读已审发布投影 → 商家回读上线与驳回状态。客户端不得传入并决定 `scope_id` 或 `merchant_id`；服务端必须由登录会员解析商家身份。AI 失败时回退到上传头像和人工审核话术，不阻断地图、到点、任务或奖励。

## 9. 分阶段落地建议

### P0：先打通真实功能闭环，不引入自由 AI

目标：让商家真的能配置一个城市分身、一个可信主点和少量玩法点，玩家能在现有暗色漫游里发现、到达、完成并收到角色回应；不是只换一组 marker。

- 商家在店铺装修中配置角色名、头像、角色原型、语气、欢迎语和禁答项；头像先支持现有上传能力与平台模板，所有内容进入审核；
- 每店绑定 1 个核验主点，并可提交最多 3 个故事／发现／任务／彩蛋卫星点；服务端校验商家归属、数量、距离、坐标与发布状态；
- 玩家 `/api/roam/pois` 读取模型增加正交的实体、内容和点位角色投影，暗色地图按餐厅／好玩／剧情／任务／彩蛋显示不同 marker；
- 主点显示门店分身头像与内容角标，卫星点显示内容图形；点开后原地出现深色地点卡，支持筛选和横滑切点；
- 到点与任务仍由现有服务端验证，完成后读取审核过的 NPC 话术；NPC 或 AI 服务失败时，发现、到点、任务和奖励继续成立；
- 实物权益与付费兑换只允许在主点触发，卫星点只推进玩法或发非商业虚拟收藏；
- 选择 3–5 家真实商户做一条街区样板，覆盖餐饮、体验、故事和彩蛋至少四类内容。

验收：商家能保存并回读自己的分身与点位，不能读写其他商家；玩家能在 10 秒内分辨“吃什么／玩什么／哪里有故事／哪里是隐藏内容”，并完成一次从暗色 marker → 地点卡 → 到点验证 → 任务完成 → NPC 回应的闭环。

### P1：真实 AI 形象生成与更丰富的门店分身

目标：在 P0 可配置、可审核、可游玩的基础上，接入受治理的图像生成能力，而不是把“上传头像”冒充 AI 生成。

- 接入明确模型供应商、授权、保存期、删除和内容安全规则的图像生成服务；当前仓库只有 OSS 上传，没有可直接复用的真实文生图服务；
- AI 从商家已授权的 Logo、门头、代表产品、品牌色和故事生成 3 个视觉方向，商家选定后产出固定多状态资产；
- 建立性格、可信知识、禁止回答和审核话术，仅上线预生成／可审核互动；
- 用试点数据决定是否调整“1 主点＋最多 3 卫星点”的上限和审核策略；
- 门店分身只消费本店事实和本点事件，全局 NPC 继续负责整局。

验收：一名未培训商家能在 15 分钟内完成起稿；审核人员能判断内容、位置、授权和玩法是否可上线；首次玩家无需工作人员解释即可完成至少一个点。P1 不开放自由对话。

### P2：剧情、记忆、声音和联店路线

目标：从“单店有趣”升级为“街区可持续探索”。

- 城市分身记住有限到访事实和已解锁内容；
- 自由对话只作为单独小流量实验：玩家主动打开，经输入攻击检测、输出过滤、事实来源限制、全量审计、举报下线和人工接管后才可开启；
- 语音只用于欢迎、故事和关键节点，先预生成再上线；
- 多店角色可通过线索接力，但不能彼此自由生成事实；
- 俱乐部可把多个审核点编成顺序／自由／分支路线；
- 彩蛋按时间、复访、完成条件或活动解锁；
- 完局生成真实足迹、角色合影或地点纪念卡。

验收：先在产品评审确认样本量、周期和 Go／No-Go 阈值，再判断路线完成率、第二家店到达率、复访解锁率和商家续用率是否优于无角色／无剧情对照组；未设阈值前不声称“显著提升”。

## 10. 样板玩法建议

首个样板不要做大而全，建议用 3 家店、每店 1 个城市分身、总计 6–8 个点完成验证。

### “街角守店人”样板

1. 玩家在暗色漫游发现态看到三位守店人头像，而不是三枚相同商家 pin。
2. 第一位守店人给出一个街区观察任务，答案指向附近故事点。
3. 故事点解锁第二家店的隐藏菜单暗号。
4. 第二家店完成扫码或现场问答后，得到一枚地图碎片。
5. 碎片在地图上显影第三家店附近的彩蛋范围，不直接给精确坐标。
6. 第三家店完成最终任务后，三位角色共同出现在完局纪念卡；每家店保留自己的到访事实和权益归属。

这个样板能同时验证：头像 marker、类别图标、地图卡、卫星点、跨店线索、到店验证、角色话术、收藏和三商家数据边界。

## 11. 指标与负控

### 11.1 产品指标

- 地图 marker 点击率；
- 地点卡到“去看看／接任务”的转化率；
- 从第一点到第二点的到达率；
- 到达后任务开始率和完成率；
- 每次漫游发现的类别数，不只统计 POI 总数；
- 商家分身配置完成率、审核通过率和发布后使用率；
- 7／30 日复访、彩蛋解锁和收藏回看；
- 角色提示关闭率、自由聊天打开率和有效下一步点击率。

### 11.2 安全与质量指标

- 重复／垃圾点位率；
- 坐标偏移导致的到达失败率；
- 关闭／暂停点仍被导航的次数；
- AI 内容拒审、肖像／声音授权投诉、越界回答率；
- 玩家在点位停留过久、进入危险／非开放区域的报告；
- 同店重复 POI、同名连锁误合并和 marker 冲突率。

### 11.3 必须做的负控

1. 把所有 marker 临时改为同一图形，首次测试用户应明显更难分辨类别；否则新图标体系没有产生价值。
2. 关闭一个商家点位，地图和地点卡必须立即显示暂停且不能开始任务；否则状态观测是假绿。
3. 把门店 NPC 的 `scope_id` 换成另一商家，权限／解析必须失败，不能读取对方故事或权益。
4. 删除某彩蛋的前置条件，发布校验必须拦截“默认公开”；不能让隐藏内容因缺配置泄露。
5. 模拟 AI 服务失败，地图、到店、任务和奖励主流程必须继续工作；城市分身静默降级而非阻断。

## 12. 明确不做

- 不做商家无限点位和付费买地图占位；
- 不做玩家／店主默认实时位置公开；
- 不做每个 marker 都是大头像；
- 不做进入地图即自动播放多角色语音；
- 不做无审核、无知识边界的自由 AI 客服；
- 不做只靠颜色区分餐厅、故事、彩蛋和完成状态；
- 不做为了地图换皮而替换现有微信原生地图与后端；
- 不把 GitHub 项目可运行误写成可直接用于城瘾商业代码；
- 不把生成了角色图、写了迁移或通过本地测试误写成已经上线。

### 12.1 上线红线与必需证据

| 门禁 | 上线前证据 | 失败时行为 |
|---|---|---|
| 代码与素材许可 | 依赖许可清单、角色资产来源、商业使用权审核记录 | 不合入商业版本；仅作设计参考 |
| 肖像与声音 | 被使用者明示授权、用途与有效期、撤回通道 | 改用平台通用非真人资产，立即下线争议内容 |
| 位置与到访隐私 | 收集目的告知、最小字段清单、保存期、删除入口、不公开实时位置的验证 | 停止采集和个性化，回退到无记忆地图 |
| 未成年人 | 年龄与监护规则、高风险时段／地点限制、举报通道 | 不开放位置记忆、夜间引导和自由对话 |
| 点位安全 | 坐标复核、现场可达性、营业时间、危险动作清单、投诉紧急下线演练 | 发布阻断或紧急下线，同步停止导航 |
| 跨商家放点 | 场地方同意、奖励与数据归属协议、到期日期 | 不发布该卫星点，不影响本店主点 |
| AI 回答 | 知识来源、禁答集、输入／输出防护测试、审计日志、人工接管与举报流程 | 关闭自由对话，保留已审核话术和非 AI 主流程 |
| 模型与供应商数据 | 数据是否用于训练、存储地域、保存期、删除／导出能力和合同责任 | 不传用户可识别位置／到访数据，停止该供应商链路 |
| 投诉、删除与追溯 | 玩家／商家删除入口、响应时限、发布版本与审核人回读 | 先下线争议节点，保留必需审计证据后按规则删除 |

具体适用的隐私、未成年人和 AI 合规要求必须由产品、安全／法务和运营联合确认；本表是上线证据框架，不代替法律意见。

## 13. 评审时只需要决定的四件事

1. 对外名称先用“城市分身”，还是更具 IP 感的“店灵／守店人”。
2. 是否确认漫游全程沿用现有暗色 Play 语言，只在发现态／游玩态切换信息密度和 marker 优先级。
3. P1 试点是否先用“1 主点＋最多 3 卫星点”作为待验证上限。
4. 样板先选哪 3–5 家商户，是否能提供授权素材、稳定现场物和真实营业时段。

这四项确认后再进入视觉方案和交互原型；暂时不需要先决定模型供应商、3D 方案或完整数据库重构。

## 15. 置信度与证据边界

- 高：当前仓库中的 `NpcProfile scope_type=2`、商家节点、漫游 NPC、POI 和店铺装修字段；均来自本地固定源码基线。

- 中：统一暗色下采用“头像主点＋内容图标卫星点＋发现／游玩两种信息状态”会更适合城瘾；这是基于现有视觉基线和信息层级的设计推断，仍需用原型和首次用户测试验证。
- 中：城市分身会提升商家装修完成率和玩家到店率；需要真实商家样板和对照数据证明。
- 未验证：当前生产数据库是否具备全部相关迁移、线上 NPC feature flag、真实商家 POI 数据和微信已上传版本；本文不据此做上线判断。
