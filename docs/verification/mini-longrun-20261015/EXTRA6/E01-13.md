## 真实入口与可达事实

授权生产审计路径：ClubWaitlistServiceImpl.java、ClubEventOpsMapper.xml。只读依赖：CmsRegistrationServiceImpl.java、service/support/SaleAvailabilityPolicy.java、IClubWaitlistService.java、ApiClubEventOpsController.java及已有候补回归。

`ClubWaitlistServiceImpl.join`：requirePolicy通过真实FOR UPDATE查询要求series ACTIVE、occurrence ACTIVE、activity club配套且未删；随后校验participationGuard、活动成员、票种scope/未删/有效总库存、remaining==0、无有效报名及活跃候补，最后只insert WAITING。

`seriesPolicyByActivity`没有activity.status/publish_status/end_date或ticket.sale/signup/start时间条件。因此在合法成员/满额且series/occurrence仍ACTIVE时，单独将activity下架/结束、或票报名截止过去，确实可能仍写WAITING。这是实际可达路径的静态结论，未执行复现。但该写入不扣库存、不生成OFFERED、不创建registration，不自动获得可付款权利；“可以排队”并不等于“可以即时成交”。

正常整场取消会取消occurrence并终止活跃候补，之后requirePolicy的ACTIVE关联失败；该原链与本项“只改变activity发布/时间但保留ACTIVE occurrence”不同，不能混为已取消场次仍可加入。

## 不同阶段的既有合同

| 阶段 | 真实既有闸与承诺 |
| --- | --- |
| WAITING | 入队为满额票的活动成员登记，不占库存。IClubWaitlistService/Controller没有声明“入队即完成可售资格或可立即付款”；既有满额入队普通测试只核成员/scope/库存及重复 |
| 维护晋升发现 | selectWaitlistMaintenancePage(kind=3)要求activity status=1/publish_status=1/del_flag=0/end_date>now，ticket余量>0且coalesce(signup_deadline,start_time)>now（或为空）；说明维护发现有独立过滤，但不能直接推导同过滤必须约束所有WAITING登记 |
| OFFERED晋升 | promoteNextLocked按FIFO/资格与真实库存扣减后offer；offerDeadline=min(配置时长,signupDeadline或fallback startTime)，截止<=now不晋升，不给已过截止token续期 |
| quote | CmsRegistrationServiceImpl.quoteRegistrationForOffer先validateForQuote，再进入正常quoteRegistrationInternal；仍验活动在架未结束、票/主题可售。hold仅豁免再次扣库存，不豁免所有可售闸 |
| registration/create/payment retry | validateAndGetActivity拒绝活动下架/结束；assertRegistrationSellable对商业主题调用SaleAvailabilityPolicy，对免费UGC核在架和票signupDeadline；不是WAITING插入路径 |

只读 `CmsRegistrationServiceImpl.validateAndGetTicket` 的既有CU-C-32注释还明确：普通活动报名开始即停售，**持有效候补hold的inventoryAlreadyHeld=true不适用该普通startTime停售闸，其售止口径为signupDeadline**。因此简单要求join复制所有普通报名条件会把阶段差异改成新政策，甚至可能误伤已经承诺保留名额的既有行为。

“票过售卖期”也必须先明确是哪种事实：SaleAvailabilityPolicy使用topic SELLING/sellingStartedAt/saleEndAt与ticket.signupDeadline，ticket.startTime/endTime另有履约/普通活动判断；ticket.sale_start_time/sale_end_time在既有migration/fixture注释中为发布回显尚未接购票闸字段。不能据字段名字将展示字段直接变成候补拒绝依据。

## 交C00的具体决定边界

在继续实施前需明确WAITING是否允许：暂时下架后等待重新上架、活动最终结束、主题售卖尚未开始或硬售止、票signupDeadline到达等各类状态；不能用一个“不可售”合并处理。还须明确已有WAITING在上述变化时应保留、可取消还是终止，避免只挡新增却静默改变存量或名额释放链。

本lane不提出必须新建接口/DDL，不更改原鉴权；如C00已有明确历史裁决可提供精确依据后恢复本项，按批准状态分支作最小修复及反例回归。没有裁决则保持BLOCKED，释放该项继续其他独立工作，不能写断言将新政策固化。

另一个可独立继续只读的边界是维护扫描已过滤activity可用性，但直接promoteNext及cancel/expire触发的内部promoteNextLocked只验policy/票deadline，没有同样的activity发布/结束条件。这涉及OFFERED实际hold而非WAITING登记，必须单独审计既有晋升承诺，不能在本项全局修改共享policy使下架场次的取消/到期释放也被拒绝。此处只是后续具体线索，未定为已知bug。
