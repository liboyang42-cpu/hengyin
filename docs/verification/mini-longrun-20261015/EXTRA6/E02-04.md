## 实际执行顺序与反证

源码 `chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/CommunityPostServiceImpl.java`：

1. delete是@Transactional写入口。先requirePrincipal、校验requestId，再locked(postId)检查正ID并SELECT FOR UPDATE；不存在404。
2. isCommandReplay以memberId/requestId查回执。只有command_type=POST_DELETE且aggregate_id=当前postId才返回重放；异命令或异帖409。回执查询不跨会员。
3. 已匹配回执直接结束，刻意发生在requiredVersion和状态决策之前。因此同身份重复删除携带原expectedVersion仍成功，不因首删version增加/DELETED而报过期；不会再次orphanMedia、排擦除队列、写搜索/事件或回执。
4. 没有回执才要求非负expectedVersion。CommunityPostLifecyclePolicy.decide先核当前版本，不匹配409；再核删除归属（非作者403），再核现有允许删除生命周期。未把“相同ID但新requestId”自动当幂等重放，也未扩大REMOVED/DELETED可删除状态。
5. transitionCas还以id/expectedLifecycle/expectedVersion三条件更新，零行409；成功后执行媒体孤立、擦除任务、搜索投影、outbox与回执，均处于原写事务。队列失败及回执冲突抛RuntimeException，外部Spring事务入口应回滚，不捕获为成功。

只读SQL依赖 `chengyinhub-system/src/main/resources/mapper/business/CommunityPostMapper.xml`：selectByIdForUpdate按id FOR UPDATE；selectCommandReceipt明确member_id+request_id；transitionCas按id+当前生命周期+版本；insertCommandReceipt使用INSERT IGNORE，其返回0后由服务再次判别回执身份，不能视为无条件成功。

只读DDL `chengyinhub-admin/sql/migration_community_post_platform_20260909.sql`：community_post_command_receipt唯一键(member_id,request_id)，不同会员相同客户端字符串不串回执。本项未执行/修改DDL或迁移。

## 指定触发结果（静态结论）

| 输入/交错 | 当前分支 |
|---|---|
| 同member/request/post重发首删请求，expectedVersion仍为原值 | 精确已存POST_DELETE回执早返回，不重复副作用 |
| 不同requestId携带过期expectedVersion | 无该回执，版本决策409，不进入更新与副作用 |
| 同requestId用于另一帖或另一命令 | 已存回执命令/aggregate不匹配409，不借旧回执删新帖 |
| 另一会员使用相同字符串 | 回执按会员隔离；没有该会员回执则仍经过版本及作者归属校验 |
| 同帖两个删除请求竞争 | 外部事务入口先锁同一父行；更新仍有CAS，后者不能无条件覆盖首个已提交版本 |

回执重放不重新比较expectedVersion属于既有身份合同；本项没有引入通用请求指纹、改变归属检查顺序或收紧已获成功回执的重放政策。没有发现上述指定触发的静态源码反例，所以不改实现。
