## 既定保护事实

实际生产 `ClubEventOpsMapper.xml.countProtectedActivityHistory(activityId)` 只要下列任一事实存在就返回1：

- cms_activity.is_settlement非0；
- owner_type=2且owner_id为该活动的**任意**cms_registration，不按付款/报名状态过滤；
- 该活动候补状态为WAITING、OFFERED、CLAIMED。

因此成功报名数为0不能绕过保护；已取消/过期报名仍是报名历史并受保护。这里必须区分两类“历史”：**报名历史任意状态保留**；候补CANCELLED/EXPIRED/CONVERTED不单独纳入活跃候补谓词。CONVERTED已有报名单时仍由任意报名历史分支保护。不能将“排除取消/过期候补”误读为同时排除取消/过期报名，也不能擅加全部终止候补永久锁定的新政策。

数据库active_member_key也以WAITING/OFFERED/CLAIMED三态定义活跃身份，和保护SQL采用相同活跃范围。真实损坏/孤立CONVERTED且无报名单不在本项凭空造fixture并推导新政策。

## 写入口、检查次序与并发链

主文件 `ClubEventOpsServiceImpl.updateFuture` 使用READ_COMMITTED事务：

1. 锁series、锁club并重检授权/expectedVersion；不允许重排修改系列默认负责人、容量、候补开关或认领窗口。这些系列字段仍会被旧场次读取，已有明确拒绝分支。
2. 读取未来ACTIVE occurrence及其activity的FOR UPDATE行，按上海日期建立唯一集合。
3. 保留日期在移除循环直接continue、在新增循环也continue；旧occurrence/activity既不取消也不重建，时刻不被请求值覆盖。可在保留受保护旧场次的同时新增独立日期，不把此行为误报为破坏旧场次。
4. 移除日期先调用真实countProtectedActivityHistory。返回非0即409，发生在角色撤销、活动取消、occurrence CAS和新场次生成之前。
5. 无保护才进入角色撤销与activity/occurrence CAS；角色审计失败或CAS零行抛异常，原事务回滚。activity取消SQL另守任意报名历史与结算；未因为它未重复写候补谓词就断言存在可达绕过。

只读追踪 `ClubWaitlistServiceImpl` 的实际候补写链以核最后一点：join/promoteNext/cancel/claim所用requirePolicy调用 `selectSeriesPolicyByActivityForUpdate`，生产SQL锁定含相同series/occurrence/activity的连接行；claim经validateOffered(forUpdate=true)也先取得该policy。到期维护先锁同series。它们与updateFuture持有的series行在事务内互斥，不是只靠一次无锁count保护：

- 候补先提交：updateFuture在series锁后READ_COMMITTED看见已提交活跃候补并拒绝移除。
- updateFuture先持series并完成移除：join/claim等后取policy时不再满足ACTIVE occurrence条件，不能在已取消场次上新写活跃候补。

这是静态锁链依据，不是MySQL并发运行证据；具体执行计划/死锁恢复仍未本轮验证。没有修改任一候补Service或Mapper CAS合同。
