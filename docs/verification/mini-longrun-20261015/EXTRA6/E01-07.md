## 静态确认的问题链

生产 `ClubWaitlistServiceImpl.myStatus` 使用默认隔离的事务，先普通读取 policy/latest。部署数据库为 InnoDB RR 时，该普通读建立快照。`expireStaleOfferForStatus` 对已到期 OFFERED 先调用 `expireOffered`，后者按 series→club→ticket→waitlist 执行锁定读。

具体交错：offer 在截止之前被另一事务认领并提交 CLAIMED；本次 status 首次普通读仍有截止前已建立的 OFFERED 快照，随后按当前时刻进入到期 helper。`expireOffered` 的 waitlist FOR UPDATE 已看到 CLAIMED，不做 EXPIRED CAS、不归还 hold。但旧 helper 随后的普通 `selectLatestWaitlist` 仍可重复读取 OFFERED 旧快照，因其截止已过而把返回对象手工标为 EXPIRED，丢掉真实 CLAIMED/registrationId/version。另一个可达路径是第一次 policy 读建立快照，claim 在它之后、latest 之前提交；latest 仍看到旧 OFFERED。维护转换为 CONVERTED 或已过期维护也可能在该旧快照内丢失当前状态/版本。

SQL 证据：`ClubEventOpsMapper.xml` 的 `selectLatestWaitlist` 是普通 SELECT；已有 `selectWaitlistByIdForUpdate` 使用 `where id = #{id} for update`，属于当前读。没有为本项新建查询、字段或 Mapper API。

## 最小修改与锁序

唯一生产修改在 `chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/ClubWaitlistServiceImpl.java` 的 `expireStaleOfferForStatus`：到期处理后，使用已有 `selectWaitlistByIdForUpdate(entry.getId())` 回读同一个 offer，而不是再次普通 latest 查询。保留读取对象的原 member/activity/ticket 校验与外层 club 校验；查不到仍沿原无 token 的 EXPIRED 兜底，不从未知读面恢复付款能力。只有当前仍是已过期 OFFERED 才沿原逻辑屏蔽 token；CLAIMED/CONVERTED 等当前状态原样保留，不手工改为 EXPIRED。

锁序核对：

1. `expireOffered` 若进入实际锁定链，先锁 series、再 club、再 ticket、最后 waitlist；本次补充 current-read 只重复锁同一 waitlist，不再申请前序锁。
2. 若 `expireOffered` 在 snapshot 阶段已看到非 OFFERED 而提前返回，本次仅锁同一 waitlist；helper/`myStatus` 后续只有 scope 校验、普通报名计数与响应投影，不再申请 series/club/ticket 锁，不形成反向锁链。
3. 不改变事务隔离级别或其它写入口。初始 latest 的选择语义保留；进入到期处理后明确回读正在到期判断的原 offer 身份，不以旧快照猜该 offer 的当前终态。
