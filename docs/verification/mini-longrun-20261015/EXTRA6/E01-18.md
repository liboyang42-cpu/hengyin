## 实际状态写入入口：不是人工造不可能的下架

只读真实外部入口：`chengyinhub-admin/src/main/java/com/chengyinhub/web/controller/api/ApiActivityController.java` 的 `activityUpdatePublishStatus`，路径 `/api/activity/update_publish_status`。

该入口取得登录主体及现有publisher，核activity.memberId属于当前主办主体并执行原hosted-run限制，随后 `setPublishStatus(old==1?0:1)`，调用 `CmsActivityServiceImpl.updateCmsActivity`。实际Service委托 `CmsActivityMapper.updateCmsActivity`，XML更新publish_status。该链没有同步关闭club_event_series、取消club_event_occurrence或终止waitlist；因而合法自有club场次下架、series/occurrence仍ACTIVE是可达业务状态，不是只凭手工篡库的假前提。

活动结束也会自然发生：now越过activity.end_date不会自动将series/occurrence状态改为CANCELLED，票signupDeadline/startTime可以仍有已知较晚边界；两类事实独立存储，不能假设时间字段永远相互相等。

## 同一“新OFFERED”阶段的可观察准入失配

主读文件：`chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/ClubWaitlistServiceImpl.java`、`chengyinhub-system/src/main/resources/mapper/business/ClubEventOpsMapper.xml`。

| 实际路径 | 当前活动状态闸 |
| --- | --- |
| maintain kind3扫描→promoteNext | production selectWaitlistMaintenancePage要求activity.status=1、publish_status=1、del_flag=0、end_date>now；series/occurrence ACTIVE、候补启用、票有效且有余量、报名截止未到 |
| 直接promoteNext→promoteNextLocked | requirePolicy只要求series/occurrence ACTIVE与activity同club/未删；工厂只核waitlistEnabled、票scope/库存、offerDeadline及FIFO/成员资格，没有activity.status/publish/end检查 |
| cancel OFFERED→restore→promoteNextLocked | 取消成功回补hold后直接工厂，同样缺少活动状态闸；这是实际公开waitlist/cancel可达的自动晋升，不依赖未公开的人工promote API |
| expireOffered/expireClaimedTerminal→promoteNextLocked | 旧hold到期或订单终态消费后自动工厂，仍缺少上述状态闸；即使maintain的kind3不选该活动，kind0/kind2处理旧hold也能绕过kind3发现条件生成新offer |

共同工厂先deductInventory(1)，再offerWaitingCas将下一WAITING→OFFERED并产生token hash。因此这不是E01-13“是否允许无库存影响的预登记”，而是同样的新库存hold由不同触发器采取不同活动可用性规则。

具体静态触发：正常活动已存在成员A的OFFERED与成员B的WAITING，唯一库存由A hold占用；主理人通过真实入口下架活动，series/occurrence保持ACTIVE，票signupDeadline尚未到。A随后取消候补或其offer到期，原链合法释放A的hold，但工厂立刻扣回刚释放库存并为B创建新OFFERED。若仅靠maintain kind3，该下架活动不会进入晋升候选。结束活动且ticket时间仍晚于now时同理。

## 持token仍不能成交的真实下游闸

只读 `CmsRegistrationServiceImpl.quoteRegistrationForOffer`：先bridge.validateForQuote取得hold，再进入quoteRegistrationInternal；活动报价无论是否持hold都调用validateAndGetActivity。该方法拒绝activity.status!=1、publish_status==0、del_flag==2或now.after(end_date)。所以新B的token虽通过候补signature/scope/policy检查，活动下架/结束仍在报价层拒绝。

实际create外层事务同样先claimForOrder，然后createRegistrationInternal调用validateAndGetActivity；失败回滚claim，不生成可完成订单，但新OFFERED的库存hold在重试前仍保持，之后到期可能又自动给下一WAITING生成不可成交的新hold。

已有 `inventoryAlreadyHeld=true` 例外仅说明：不再次扣库存、不用普通ticket.startTime停售闸误伤已持名额者。它没有绕过activity在架/结束检查，也没有允许下架后为新成员生成新hold。不能据该例外把“新OFFERED对活动状态一律放行”当现有合同。

## 证据结论与范围

已确认的是**同一新OFFERED工厂相对既有kind3活动准入谓词存在源码失配**，且公开取消/维护到期链可达，后续真实报名又拒绝该活动。没有据此宣称已运行发现资金损失、越权或重复退款。

可对齐的既有规则仅限activity.status=1/publish_status=1/del_flag=0/end_date>now，与kind3完全同尺；不扩展到E01-13尚待裁决的WAITING登记、主题销售生命周期或ticket.sale_*展示字段。end_date=null和恰等于now在kind3均不选，而registration对null/等值较宽，此差异要在实施审阅时明确沿“新offer工厂对齐原维护晋升”范围，不借此统一所有报名时间合同。

## 最小修复提案（当前不实施）

1. **只在promoteNextLocked的新hold路径**加入统一活动可用性复核，放在任何队首状态修改、扣库存与OFFERED CAS之前。不可用返回false，保持WAITING，不撤销已有合法hold，也不抛错回滚前面的旧hold取消/过期释放。
2. 使用生产Mapper从当前activity行按exact activityId+policy.clubId读取现有kind3状态/时间谓词。应为当前锁定读（例如返回匹配activityId的SELECT ... FOR UPDATE），不能在RR维护事务中普通读旧快照。所有现有新晋升调用已先锁含activity的policy/series路径，再club/ticket；复核同一activity行只重复已有锁，不引入新的相反锁序。实施时须逐调用确认这一点。
3. 保持requirePolicy/seriesPolicyByActivity的宽范围不变：这些共享查询也被cancel、expire、claim使用。若全局加入publish/end条件，会把下架活动旧hold的取消/归还也挡住，是错误修法。
4. 不依赖扫描页参数“已经过滤”：取消、到期、直接调用都进入同一工厂；扫描后状态还可能变化。活动下架真实UPDATE与activity FOR UPDATE自然串行，若先完成准入读再下架，按旧hold处理；若下架先提交，新offer不生成。
