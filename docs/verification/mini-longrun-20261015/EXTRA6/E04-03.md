## 既定政策与真实触发

已有 `SmsCouponHistoryServiceImpl.isNotIssuable` 以 status=3/4 禁新增；`isDisabled` 只以 status=3 拒已领券核销。status=4 已领仍可核销，是既定合同，不能用统一“非active即失效”替代。

生产真实停发链：

- `chengyinhub-admin/src/main/java/com/chengyinhub/web/controller/api/ApiCouponController.java:207` 的 `stopIssuing` 校验原 owner/merchant 及现有状态，调用 `smsCouponService.stopIssuingCoupon`。
- `chengyinhub-system/src/main/resources/mapper/business/SmsCouponMapper.xml` 的 `stopIssuingCoupon` 按 id、owner、未删、status in(0,1) 更新为4；可提交真实状态变化。
- 同 XML 的 `tryIncrementReceiveCount` 只检查当前库存；`incrementReceiveCount` 只检查 id，两者都没有当前 status=3/4 拒新增条件。
- `chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/SmsCouponHistoryServiceImpl.java:263` 的 `grantCouponWithReceipt` 检查调用方旧 coupon 对象后才执行占库。真实调用方包括 `TopicCompletionCouponRewardServiceImpl.grantOnce`（grantCouponById）和 `MerchantCrmCouponGrantAdapter.grant`（先读模板，再grantCouponWithReceipt）。

静态失败次序：调用者读到 status=1 → stop 独立提交 status=4 → 原调用继续占库并插历史。预期拒发断言为 null、receive_count 不变、无新增 history。与发放先取得行锁并成功后停发的合法顺序不同。没有运行复现，不把静态证据写成实测失败。

## 为什么不直接修改共用统计方法

`incrementReceiveCount` 也被 `SmsCouponHistoryServiceImpl.insertSmsCouponHistory` 用于后台原始新增后的统计维护。给这个共用方法加状态过滤会改变后台原始新增的统计语义，而且原方法忽略计数行数，可能使历史存在而统计不增。本项不能借停发修复顺带裁决该后台合同。

Service 只增加普通重读仍保留重读之后的停发窗口；复用 `CouponSourceGrantMapper.selectCouponForUpdate` 会给所有普通发放引入来源 Mapper 锁依赖，并改变既有 mock 夹具。当前授权内没有既原子保护停发、又保持统计方法和调用合同不变的完整最小方案。
