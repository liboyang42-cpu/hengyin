## 旧不限量快照转限量候选的可达性反证

单看 `grantCouponWithReceipt` 的旧 publishCount 分流，旧不限量对象会走仅按 id 的 `incrementReceiveCount`，看似能在配置变成正数后绕过上限。但实际生产调用链不支持这个推演所需的配置转换：

1. `chengyinhub-admin/src/main/java/com/chengyinhub/web/controller/business/SmsCouponController.java:87` 的 `edit`，在调用 `smsCouponService.updateSmsCoupon` 之前执行 `stripStatCounters`。
2. 同文件 `:101` 的 `stripStatCounters` 明确 `setPublishCount(null)`，同时清空 receiveCount/useCount。
3. `SmsCouponMapper.xml` 的 `updateSmsCoupon` 只有 publishCount 非空才更新该列，所以该后台修改入口不改变发行上限。
4. 全部生产 Java 调用中，`updateSmsCoupon` 的实际 Controller 调用只有该入口；`ApiCouponController.java:182` 的 `setPublishCount` 在新建流程中，不是同券更新。

因此没有实际调用证据证明“同券旧不限量快照→另一事务改为限量”的生产触发可达。直接改 SQL 只会制造一个假设转换向量，且共用 `incrementReceiveCount` 还有后台原始新增调用，不宜以未证实缺陷改其语义。本项最终保留原源码，不新增该假设回归。未来若新增可改变发行上限的真实入口，需重新审阅该旧对象分流问题。
