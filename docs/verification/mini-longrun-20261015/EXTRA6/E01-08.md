## 真实签名与服务链

审计精确生产路径：

- `chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/ClubWaitlistTokenCodec.java`
- `chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/ClubWaitlistServiceImpl.java`
- `chengyinhub-system/src/main/resources/mapper/business/ClubEventOpsMapper.xml`

codec.token使用HMAC-SHA256绑定 `offerId:memberId:activityId:ticketId:offerExpiresAt毫秒值`，Base64URL无padding。matches不仅比较入参token的SHA-256与落库offer_token_hash，还常量时间比较从**当前entry事实**重新生成的token；只持有原token或复制原hash不能把它迁移到另一行/主体/活动/票种/到期时间。空entry/token/hash直接false；缺签名事实无法生成合法token，不走假成功默认。

quote与claim共用 `validateOffered`，差别在读取锁和最终是否执行claim CAS，不存在quote另写一套宽松归属判断。它们都要求成对的有效offerId/token、当前时间、活动ownerType=2、ownerId/ticketId且不能是多票请求。取出对应offer后依次约束：

- entry状态OFFERED、version存在；
- 调用member等于entry.memberId；
- 请求ownerId等于entry.activityId、ticketId等于entry.ticketId；
- expiresAt严格晚于now（等于截止即拒绝）；
- codec.matches双重签名/持久hash校验；
- 活跃series/occurrence/activity policy及waitlistEnabled，entry.clubId与policy.clubId一致；
- 原participationGuard与真实活动成员资格校验。

claim先requirePolicy锁定系列策略，再锁offer行；成功验证后生产claimOfferCas仍约束id、OFFERED、expectedVersion、member/activity/ticket及 `offer_expires_at > now`，仅一行成功才返回claim，零行409。quote只读取/验证后投影同一entry为claim视图，不执行claimCAS，也不扣第二份库存。

## 错配输入反证

| 特定输入 | 已有拒绝依据 |
| --- | --- |
| member A的token由member B提交 | service直接比entry.memberId；即使操作者拿到了原token仍拒绝，不能靠token替代登录主体 |
| 原token用于另一activity或ticket | 请求字段与entry字段直接比较；若另取新的offer行，token还因签名绑定offer/member/activity/ticket而不匹配 |
| 把offerId改为另一候补行 | 查询定位另一entry，签名包含id；保留原token/hash不足以通过matches |
| token末尾篡改/空串/伪造hash | HMAC重建及落库hash双比较；空串不会成为合法token，超256或字段不成对走400 |
| token未改但已CLAIMED/CONVERTED/EXPIRED/CANCELLED | service必须OFFERED，claim SQL再次约束OFFERED+version；不因token仍可重建就放行终态 |
| 已到截止的原token | service与SQL都严格 `expires > now`；不加宽到期、无续期或时间容差 |
| token签发后退会或资格受限 | 共用资格检查仍可拒绝quote/claim；重用缓存token不绕过当前成员资格 |

version不属于既有HMAC字段，但service读取当前version、state，SQL使用当前expectedVersion及OFFERED/期限CAS；不能为了“增加安全字段”改变token签名使已签发token集体失效。clubId虽未独立放入签名，也由entry所属activity与当前policy/club关联校验约束，不新增同义token协议。
