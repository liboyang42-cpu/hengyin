## 主体与父子范围链

精确生产文件：

- `chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/ClubEventOpsServiceImpl.java`
- `chengyinhub-system/src/main/resources/mapper/business/ClubEventOpsMapper.xml`

Controller的series/list、series/detail、series/occurrences均先从既有principal()取登录主体，并将请求clubId/seriesId明确传入对应service；不把请求中的actor作为授权主体。Service三个入口首先 `requireActivityManage(actor,club)`：检查正ID、principal/club与授权上下文一致、有效owner、ACTIVITY_MANAGE以及owner/co-owner角色。后续没有用series自身club覆盖请求中已经授权的club。

| 特定触发 | Service及SQL反证 |
| --- | --- |
| 对club A有权限，提交club B的seriesId与club A配对 | detail与occurrences均先调用 `selectActiveSeriesByIdAndClub(seriesId,clubId)`；WHERE同时要求id、club_id、ACTIVE。错配返回null，`validateReadableSeries`立即409，在未来场次/人数查询前终止 |
| 伪造Mapper返回另一club的父行 | `validateReadableSeries`仍要求请求club与父行club一致，并核正ID/topic/负责人及ACTIVE/version/策略完整；不会直接投影另一club数据。实际Mapper的id条件已排除返回另一series，不为虚构错误Mapper额外造修复 |
| listSeries试图取得另一club系列 | `selectActiveSeriesByClub`只按请求已授权club_id及ACTIVE取行，每行再次验证club；子查询使用该父行id与同一请求club |
| occurrence属于目标series，但关联activity属于另一club | `selectFutureOccurrences`同时JOIN series.club_id与activity.club_id到请求club；`selectSeriesOccurrenceRows`同样同时限定父series.club与activity.club，且排除activity.del_flag!=0。孤立/错误关联不被投影 |
| 请求同club不同series的场次 | 两条子查询均 `where o.series_id = #{seriesId}`，不单凭club取全部场次。Mapper Java的@Param名称与service实参顺序一致，无seriesId/clubId串位 |
| 伪造未来子行指向别的series或缺activity/time | detail遍历及list的seriesStartTime核row.seriesId与当前series、正activity、occurrenceAt和ACTIVE；无效状态409，不能据默认时刻伪造成功 |
| 日期清单出现已取消/过去场次 | `selectSeriesOccurrenceRows`刻意不排除时间与occurrence状态，但仍保留父series/club/activity关联；显示这些场次是既有清单合同，不属于跨域泄漏，不能顺手删除 |

清单的报名/退款子查询以已经筛选后的activity ID及owner_type=2统计。`countProtectedActivityHistory(activityId)`只对已范围过滤行调用，用于布尔编辑保护，不返回另一club正文/身份。它不必新增一个扩大合同的隐私/RBAC判断。
