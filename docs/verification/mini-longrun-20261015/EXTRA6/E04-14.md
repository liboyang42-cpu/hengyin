## 原消费方的独立窗口

E04-06已修reverse首读锁住历史，但redeemCoupon首读仍为普通selectSmsCouponHistoryById。

真实历史编辑入口：`SmsCouponHistoryController.edit` → `SmsCouponHistoryServiceImpl.updateSmsCouponHistory` → `SmsCouponHistoryMapper.updateSmsCouponHistory`；XML可更新coupon_id/member_id，没有剥离这两个字段。原字段权限不在本项改变。

具体反例：

1. redeem事务普通读history14，关联coupon30，随后按旧coupon30校验商家owner/scope/merchant。
2. 独立管理员事务将同history14改为coupon31（可同时改领券member），提交；模板31可能归另owner/merchant。
3. claimUnusedCoupon只按historyId/use_status/删除/时间CAS，仍可把当前已关联31的历史更新为已用。
4. Service却用旧coupon30入结算、更新30的use_count，审计relationId=30；当前历史已经关联31，权限判断与副作用和当前关联不同。

这不是同history重复CAS问题；E04-05的正确CAS/终态回读不能校验CAS时的原coupon关联。E04-10只保护模板自身status3的当前状态，也不固定history关联。

## 最小源码方案与锁序

仅将 `chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/SmsCouponHistoryServiceImpl.java` 的redeem首读改为现有 `selectSmsCouponHistoryByIdForUpdate`。不改Mapper接口、SQL或管理员编辑权限。

真实SQL已有FOR UPDATE；原history当前身份及有效期/软删状态从读取起持锁到核销事务提交，期间管理员无法改关联。仍history→coupon计数UPDATE锁序，与已修reverse及原成功CAS后的顺序一致，不引入先模板后历史反序。原owner/merchant校验、状态枚举、时间端点、status4已领可用、NULL语义和全部资金/结算计算保持。

先编辑提交时，Service锁读当前关联，用当前coupon重新做既有归属判断；归属不同返回原FORBIDDEN，不应继续用Controller之前读到的旧模板权限。

## QR验证分界：不能夸大此修复

只读 `ApiCouponController.qrToken` 先按当前history.memberId校验签发人；`SmsCouponService.generateCouponQrToken` 调用issueCoupon(historyId,时间,secret)。现动态凭据绑定history ID和时效，没有原coupon/member身份版本字段。

`couponVerification` 在Service事务之外验签得到historyId，普通读target/coupon并做预检，然后调用redeemCoupon(historyId,ownerMemberId,merchantId,actor...)。Service不接收原token身份信封，也没有领券会员参数校验。

因此首读锁可固定**Service内**读取到提交的历史关联，并使Service按进入时当前coupon执行已有商家权限；不能证明签发、验签、Controller预读到Service锁读之间的历史重分配会使原token失效，尤其member_id重分配涉及原凭据到底代表哪位领券人的合同。本项不新增token版本/API/字段权限，不能冒称修复全部token窗口；若需该边界，另行调查和决策。
