## 实际生产链

主文件为 `chengyinhub-system/src/main/java/com/chengyinhub/business/service/impl/ClubWaitlistServiceImpl.java` 与 `chengyinhub-system/src/main/resources/mapper/business/ClubEventOpsMapper.xml`。只读参考OmsTicketMapper.xml、原回归及取消入口DTO/controller。

cancel与promoteNext都是rollbackFor=Exception事务。两者先经requirePolicy取得含series/occurrence/activity的FOR UPDATE，再锁club owner；随后锁同ticket，最后读取waitlist。取消同一活动票种与晋升由共同series/club/ticket行锁串行化，不是两个无锁快照分别决定操作。

cancel按登录member/activity/ticket锁定活跃候补，并验证club与version；CLAIMED直接拒绝，要求从报名订单取消，不在候补入口释放已有订单名额。WAITING/OFFERED取消CAS同时约束id、原state、version、member/activity/ticket；CAS零行抛409。只有OFFERED真正取消成功才restoreInventory(1)，失败则抛异常使整个取消事务回滚；随后在同一事务调用promoteNextLocked。

promoteNextLocked只取同activity/ticket的WAITING，按joined_at asc、id asc锁定FIFO队首。每个队首验证scope、version及当前成员资格，退会队首先CAS CANCELLED然后继续，不占库存。有效队首先原子扣1库存，再做WAITING+version→OFFERED CAS；零行抛异常回滚占位。不会从CANCELLED重新offer，也不按较晚响应改写状态。

## 两种相邻顺序

| 具体交错 | 当前源码闭合 |
| --- | --- |
| cancel先持共同锁并取消WAITING，再promotion取队首 | 取消行已是CANCELLED，队首SQL只取WAITING，不能晋升该已取消行；WAITING本未占库存，取消不回补 |
| promotion先把队首WAITING→OFFERED提交，cancel随后取得当前锁读 | cancel看到OFFERED及新version，CAS取消并仅归还该offer持有的1名额；在同一事务按原FIFO晋升下一位 |
| cancel OFFERED回补后，与另一promoteNext相邻 | 取消事务仍持series/club/ticket锁并完成内部晋升，外部晋升后取锁只能读提交后的库存；不能同时消费同一回补名额 |
| 同取消重复到达，原队列没有重新加入 | 首次CAS将其移出活跃态；后次selectActiveWaitlistForUpdate返回null，false且不再restore |
| 取消CAS/回补/后续offer CAS失败 | 异常传播至原事务，原取消、回补与晋升整体回滚；不通过catch把失败伪装为成功 |
| CLAIMED与cancel相邻 | cancel不能在已CLAIMED状态释放hold或自行执行退款；保持原订单边界，不增新资金政策 |

OmsTicketMapper库存回补有remaining+qty<=total的SQL上限，扣减有remaining>=qty；结合共同锁与state/version CAS，未发现本项取消/晋升之间双回补或双占库存的可达分支。持锁不代表已实测无死锁，本轮没有运行并发或数据库验证。

## 一个可独立裁决的协议边界（不计已知bug）

旧取消请求与用户重新加入交错：取消旧entry成功后，同member对同activity/ticket重新join生成新entry；之前在途的重复cancel随后到达，会按三元组锁到**当前新entry**，因为 `ClubWaitlistRequest` 只有activityId/ticketId，controller/service没有entryId/expectedVersion/requestId供服务端区分旧手势与新队列。

精确只读依赖：`chengyinhub-system/src/main/java/com/chengyinhub/business/domain/dto/ClubWaitlistRequest.java`、`chengyinhub-admin/src/main/java/com/chengyinhub/web/controller/api/ApiClubEventOpsController.java` 的cancelWaitlist，以及本laneService.cancel。现有“取消一次回补一次”测试没有插入重新join；本项cancel×promotion反证也不覆盖新entry代次。

这可能是当前“取消当前票种候补”命令的既定语义，不能擅称安全缺陷。若产品要求取消绑定旧手势/旧entry，需要C00先裁决命令合同，并精确转交DTO/controller/调用者；仅改现有Service无法区分两个字段完全相同的请求。应作为独立协议审计或BLOCKED_DECISION，不能自动增加必填version/requestId，也不能在本项造新接口。没有第二个充分独立且未入池的候选，不强凑。

## 接续补充：直接取消×晋升真实MySQL回归源码

新文件：`chengyinhub-admin/src/test/java/com/chengyinhub/business/longrun/E01_06Test.java`。状态 **REGRESSION_SOURCE_DELIVERED_UNVERIFIED**，预期2个方法，全部NOT_RUN：

1. `offeredCancellationCommitsBeforeBlockedPromotionWithoutSecondRestoreOrOffer`：初始队首已OFFERED持有唯一名额，remaining=0。取消先通过真实policy FOR UPDATE并持锁停在显式门闸；另线程实际调用promotion并在相同事务锁上等候。放闸后取消在同事务回补1并晋升下一位，外部promotion随后看到remaining=0返回false。
2. `promotionCommitsBeforeBlockedCancellationThenNextFifoMemberGetsOnlySlot`：初始3个WAITING、唯一remaining=1。promotion先持policy锁停门闸，取消请求在锁上等候；晋升队首提交后取消锁读见其OFFERED，取消并回补，在同事务晋升原第二位。

两方法共同断言：原队首CANCELLED/version2，第二位OFFERED，第三位WAITING；第二/第三位joined_at相同，生产id升序必须选择第二位；唯一offer及库存0，库存不负也不超total。票Mapper代理仅在**真实SQL返回1后**计数restore/deduct：两序restore都只能1，deduct分别1/2。重复cancel原member返回false，再promote仍false，计数/库存及原队首终态不变，无重offer。最终事实通过独立DataSource/JDBC读取已提交状态，不用代理返回值代替数据库事实；另核第二位落库token hash与其身份匹配。

门闸/锁等待不是仅靠线程调度推断：第一个真实policy SELECT返回后才发firstLocked并等待释放；第二线程在真实事务连接读取connection_id后发attempt。主线程独立查询information_schema.innodb_trx，必须观察该精确connection_id的 `trx_state='LOCK WAIT'`，再断言Future尚不能完成；观察不到或权限不足即失败，不assume/跳过。释放后两个Future完成才读取事实；finally释放门闸、终止并等待worker退出后才允许scratch清理。

全部policy/成员资格/票/候补查询与state/version/库存SQL执行生产ClubEventOpsMapper.xml及OmsTicketMapper.xml；真实ClubWaitlistServiceImpl经Spring TransactionInterceptor与共享DataSource事务管理器运行。Java代理只布置门闸与观察SQL影响行数，不替换结果；participationGuard为这两个入口未调用的stub，不把它当真实资格验证，成员资格实际来自club/member生产SQL。
