## 可实现producer签名

建议在既有 `chengyinhub-system/src/main/java/com/chengyinhub/business/domain/JourneyStory.java` 新增：

```java
public static String remapNodeIds(String rawJson, java.util.Map<Long, Long> nodeOldToNew)
```

输入为**所有待映射引用仍是旧ID的原始剧情JSON**；输出为同一JSON树中已知节点引用映射后的文本。不是HTTP或DTO，不增加DSL、schemaVersion、条件类型或优先级。

必须操作raw JsonNode/ObjectNode，不经JourneyStory.parse→typed序列化：JourneyStory及其嵌套DTO用@JsonIgnoreProperties(ignoreUnknown=true)，typed往返会丢扩展字段。树写回保持未知字段/值、对象成员相对顺序与数组顺序，字符串内容不做替换；不承诺保留JSON空白/转义的字节形式。未修改时可直接返回原raw。null/空白沿现有remapChapterIds/其他helper原样返回。

## 精确语义位置与边界

仅改当前JourneyStoryValidator认识的条件槽位，不递归扫描未知扩展对象中的同名字段：

- `stages[].end.changed[].when`：单个条件对象或null。
- `ending.endings[].when[]`：条件列表。
- `ending.exhibits[].when`：单个条件对象或null。
- `ending.badges[].when[]`：条件列表。
- `ending.dispositionNodeId`：可空正整数引用。

在这些条件对象中：op恰为NODE_COMPLETED时映射其nodeId；比较条件var精确匹配 `sys.outcome.([1-9][0-9]*)` 时仅替换末尾ID。保留op、value和其它字段。不按数字文本全局替换，不碰chapterId/npcId/tag/正文/未知扩展字段。

validator还认识sys.asked/sys.mistakes/sys.passed等节点型变量；本次请求明列的最小范围是NODE_COMPLETED、dispositionNodeId、sys.outcome。**不默默扩围**；若C00需要这些其他既有变量同步映射，应先在合同中点名，仍不是新增DSL。已知存在不等于本次已完整承诺所有节点型变量。

## 缺映射及非法ID：沿既有语义，避免意外收紧

- withEndingChapters现有NODE_COMPLETED逻辑用 `cond.path("nodeId").asLong()`，缺映射抛IllegalArgumentException；JourneyStoryValidator对此也用asLong(0)后检查>0。因此字符串数字/可转换小数目前存在coercion入口，不能在新helper中悄悄改成严格IntegralNumber并把它称为原合同。建议本次按现有asLong正值语义取源ID；无正值/无对应映射拒绝，不留旧引用，不置空或删除条件。
- dispositionNodeId的validator用optionalPositiveLong：缺席/null可保留，其余必须IntegralNumber、canConvertToLong且>0，不能套NODE_COMPLETED的宽转换；缺映射拒绝。
- sys.outcome源var必须是TextNode并精确匹配当前正整数ID形状；匹配后Long溢出应转为IllegalArgumentException，不截断；已知sys.outcome前缀但非法形状建议明确拒绝，其他未知var值保留给原validator处理，不能把未知DSL变默认命中。
- 映射目标必须非null正Long，目标<=0拒绝，不能把非法目标写进JSON。null/空map仅在没有需映射引用时容许；遇到引用即缺映射错误。映射不删除missing引用，不用映射values猜已经映过，不按sort/id顺序推测目标。
- JSON语法不可读或根非对象：IllegalArgumentException，不回落空剧情。此helper不是完整剧情validator，不因稀疏草稿缺无关必填字段而额外拒绝；保存/发布的原validator仍负责全量校验与归属。

## 真实consumer链与避免二次映射

`CmsTopicServiceImpl.persistJourneyStoryAfterChapterRebuild` 当前链：清旧opening → remapChapterIds → 回填本次opening → 如果存在endingChapters则withEndingChapters → 更新journey_story_json。createTopic/updateTopic均在章节/节点取得新DB ID后进入此方法，routeNodeMaps.oldToNew已有真实旧新节点映射。

关键：JourneyStory.withEndingChapters目前已对**新章DTO条件的副本**映射NODE_COMPLETED。如果C03在它后面直接对整故事调remapNodeIds，就会把部分新ID当旧ID再次映射。不能用“映射不到时如果在values里就放行”的猜测绕过，因为交叉映射/ID碰撞会使含义不清。

建议冻结的producer/consumer组合：

1. CORE/C03对来源storedStory先调用新remapNodeIds，得到旧剧情已有各段和disposition的已映射版本；然后沿既有opening/章映射流程。
2. E03在同一JourneyStory源码中，让withEndingChapters对每条**新生成章条件的deepCopy**复用私有单条件映射逻辑，覆盖NODE_COMPLETED和sys.outcome；不对已有root/disposition/其它旧段再次全树映射。
3. C03维持withEndingChapters传入routeNodeMaps.oldToNew，新生成条件仅映一次。没有结局章的保存也必须执行第1步，以修复旧stages/exhibits/badges/disposition引用。
4. CORE/C03-05待producer公共完整SHA后集成；不能向不存在签名堆引用。本队不编辑CmsTopicServiceImpl。

以上第2步需要C00明确同意纳入E03-11的JourneyStory精确内部修改；若只授权独立新helper而不允许调整既有withEndingChapters，新章sys.outcome引用仍有缺口，consumer不能宣称整体已修复。
