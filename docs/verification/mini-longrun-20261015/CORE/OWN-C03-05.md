## 已有保真与精确例外

CmsTopicServiceImpl.persistJourneyStoryAfterChapterRebuild将完整JSON传给JourneyStory.withOpeningChapterId/remapChapterIds，而不是反序列化到已知字段POJO再写回。JourneyStoryValidator.validate返回原trimmed字符串；remapChapterIds对JSON树原位更新stages章节ID，因此原顺序和未知JSON属性通常保留。update未传journeyStory时以exist.journeyStoryJson回退后重映射。

这里纠正OWN-C03-02证据中过宽的一句话：remapChapterIds对stages/opening缺映射抛错；ending.endings[].chapterId缺映射则按原既定注释移除chapterId，降级保留标题/摘要，并非一律拒绝。章节身份唯一不串位的结论不变，不能借此改变旧结局降级政策。

## 真实未闭合节点引用

合法旧plain journeyStory（不是本次章节ending字段）可含：

```json
{"schemaVersion":1,"ending":{"endings":[{"code":"visited","title":"到过旧节点","when":[{"op":"NODE_COMPLETED","nodeId":11}]},{"code":"other","title":"其他","fallback":true}]}}
```

JourneyStoryValidator.validateEndings/requireCondition明确支持上述字段。若本次已有NodeDTO.id=11重建生成901，service现persistJourneyStoryAfterChapterRebuild只调用remapChapterIds；当routeNodeMaps.endingChapters为空时不调用withEndingChapters。后者只处理本次结局章里NODE_COMPLETED的转换，不转换原plain ending。结果旧nodeId=11仍留在已写story中。草稿保留坏引用，后续发布引用校验拒绝，或不完整旧路径读结局落fallback；不应称保存读回已完整保真。

同类已定义节点引用还有ending.dispositionNodeId及条件var=sys.outcome.<旧id>/sys.passed等；不能只修一个字段留同源残缺。无需新增HTTP/DTO/DSL字段或改变结局首命中顺序。
