## 实际合同与缺口

TopicCreateDTO.collaboratorIds是List<Long>，仅有字段说明，没有元素非空/正数/去重/邀请接受规则。TopicUpdateDTO直接继承。现有B02合同明确该集合全量替换：缺席且已有行则拒绝，显式[]清空，但没有定义数组内null/重复如何处理。

CmsTopicServiceImpl.saveCollaborators只逐项新建dataType=1/dataId=topicId/memberId行；CmsCollaboratorsMapper.xml动态insert在memberId为null时略去该列。base_schema的cms_collaborators.member_id本来可null，只有主键，没有(data_type,data_id,member_id)唯一约束。因此这里不能依据既有非空约束或唯一键声称“原持久化明确拒绝但service吞掉”：数据库结构本身允许空行/重复关联。

现引用材料将此集合描述为合作者署名ID名单，明确不能把署名等同于邀请接受/协作编辑权限。成员存在性/协作许可不是本项可自行增加的鉴权模型。

## 不猜输入及成员政策

可选处理至少包括：整包拒绝null/重复、跳过null且去重、保留重复原顺序。当前已读的既有DTO/mapper/合同未给唯一答案。未经C00冻结选择就直接归一化或新增member查询，会改变已有输入错误语义/名单含义；不能以“修保存”偷偷建立合作权限规则。
